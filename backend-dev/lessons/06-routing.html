What is routing in backend?

The HTTP method says what you want to do; the route says where. Routing is the server taking that pair, like GET /api/books, and mapping it to the one handler that knows how to respond.

What you'll learn

  • Why method + path together form the routing key
  • Static vs dynamic routes, and path vs query parameters
  • Nested routes and the meaning they express
  • Versioning, deprecation and catch-all routes

Method + path = a unique key

A request arrives as GET /api/books. The server combines the method and the path into one key and looks up a handler, which then runs the business logic, talks to the database and returns data.

That's why GET /api/books (list books) and POST /api/books (create a book) never clash: same path, different keys.

Analogy

Think of an office reception desk. "Deliver" or "pick up" is the method, and "Floor 3, Room 12" is the path. Reception looks at both and sends you to exactly one person. The same room can have one person for deliveries and another for pickups.

Watch a router match requests

Pick a request (or type your own). The router checks each registered route in order until one matches, then pulls the parameters out of the URL.

Static and dynamic routes

Static route

/api/books is a fixed string with no variables. It always points to the same handler and returns the same kind of data.

Dynamic route

/api/users/:id has a slot. /api/users/123 fills id with "123". The colon syntax is the convention in almost every language and framework.

Gotcha

Everything in a URL is a string. 123 arrives as "123", and converting it to a number is your job (lesson 9: transformations).

Read a dynamic route out loud and it explains itself: GET me the data at /api/users for the user with id 123. That human readability is a core goal of REST.

Path parameters vs query parameters

/api/users/123/posts?page=2&limit=20&sort=desc

static path parameter query parameters

  • Path parameters are part of the route and carry meaning: which resource you're talking about.
  • Query parameters are key–value pairs after the ? carrying metadata: how you want it (search terms, page, limit, filters, sort order).

Why not put a search term in the path, like /api/search/some value? It technically works, but it's hard to maintain and loses the semantic meaning of a path. And since GET requests have no body, the query string is the natural place for these options.

Analogy

The path is the shelf number of a book in a library: it identifies the thing. Query parameters are what you tell the librarian: "only paperbacks, newest first, 20 at a time."

Example: pagination

// GET /api/books           → page 1 by default
{
  "data": [ /* 20 books */ ],
  "total": 100, "page": 1, "totalPages": 5, "limit": 20
}
// next page:  GET /api/books?page=2

Versioning and deprecation

Requirements change. Maybe a new mobile app needs title instead of name. Rather than inventing /api/new-products, put a version in the route:

GET /api/v1/products
{ "data": [
  { "id": 1, "name": "Lamp", "price": 20 }
] }
GET /api/v2/products
{ "data": [
  { "id": 1, "title": "Lamp", "price": 20 }
] }

Catch-all route

Registered last, * catches anything nothing else matched, like /api/v3/products. Instead of an empty or confusing default, it returns a friendly 404: "this route doesn't exist". Try it in the router above.

Key takeaways

  • Routing maps method (what) + path (where) to a handler. Same path with different methods means different handlers.
  • Static routes are fixed strings; dynamic routes have :param slots, whose values always arrive as strings.
  • Path params identify the resource; query params carry options such as search, pagination, filters and sorting.
  • Nested routes express relationships: /users/123/posts/456.
  • Version routes (/v1, /v2) to ship breaking changes with a migration window, then deprecate.
  • A catch-all route at the end returns a clear 404 for unknown paths.

Check yourself

Where should "sort by price, descending" go: path or query?

Query: ?sort=price&order=desc. It's an option about how to return the data, not which resource it is.

Why must the catch-all route be registered last?

Routers usually match in order. A * registered first would swallow every request before the specific routes got a chance.

Your handler does if (params.id === 123) and it's never true. Why?

Path params are strings: "123" !== 123. Transform (parse) the value first.
