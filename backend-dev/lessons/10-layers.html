Controllers, services, repositories, middleware & request context

Between "request arrives" and "response leaves", a production server passes the request through a chain of pieces with clear jobs. Middleware handles what every request needs, the controller speaks HTTP, the service does the real work, the repository talks to the database, and a request context carries shared facts along the way.

What you'll learn

  • The request lifecycle inside your server
  • What controllers, services and repositories are each responsible for
  • How middleware and next() work, and why order matters
  • What request context is for, and why user IDs come from it

The life of a request inside your server

The operating system hands the request to the port your server listens on. From there it passes through middleware, gets routed to a handler, and flows down through the layers and back. Press play and watch the context fill up as it goes.

Analogy: a restaurant

The host stand checks every guest on arrival (middleware). The waiter takes your order, makes sure it's valid, and brings back the plate and the bill (controller). The chef cooks, coordinating several stations, and never talks to customers (service). The pantry fetches exactly the ingredients asked for (repository). And the order ticket travels with your meal: table number, allergies, notes that every station can read (request context).

None of this layering is required: you could do everything in one function. It's a design pattern that keeps a growing codebase maintainable, debuggable and easy to extend.

Controller, service, repository

Speaks HTTP. It receives the request and response objects from your framework, and nothing below it should know HTTP exists.

async function listBooks(req, res) {
  // 1. bind: pull data out of the request into native types
  const input = { sort: req.query.sort };
  // 2. validate + transform (fill defaults for optional params)
  const parsed = listBooksSchema.safeParse(input);
  if (!parsed.success) return res.status(400).json({ errors: parsed.error.issues });
  const { sort = "date" } = parsed.data;
  // 3. call the service with clean data + who is asking
  const books = await bookService.listBooks({ sort, userId: req.ctx.userId });
  // 4. choose the status code and send the response
  return res.status(200).json({ data: books });
}

Business logic. It should look like an ordinary function: from a glance, you shouldn't be able to tell it's used by an API. It orchestrates repositories, external APIs, emails and notifications.

async function listBooks({ sort, userId }) {
  const books = await bookRepo.findAll({ sort });
  const favourites = await favouriteRepo.findIdsByUser(userId);
  return books.map(b => ({ ...b, isFavourite: favourites.has(b.id) }));
}

// Some services never touch the database:
async function sendWelcomeEmail({ email }) {
  await mailer.send(email, "welcome");
  return { success: true };
}

Data access only. It takes parameters, builds a query, and returns what the database returned. One method, one kind of result.

async function findAll({ sort }) {
  const column = sort === "name" ? "name" : "created_at"; // whitelisted, never raw input
  return db.query(`SELECT id, name, created_at FROM books ORDER BY ${column}`);
}

async function findById(id) {
  return db.one("SELECT * FROM books WHERE id = $1", [id]);
}
// ✕ Don't write findBooks(id?) that returns one book OR all books.

In Node.js a body-parser middleware usually deserializes JSON before your handler runs. In Go, Python or Rust you typically "bind" the body into a struct or class explicitly in the controller.

Middleware

Middleware are functions that run in the middle, at the boundaries between entry, routing, handlers and the response. Like handlers they receive request and response, plus one more thing: next.

  • Call next() to pass control to whatever comes next (another middleware, the router or the handler).
  • Or respond right away and end the request there, without wasting resources further down.
function rateLimit(req, res, next) {
  const hits = counter.increment(req.ip, { windowSeconds: 2 });
  if (hits > 30) return res.status(429).json({ message: "Too many requests" }); // stop here
  next(); // otherwise, hand over
}

Why not just call a helper in each handler? With hundreds of endpoints, you'd still repeat that call everywhere, and someone will forget one. Middleware runs for every request (or every route in a group) automatically: it's code reuse at the pipeline level.

CORS

Checks the Origin and adds allow headers for your frontend. Runs first, so unknown origins are rejected early.

Security headers

Adds CSP, HSTS and similar headers to every response.

Logging

Records the method, path, status and duration of every request, for debugging and audits.

Authentication

Verifies the token. Fail → 401 right here. Success → puts the user and role into the context.

Rate limiting

Too many requests from one IP in a time window → 429.

Compression & parsing

gzip large responses; parse JSON or form bodies; optionally run validation.

Global error handler

Catches an error from anywhere, decides 4xx vs 5xx, and returns a consistent error shape.

Order matters

Requests flow one way through the chain, so a middleware only sees what happened before it. A typical order:

CORS→security headers→logging→rate limit→auth→routes & handlers→error handler (last)
Gotcha

Put the global error handler in the middle and it can't catch errors thrown by handlers after it. It must be last.

Request context

A request context is a small key–value store scoped to one request. Every middleware and handler on that request can read and write it, so they can share facts without being wired directly to each other. When the request ends, it's gone.

Who's asking

Auth middleware stores userId and role; handlers and permission checks read them later.

Request ID

A UUID generated up front is logged everywhere and forwarded to other services (e.g. X-Request-ID), so you can trace one request across logs and microservices.

Cancellation & deadlines

Timeouts and abort signals propagate to downstream calls, so work stops when the client gives up instead of hanging forever.

Security rule

When creating a book, take user_id from the context (set by verified auth), never from the request body. A malicious client could simply put someone else's ID in the payload.

Key takeaways

  • Controllers deal with HTTP: bind, validate and transform, call the service, pick the status code, respond.
  • Services hold business logic and orchestration, and know nothing about HTTP.
  • Repositories do one database operation each and return one kind of result.
  • Middleware gets req, res and next: it either passes control on or ends the request early (401, 429…).
  • Middleware order matters: CORS early, error handler last.
  • Request context is request-scoped shared state: user identity, request ID, deadlines. Trust it over client-supplied IDs.

Check yourself

Where should "send a 404 if the book doesn't exist" be decided?

The service (or repository) reports "not found", for example with a typed error or a null result. The controller (or global error handler) translates that into the HTTP 404. Status codes belong to the HTTP layer.

Why make authentication a middleware instead of code in each handler?

Every protected route needs it. As middleware it runs automatically, rejects bad tokens early with 401, and stores the user in the context for downstream code, with no duplication and no forgotten routes.

What's wrong with findBooks(id?) returning a single book when given an id and all books otherwise?

It breaks single responsibility: callers can't rely on the return shape, and the logic branches inside the data layer. Use findAll() and findById(id).
