Complete REST API design

Good API design is mostly about removing guesswork. REST already gives you the rules: resources as plural nouns, methods as verbs, predictable status codes. Follow them consistently and anyone can integrate your API without reading your code. And you stop debating "plural or singular?" for good.

What you'll learn

  • Where REST came from and what the name means
  • URL design rules: plural nouns, hierarchy, slugs, versioning
  • Idempotency and choosing the right method, including custom actions
  • A step-by-step workflow from wireframes to endpoints
  • Pagination, sorting and filtering done right
  • Consistency, sane defaults and docs

Why standards?

Even experienced developers still ask: plural or singular paths? PATCH or PUT? Which method for an action like "archive"? Which status code? The standards were written in the multi-page-app era, and today's single-page apps raise new questions.

Without shared rules, the only way to learn how an API behaves is to read its code or trial-and-error it. With them, consumers can predict behaviour: fewer bugs, fewer meetings, faster integrations. The aim here isn't new standards, just a clear set of rules extracted from the existing ones.

Where REST came from

Representational

A resource (a user, a book) can be represented as JSON for an API client, HTML for a browser, or XML.

State

The resource's current data. A cart's state is its items, quantities and total.

Transfer

Moving representations between client and server using HTTP methods.

Designing URLs

https://api.example.com/v1/books/harry-potter?format=short#reviews

scheme · authority (an api. subdomain is a common convention) · version · path · query · fragment (jumps to a page section; not used by APIs)

  • Resources are always plural nouns: /books lists books, and /books/42 is still books, because you're picking one item from the collection. Never /book/42.
  • / means hierarchy: collection → item → sub-resource or action.
  • Lowercase, hyphens, no spaces or underscores. "Harry Potter" becomes the slug harry-potter, which is safe across browsers, servers and operating systems.
  • Version in the path (/v1) so breaking changes get a new version (lesson 6).
Analogy

A REST URL reads like a library's shelving system: /books is the aisle, /books/42 is one book on it, /books/42/reviews is the notes tucked inside that book. Learn the system once and you can find anything.

Methods and idempotency

Idempotent means: doing it once or a thousand times leaves the server in the same state. (Responses can differ. GET can return new books someone else added, but your call didn't change anything.)

MethodUseIdempotentWhy
GETFetchyesReading causes no side effects.
PATCHUpdate some fieldsyes*Setting name A→B, again and again, stays B.
PUTReplace the whole resourceyesSame payload, same result.
DELETERemoveyesThe second call gets a 404, but changes nothing.
POSTCreate, or a custom actionnoEach call creates another book with a new ID.

*for "set field to value" updates, which is how PATCH is used in practice.

PATCH vs PUT: in today's JSON-heavy single-page apps you almost always send partial fields, so use PATCH for updates. Mixing them up is tolerable internally, but a public API should respect the semantics so integrators aren't misled.

Custom actions don't fit create, read, update or delete: "send email", "archive organisation", "clone project". REST leaves POST open-ended for exactly this: POST /organizations/:id/archive. Archiving isn't just status = archived; the server may also clean up projects, notify members and more, so it deserves its own action.

From wireframes to endpoints

Design the interface before writing any code: how will consumers use this API?

Playground: an organizations API

This is a tiny in-browser server following every rule in this lesson. Use the quick buttons or write your own requests, and watch the status codes.

EndpointDoesSuccess

POST /organizationsCreate; returns the new entity201

PATCH /organizations/:idPartial update; returns the updated entity200

Notice: create and list share a path, and get, update and delete share a path. The method tells them apart. And a POST doesn't automatically mean 201: return 201 only when something new was created.

Pagination, sorting and filtering

Never return every row. Serializing a thousand records is slow, the client waits, and the user only sees 10–20 at a time anyway.

Pagination

page and limit in; data, total, page, totalPages out. Defaults: page 1, limit 10–20.

Sorting

sortBy and sortOrder. Default createdAt desc. Without an explicit sort, databases return rows in no guaranteed order.

Filtering

Field names as params: ?status=archived&name=acme.

Rule

A list that matches nothing is 200 with an empty array, not 404. Return 404 only when the client asks for a specific resource that doesn't exist.

Consistency is the feature

Once a consumer integrates one endpoint, they'll assume the rest work the same way. Reward that assumption.

  • Same patterns everywhere: if organizations are plural, projects are plural. If one payload says description, none say desc.
  • camelCase JSON keys, in requests and responses.
  • No abbreviations: you know what dsc means; your integrators don't.
  • Sane defaults: page 1, limit 10, newest first. A new organization defaults to status: "active", so only require what you truly need.
  • Server-managed fields (id, createdAt, updatedAt) are never accepted from the client.
  • Interactive docs (OpenAPI/Swagger, lesson 28) from day one: a playground for integrators and a testing tool for you.
Analogy

A consistent API is like a city where every street sign uses the same format. After the first few streets you stop reading the signs carefully, because you know where to look.

Key takeaways

  • REST came from Fielding's constraints for scaling the web: client–server, uniform interface, layers, cache, statelessness.
  • Paths are lowercase plural nouns with hierarchy; slugs use hyphens; version in the path.
  • GET, PUT, PATCH and DELETE are idempotent; POST isn't. Use POST for custom actions like /:id/archive.
  • Workflow: wireframes → nouns (resources) → schema → actions → interface design → code.
  • Status codes: 201 for creates, 204 for deletes, 404 only for specific missing resources, 200 for empty lists.
  • Lists need pagination, sorting and filtering with sane defaults.
  • Consistency beats cleverness: same names, same shapes, same rules everywhere.

Check yourself

Design the endpoint to fetch the comments of post 7.

GET /v1/posts/7/comments: plural nouns, hierarchy through slashes, paginated like any list.

GET /tasks?status=done matches nothing. What do you return?

200 with { "data": [], "total": 0, "page": 1, "totalPages": 0 }. An empty list isn't an error.

"Publish a draft article": which method and path?

It's a custom action with side effects (notifications, timestamps), so POST /v1/articles/:id/publish.

A client calls DELETE twice on the same item. Is DELETE still idempotent if the second call returns 404?

Yes. Idempotency is about server state, not the response. The second call changes nothing.
