Production-grade configuration management

Configuration is everything that controls how the same code behaves in different places: which database it talks to, what it logs, which features are on, how long it waits. Managed well, you change behaviour without touching code. Managed badly, you get configuration chaos.

What you'll learn

  • What counts as configuration (far more than secrets)
  • The main types of config
  • Where config lives: env vars, files, key–value stores and secret managers
  • Why each environment needs different values
  • Security, and the one habit that saves you: validating config at startup

More than passwords

Say "config" and most people think of the database URL, JWT secret and API keys. That's like saying a car is just its engine: crucial, but only part of the picture. Config also decides how your app starts, how it connects to other services, what and where it logs, where metrics go, and which features are enabled for whom.

Analogy

Your code is a recipe; config is the kitchen it's cooked in. The same lasagne recipe needs different oven settings at home, in a test kitchen and in a restaurant serving hundreds. You don't rewrite the recipe; you adjust the settings.

Each setting has its own character: some are secret (leaking them causes real damage), some change often and some quarterly, some are the same everywhere and some differ per environment. Modern backends are distributed systems (databases, caches, queues, third-party APIs), and every integration point needs config, including how to handle failures and stay secure.

Configuration chaos

Hard-coded values scattered through the codebase, environments that behave differently, secrets committed to Git, and bugs nobody can reproduce because nobody knows which setting was live. A misconfigured frontend shows the wrong button; a misconfigured backend can leak customer data, charge cards wrongly, or take the platform down.

Types of configuration

Application settings

Port, log level (debug locally, info in prod), connection pool size, timeouts. A 60 s timeout on an AI-image endpoint that takes 80 s gives you 504s.

Database

Host, port, user, password and database name (often combined into one URL), plus query timeouts.

External services

API keys for email (Resend, Mailchimp), payments (Stripe), auth (Clerk) and so on.

Feature flags

Turn features on or off, for some or all users, without deploying.

Security

JWT and session secrets, session timeouts.

Performance tuning

Pool sizes, worker counts, runtime knobs like Go's GOMAXPROCS.

Business rules

Maximum order amount, discount limits, centralised instead of buried in code.

Infrastructure

DevOps-level settings for deployments, regions and scaling.

Feature flags in action

Analogy

A feature flag is a light switch wired in advance. The new feature is already installed (deployed); flipping the switch (config) turns it on for some rooms (users), with no electrician (deploy) needed.

Where config lives

Environment variables

The most common source, provided by the operating system. Locally a .env file is loaded by a library like dotenv. In the cloud, the deployment injects them, often pulled from a secret manager.

Files

YAML (supports comments, unlike JSON) or TOML. Open-source projects like Authelia and Apache Answer ship a config.yaml with server, log, storage and session sections.

Key–value stores

Consul, etcd: lightweight, central, and cloud-native.

Secret managers

HashiCorp Vault, AWS Parameter Store, Azure Key Vault, Google Secret Manager: encrypted, audited and centralised. Ideal across Kubernetes, autoscaling and multiple clouds.

Real apps often use a hybrid: a loader reads several sources with a defined priority, merges them into one runtime config, then validates it.

Why each environment differs

Same code, different priorities:

Priority: developer productivity and debugging.

LOG_LEVEL=debug
DB_POOL_MAX=10             # a laptop handles this easily
DATABASE_URL=postgres://localhost:5432/app
FEATURE_NEW_CHECKOUT=true  # try everything
STRIPE_API_KEY=sk_test_…

Priority: automated validation and quality. A GitHub Action spins up a throwaway environment for unit and integration tests.

LOG_LEVEL=warn
DATABASE_URL=postgres://ci-db:5432/test
EMAIL_PROVIDER=fake        # never email real people from CI

Priority: mirror production, without production costs. Used by developers and testers, so a little slowness is fine.

LOG_LEVEL=info
DB_POOL_MAX=2              # deliberately small to save money
FEATURE_NEW_CHECKOUT=true
STRIPE_API_KEY=sk_test_…

Priority: reliability, security and performance.

LOG_LEVEL=info             # don't flood valuable logs
DB_POOL_MAX=50             # ready for traffic spikes
FEATURE_NEW_CHECKOUT=us-only
STRIPE_API_KEY=(from secret manager)

Because behaviour lives in config, none of these differences require a code change.

Keeping config secure

  • Never hard-code secrets (database URLs, API keys, JWT secrets) or commit them to Git.
  • Prefer a secret manager. It encrypts secrets at rest and in transit, so you don't have to build that yourself. When it comes to security, over-engineering is fine.
  • Least-privilege access. Frontend developers get the frontend's config, backend developers get databases and Redis, and only DevOps gets cloud-infrastructure credentials.
  • Rotate keys and secrets periodically.
Analogy

A .env file passed around on Slack is a house key under the doormat. A secret manager is a bank vault: locked, logged, and you can change the locks.

The one habit: validate config at startup

Reading process.env.WHATEVER directly means a missing or mistyped value surfaces as a strange bug in production, possibly weeks later. Instead, load every source, then validate the whole config with a schema before the server starts: required vs optional, types, defaults. If anything is wrong, refuse to start (lesson 16 shows why that's the safe failure).

// config.ts (Zod). In Go, use a validator such as go-playground/validator.
const bool = z.enum(["true", "false"]).transform(v => v === "true");

const Config = z.object({
  PORT:                 z.coerce.number().int().default(8080),
  LOG_LEVEL:            z.enum(["debug", "info", "warn", "error"]).default("info"),
  DATABASE_URL:         z.string().url(),                 // required
  DB_POOL_MAX:          z.coerce.number().int().min(1).default(10),
  STRIPE_API_KEY:       z.string().startsWith("sk_"),      // required
  FEATURE_NEW_CHECKOUT: bool.default("false"),
});

export const config = Config.parse(process.env); // throws → the app refuses to start
Gotcha

Env vars are always strings. Boolean("false") is true, and so is z.coerce.boolean() on "false". Parse booleans explicitly, as above.

Key takeaways

  • Config is how the same code behaves differently: connections, logging, timeouts, flags, business rules, secrets.
  • Centralise it, or you get configuration chaos: scattered values, inconsistent environments, leaked secrets.
  • Sources: env vars, YAML/TOML files, key–value stores and secret managers, often layered by priority.
  • Each environment has different priorities, so values differ (e.g. pool size 10 in dev, 2 in staging, 50 in prod).
  • Never hard-code secrets; use a secret manager, least-privilege access and rotation.
  • Validate all config with a schema at startup, and fail fast if it's wrong.

Check yourself

Your team wants to show a new pricing page to 10% of users and turn it off instantly if conversions drop. What do you use?

A feature flag (with percentage targeting), stored in config or a flag service, so it can change without a deploy.

Why is staging's pool size smaller than production's if staging should mirror production?

Staging mirrors behaviour, not scale. It's used by a handful of developers and testers, so a small pool keeps cloud costs down at the price of some acceptable slowness.

FEATURE_X=false but the feature is on in production. Likely bug?

The string "false" was coerced to the boolean true (any non-empty string is truthy). Parse booleans explicitly in your config schema.
