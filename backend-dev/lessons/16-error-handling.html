Error handling and fault-tolerant systems

Errors aren't exceptional: queries fail, external APIs time out, users send bad data, and logic hits edge cases. The question is never whether errors happen, but how ready you are to detect, contain and recover from them. This lesson is about a fault-tolerant mindset, not a framework.

What you'll learn

  • The five kinds of errors you'll meet, and which are most dangerous
  • Catching problems before users do: health checks and monitoring
  • Recoverable vs non-recoverable errors, graceful degradation and error boundaries
  • Building a global error handler
  • Error messages and logs that don't leak secrets

Five kinds of errors

The sneakiest and most dangerous. Nothing crashes; the code just does the wrong thing. An e-commerce store applies a discount twice and produces negative shipping costs, losing money on every order for weeks before anyone notices.

Usual causes: misunderstood requirements, a slightly wrong algorithm, edge cases nobody considered.

  • Connection errors: the network is down, the DB is overloaded, or the connection pool is exhausted. The whole app stops working.
  • Constraint violations: a duplicate email (unique), or an order pointing at a customer that doesn't exist (foreign key). Stronger validation prevents some; uniqueness only the database can know.
  • Query errors: typos in table names, queries so complex they time out.
  • Deadlocks: operations waiting on each other in a circle.

Payment processors, email providers, S3, Redis, Auth0 or Clerk: each is a failure point you don't control, but can't realistically avoid.

  • Network: timeouts, DNS failures, network partitions.
  • Auth: bad credentials, expired tokens, missing permissions.
  • Rate limits: 429 responses. Back off exponentially (wait 1, 2, 4 minutes…) until it succeeds.
  • Outages: they will happen (even big clouds go down). Have fallbacks, e.g. if Redis is down, use an in-memory cache.

Bad data from clients: wrong format, out-of-range values, missing required fields. These are the easiest to handle: you know the rules, so enforce them at the entry point and return 400 (lesson 9).

The classic: you add OPENAI_API_KEY locally, ship the feature, and forget to set it in production. These errors appear when moving between dev, staging and production.

Fail fast on configuration

Validate every required config value before the server starts. A crash at startup is the best case, not the worst.

The best error handling starts before the error

Finding problems the moment they appear, before they spread, beats any clever recovery.

Analogy

A /health endpoint returning 200 is a doctor checking your pulse. Useful, but it doesn't tell you much. Deep health checks are the blood tests: they confirm the organs are actually doing their job.

Basic health check

GET /health → 200. External tools ping it constantly; the status code is what matters.

Database checks

Can we connect? How long does a representative query take? 500 ms creeping up to 4 s is a warning sign.

External services

Test transactions for payments, test emails to an internal inbox, test tokens against your auth provider.

Core functionality

Config loaded, essential caches warm, internal data consistent.

Monitoring and observability

Covered in depth in lesson 18. The key ideas for error handling:

  • Track errors from every source: HTTP, database, external services, business logic.
  • Watch performance, not just errors. Slowing response times and rising resource use usually come before a failure.
  • Watch business metrics. A sudden drop in successful checkouts signals a problem even when error rates look normal.
  • Use structured (JSON) logs that tools like Grafana Loki can parse, search and chart.

Responding to errors

Recoverable → retry

A failed email send, a temporarily exhausted connection pool, a network blip. Retry with exponential backoff, but don't pile extra load onto a system that's already struggling.

Non-recoverable → contain & degrade

Serve cached data, switch off non-essential features, offer an alternative, and keep the damage contained to one area.

Analogy

When a café's card machine dies, it doesn't close. It takes cash and maybe stops serving the fancy drinks. Customers get a slightly reduced service instead of a locked door.

Recovery

  • Automatic: restart a hung process, clear a corrupted cache, fail over to a backup. Test these, since a bad recovery can make things worse.
  • Manual: some incidents need human judgement. Document the runbook and rehearse it, so it can be done quickly under stress.
  • Data first: code can be redeployed; data can't. Take backups at key moments, and know how to restore them and replay transaction logs.

Propagation and error boundaries

Not every error should be handled where it happens. Often a low-level error should be wrapped with context and bubbled up to a level that knows what it means for the business. But keep that flow deliberate, so an error doesn't escape and take down the whole process or neighbouring services.

Analogy

Ships have watertight compartments: a breach floods one section, not the whole hull. Separate processes, timeouts at service boundaries and message queues between services (lesson 14) are your compartments.

The final safety net: a global error handler

Errors can come from any layer: validation in the handler, business rules in the service, database errors in the repository. Instead of handling each one in place, bubble them all up (throw in JS or Python, return in Go) to one error-handling middleware that turns each kind into the right response.

// global error-handling middleware (Express-style)
app.use((err, req, res, next) => {
  if (err instanceof ValidationError)
    return res.status(400).json({ message: "Invalid input", errors: err.fields });
  if (err.code === "unique_violation")          // Postgres 23505
    return res.status(409).json({ message: "Book already exists" });     // some APIs use 400
  if (err instanceof NoRowsError)
    return res.status(404).json({ message: `Book ${req.params.id} not found` });
  if (err.code === "foreign_key_violation")    // Postgres 23503
    return res.status(404).json({ message: "Author not found" });
  logger.error({ err, requestId: req.ctx.requestId }); // full details stay in logs
  return res.status(500).json({ message: "Something went wrong" }); // never leak internals
});

More robust

Forget to handle a unique violation in one repository method and the user gets a vague 500. With a central handler, every case is covered once, everywhere.

Less duplication

No copy-pasted "is it unique? foreign key? no rows?" checks in every repository method. Set it up once and tweak it over time.

Errors and security

  • Never forward raw errors to clients. Database messages contain table, column and constraint names, a map for attackers. Unknown errors get a generic "Something went wrong"; details go to your logs.
  • Keep auth errors generic: "Invalid email or password", never "No user with this email" (lesson 8). The OWASP Cheat Sheet Series is a great reference.
  • Don't log secrets: passwords, emails, API keys, card numbers. Logs are shipped to many external services, and leaked logs feature in many major breaches. Log the user ID and a correlation (request) ID instead.

Key takeaways

  • Plan for errors: logic, database, external services, validation and configuration.
  • Logic errors are the most dangerous because nothing crashes; validation errors are the easiest.
  • Validate configuration at startup so a bad deploy fails before it serves traffic.
  • Detect early: deep health checks, plus monitoring of errors, performance and business metrics.
  • Retry what's recoverable; contain and degrade gracefully what isn't. Protect data above all.
  • Bubble errors to a global handler that maps them to the right status codes and generic messages.
  • Never leak internals in responses, and never log sensitive data.

Check yourself

Your recommendation service is down. Should the product page return 500?

No. It's non-essential: degrade gracefully by hiding the section or showing bestsellers from cache. The product, cart and checkout should keep working.

Why is "crash on startup if DATABASE_URL is missing" a good thing?

With rolling or blue-green deployments, the old version keeps serving while the new one fails its startup checks, so users never see the problem. Discovering it at request time means real users get 500s.

A repository throws duplicate key value violates unique constraint "books_name_key". What should the client see?

A clean 409 (or 400) with "A book with this name already exists". Never the raw message, which reveals table and constraint names.
