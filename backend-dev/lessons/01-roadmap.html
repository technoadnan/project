Roadmap for backend from first principles

Backend engineering is much more than writing CRUD APIs. It's building systems that stay reliable, scalable, fault-tolerant and maintainable. This lesson is the map: every later lesson is one stop along a request's journey, or one of the things that keeps that journey safe in production.

What you'll learn

  • What "backend engineering" actually covers
  • Why learning through one framework leaves blind spots
  • The path a request takes, and which lesson covers each stop
  • The production concerns that surround every request

More than CRUD

Most people learn backend through a course or bootcamp, then patch the gaps for years by trial and error. The result is knowledge that works but has holes. A first-principles roadmap fills those holes in a deliberate order.

Reliable

Gives the right answer every time, even under odd inputs.

Scalable

Handles 10× the users without a rewrite.

Fault-tolerant

When a part breaks, the whole thing doesn't.

Maintainable

The next engineer can change it without fear.

The framework lens problem

If you learn backend as Express, Spring Boot or Rails, you see every problem through that one ecosystem. Now imagine your company moves from Rails to Go for performance. How much of what you know comes with you?

If you understand the systems underneath (HTTP, routing, serialization, databases), almost all of it does. If you only know the framework's API, very little.

Analogy

Learning one framework is like memorising the dashboard of one car. Learning first principles is learning to drive: steering, braking and the rules of the road. After that, any car is just a new layout of buttons.

How to use this course

Don't try to memorise the map. Walk it once, lesson by lesson. Each topic makes the next one easier because they all describe the same request.

Key takeaways

  • Backend engineering means building reliable, scalable, fault-tolerant and maintainable systems, not just endpoints.
  • Framework-first learning leaves blind spots. Principles transfer across languages; framework APIs don't.
  • Most topics are stops on one request's path: network → HTTP → routing → middleware → validation → controller → service → database.
  • Supporting systems (cache, queue, search, storage, real-time) each solve one problem the database is bad at.
  • Production concerns such as errors, config, logs, shutdown, security and scaling wrap around every request.

Check yourself

Your team switches from Ruby on Rails to Go. Which knowledge transfers best?

Understanding of the underlying systems: HTTP, routing, serialization, databases, caching. The Rails-specific APIs mostly don't transfer.

Which layer would hold the rule "a user can't order more than 5 items on sale"?

The business logic (service) layer. It's a business rule, not a data-format check or a database concern.

Why doesn't one database handle everything?

Each supporting system is optimised for one job: Redis for fast lookups, queues for deferred work, Elasticsearch for text relevance, S3 for large files. A single general-purpose database does all of these poorly at scale.
