Real-time backends

Two people look at the same task board; one drags a card and the other should see it move live. Everything so far followed one shape (the client asks, the server answers), and the server has no way to speak first. This lesson walks from polling to long polling, Server-Sent Events and WebSockets, measures how many connections one machine can hold, and shows how to scale real-time across many servers.

What you'll learn

  • Why polling's cost scales with viewers, not events
  • Long polling and its gap
  • Server-Sent Events: a response that never ends
  • WebSockets: handshake, frames, masking, heartbeats

The server can't speak first

HTTP is request–response: the client starts every conversation (lesson 5). When something changes on the server, there's no way to tell a browser that didn't ask. Every real-time technique is a way around that.

Analogy

Waiting for a package. Polling: you check the doorstep every five minutes. Long polling: you phone the courier and they stay on the line until it arrives, then hang up, and you call again. SSE: the courier keeps a radio channel open and announces each delivery. WebSocket: a two-way radio; you can both talk whenever you like.

Polling: ask again and again

The intuitive fix: every few seconds the browser asks "has board 412 changed?". Usually the answer is no. It works, and for an internal tool with a few users it's a perfectly reasonable choice. At scale, three things hurt:

  • Delay: a change waits on average half the interval before anyone sees it.
  • Cost: each poll is a full request: load balancer, auth middleware, logging, database query, serialization. Mostly to say "nothing changed". Shrink the interval for snappier updates and the load grows in proportion.
  • Battery: on phones, every poll wakes the radio, one of the most power-hungry things a phone does.

The core flaw: polling's cost scales with the number of viewers, not the number of events. A board where nothing happens all day costs as much as a busy one. We want the server to speak first, and to pay only for actual changes.

Long polling: hold the question open

Ask, and let the server take its time: it holds the request open (up to a minute or so) and answers the moment something changes. The browser handles the response and immediately asks again.

RFC 6202 documents the technique together with its flaws: after each answer there's a gap while the browser processes the response and reconnects, during which the server can't reach it. Average latency is about one network transit, but the worst case is more than three. It served the web for years; then came something cleverer.

Server-Sent Events: a response that never ends

What if the response simply never finishes? The browser makes an ordinary GET; the server answers 200 with Content-Type: text/event-stream and keeps the connection open, writing a few lines of text whenever there's news. Still plain HTTP, no new protocol.

# the response body, as it trickles in
retry: 3000

id: 41
event: task.moved
data: {"task":7,"to":"in_progress"}

id: 42
event: task.created
data: {"task":9,"title":"Fix login"}

// the browser side: reconnection is built in
const es = new EventSource("/boards/412/events");
es.addEventListener("task.moved", (e) => {
  moveCard(JSON.parse(e.data));
});
// on a drop, the browser waits `retry` ms, reconnects,
// and sends Last-Event-ID: 42 automatically

Just four fields: id, event, data and retry. Because SSE is a web standard, the browser reconnects for you and sends a Last-Event-ID header, so the server can replay what was missed.

SSE is no toy. Uber built its driver push platform on it, LinkedIn used it for instant messaging with typing indicators and read receipts, and every major LLM API streams tokens to you with it: each word appearing in your chat window is a data: line. Its one limit is in the name: the server sends. A browser that wants to tell the server something (the user dragged a card) needs a separate POST. For many products that's fine.

WebSockets: one connection, both directions

A WebSocket starts life as an ordinary HTTP GET, so it passes through everything that understands HTTP, and then upgrades into something else.

The browser sends 16 random bytes, base64-encoded. The server appends a fixed GUID from the spec, takes the SHA-1, base64-encodes it and answers 101 Switching Protocols. That isn't security (anyone can compute it); it proves the responder actually understood the WebSocket request and isn't a cache replaying an old response. After that there are no more headers, methods or status codes: just a two-way stream of frames.

Frames and masking

Tiny headers

The first byte holds FIN (last piece of a message) and the opcode: 1 text, 2 binary, 8 close, 9 ping, 10 pong, 0 continuation. The second holds the mask bit and a 7-bit length; 126 or 127 mean "real length in the next 2 or 8 bytes". A small message costs a 2-byte header, versus hundreds of bytes of headers per poll.

Why browsers mask

Every browser→server frame is XORed with a fresh random 4-byte key sent in clear text. It isn't encryption. While the protocol was being designed, researchers showed that attacker-chosen bytes could look like an HTTP request to a confused proxy and poison its cache (say, replacing a popular analytics script for everyone behind it). Random masking means page JavaScript can't control the bytes on the wire.

Heartbeats

When a phone walks into a lift or switches from Wi-Fi to mobile data, the server receives nothing (no error, no close) and keeps holding a socket for a user who's gone. To a socket, idle and dead look identical. The fix is to ask: either side sends a ping, the other must reply with a pong, and no pong within ~30 seconds means the connection is dead and its resources are freed.

How many connections can one machine hold?

An experiment on a 16-core, 61 GB Linux box with a tiny Go server that only accepts and holds connections. Each limit hit was something different:

File descriptors

In Unix every socket is a file. ulimit -n said 1,024, so after stdin/stdout/stderr, the listener and the epoll instance, it stopped at ~1,017. Clients saw timeouts, not errors; the healthy-looking server logged "too many open files". Node, Python and Java inherit this soft limit; Go raises its own to the hard maximum at startup.

Ports: the client's limit

Next stop: 28,190, "cannot assign requested address". A TCP connection is identified by four things (source IP, source port, destination IP, destination port). The server's side never changes, so the load-testing client's ephemeral ports (32,768–60,999) ran out. The "65,000-connection server limit" is a myth; dialling from three client IPs reached 75,000.

Memory: the real ceiling

75,000 idle connections used ~722 MB: about 9.75 KB each (mostly the goroutine and buffers per connection), so a million is just under 10 GB of heap, plus kernel buffers. Systems chasing millions watch all sockets from one epoll loop instead of a goroutine each.

Scaling out: connections are state

We spent the whole course making servers stateless. But a persistent connection is state: it lives in one process's memory and can't be moved or shared. With two instances behind a load balancer, browser A connects to instance 1 and browser B to instance 2, and when A moves a task, instance 1 has no way to reach B.

Sticky sessions (always routing a client to the same instance) don't help: B is still on the other instance. The instances need to talk to each other, which is what pub/sub is for.

At-most-once vs at-least-once

Redis pub/sub is fire-and-forget: an instance that isn't subscribed at that instant (say, mid-deploy) misses the message forever. If you need at-least-once delivery, use something that stores messages and tracks acknowledgements: Redis Streams, Kafka, or a queue.

Catching up

Connections drop all the time: network switches, closed laptop lids, load-balancer idle timeouts. Number every message and have the client say where it got to. Uber's push platform does exactly this: "I have up to sequence 2" → the server resumes from 3. It's the same idea as SSE's Last-Event-ID.

Fan-out and reconnect storms

  • Fan-out: the real work is events × subscribers. If 30,000 people watch a board, one moved card means 30,000 writes. Discord measured 0.9–2.1 seconds to publish one event to a 30,000-member community online at once; the fix was spreading the fan-out across the machines that own the recipients.
  • Reconnect storms: an instance holding 50,000 connections dies, and 50,000 clients reconnect in the same second, each wanting its initial state. Slack made reconnecting cheap by caching start-up data at the network edge, so the storm never reaches the core.

Key takeaways

  • HTTP can't let the server speak first. Polling works around it, but its cost scales with viewers, and its delay averages half the interval.
  • Long polling holds requests open but leaves a gap after each response.
  • SSE keeps one HTTP response open forever, with built-in reconnect and Last-Event-ID catch-up; server → client only.
  • WebSockets upgrade an HTTP request into a two-way stream of tiny frames; browsers mask frames to protect proxies; ping/pong detects dead connections.
  • One machine can hold around a million idle connections; limits come from file descriptors, client ports, then memory (~10 KB per connection).
  • Across instances, use pub/sub; choose at-least-once delivery when messages matter, number messages for catch-up, and plan for fan-out and reconnect storms.

Check yourself

You poll every 2 seconds. On average, how long until a user sees a change? And what happens to load if you poll every 500 ms?

About 1 second, half the interval. Polling every 500 ms cuts the delay to ~250 ms but quadruples the request load, nearly all of it "no change".

A notifications feed only ever flows from server to browser. SSE or WebSocket?

SSE: plain HTTP, automatic reconnection with Last-Event-ID, and no need for a bidirectional channel. User actions can go through normal POST requests.

After scaling your WebSocket server to 3 instances, users only see some live updates. Why, and does enabling sticky sessions fix it?

Each instance can only write to its own sockets, so an event handled on one never reaches users connected to the others. Sticky sessions don't fix it; publish events through pub/sub (Redis, NATS, Kafka) so every instance can deliver to its own connections.

Your load test stalls at ~28,000 connections with "cannot assign requested address", though the server has plenty of RAM. What's the limit?

The load-testing client ran out of ephemeral source ports. Each connection needs a unique (source IP, source port, destination IP, destination port) tuple; use more client IPs or machines.

Why do WebSocket servers send pings?

A client that vanished (dead battery, lost network) sends no close frame, so an idle connection and a dead one look the same. A missing pong within the timeout reveals the dead connection so its resources can be freed.
