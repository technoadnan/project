Graceful shutdown

Even with zero-downtime deploys, the old server must eventually stop, perhaps in the middle of someone's payment. Graceful shutdown teaches your backend good manners: stop taking new work, finish what's in progress, clean up, then exit. No lost requests, no double charges, no corrupted data.

What you'll learn

  • Process lifecycles and Unix signals
  • SIGTERM, SIGINT and SIGKILL, and why the last one is unstoppable
  • Connection draining and choosing a timeout
  • Cleaning up resources in reverse order
  • What graceful shutdown looks like in real code

The moment that matters

You're buying something on Amazon. Mid-payment, a deploy replaces the server handling your request. Does the payment vanish? Do you get charged twice by a race condition? This problem is as old as servers, and the answer is a graceful shutdown.

Analogy

When it's late and your guests need to leave, you don't shove them out and slam the door. You let conversations wrap up, say goodbye, tidy up, and then close the door. That's the behaviour we want from a server.

Processes and signals

Your backend runs as a process: it's born when it starts, lives while running, and dies when it's terminated. When the operating system wants it to stop, it doesn't just pull the plug; it follows a protocol. On Unix-like systems (Linux, which nearly every server runs, and macOS), that protocol is signals, a form of inter-process communication. Your app registers handlers that run when a signal arrives.

SignalMeaningSent byCan you handle it?
SIGTERM"Could you please finish up and leave?" A polite nudge.Kubernetes, systemd, PM2, deploy toolsyes

Analogy

SIGTERM and SIGINT are clicking "Shut down" on your computer. SIGKILL is yanking the power cord out of the wall. Respect the polite signals, or the plug gets pulled with no chance to clean up.

Step 1: drain connections

Analogy

At closing time a restaurant doesn't switch off the lights on diners. First the door staff stop letting new customers in. Then they tell everyone inside: "We're closing in 20 minutes, take your time." People finish, pay and leave.

For your backend, connection draining means:

  1. Stop accepting new connections and requests.
  2. Let in-flight requests finish; at any moment there might be 10 or 600 of them.
  3. Then close.

HTTP server

Refuse new requests and complete the in-flight ones.

Database

Finish running queries and transactions; accept no new ones.

WebSockets

Tell connected clients you're closing, then close the sockets.

The timeout trade-off

You can't wait forever. Production systems set a hard limit, commonly 30 seconds (Kubernetes' default grace period). Too short and you cut off legitimate work; too long and deploys crawl. Base it on your real request durations: 30 s is plenty for a typical API, while long-lived WebSocket or streaming workloads may need more thought.

Draining also involves the load balancer and service discovery: the instance is deregistered and its health checks start failing, so no new traffic is routed to it.

Step 2: clean up resources

Before leaving your desk, you put the mug in the sink and coil the cables. Your process must release what it acquired:

Database connections

Commit or roll back open transactions explicitly, then close the pool. Abandoned transactions can lead to deadlocks or inconsistent data.

Network connections

The OS limits how many a process can hold; leaks waste memory and hurt performance.

File handles & temp files

Unreleased handles pile up and eat memory.

Caches, queues, workers

Let background workers finish their current job, then close Redis.

Reverse order

You put on socks, then shoes; you take off shoes, then socks. Release resources in the reverse order you acquired them, so nothing is torn down while something that depends on it is still running.

The whole sequence

In code

Your framework or library usually provides the hard parts (a Shutdown or close method that stops accepting and drains). Your job is to wire signals to them in the right order:

ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
go server.ListenAndServe()

<-ctx.Done()                                   // block until SIGINT or SIGTERM
log.Info().Msg("shutdown signal received")

shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
server.Shutdown(shutdownCtx)  // stop accepting, drain in-flight requests
jobs.Shutdown()               // let workers finish, close Redis
db.Close()                    // acquired first, released last
log.Info().Msg("server exited cleanly")
async function shutdown(signal) {
  logger.info({ signal }, "shutdown signal received");
  setTimeout(() => process.exit(1), 30_000).unref(); // hard deadline
  await new Promise(r => server.close(r));  // stop accepting, finish in-flight
  await worker.close();                      // finish current jobs
  await redis.quit();
  await pool.end();                          // close DB connections last
  process.exit(0);
}
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);

In the video's demo (a Go backend), pressing Ctrl+C logs "interrupt signal received", closes the HTTP server and database, shuts down the Asynq job server ("waiting for all workers to finish… all workers have finished"), then "server exited". It takes about a second, because nothing was in flight.

Key takeaways

  • Every deploy stops an old process. Graceful shutdown makes sure that never interrupts real work.
  • The OS talks to your process with signals: handle SIGTERM and SIGINT the same way; SIGKILL can't be handled.
  • Drain first: stop accepting new requests, let in-flight ones finish, within a timeout (often 30 s).
  • Then clean up: commit or roll back transactions, close pools, connections and file handles, in reverse order of acquisition.
  • If you ignore the polite signals, the orchestrator will eventually SIGKILL you, mid-request.

Check yourself

Kubernetes sends SIGTERM but your app has no handler. What happens to in-flight requests?

By default SIGTERM terminates the process immediately, so in-flight requests are cut off. (If the process ignored it, Kubernetes would SIGKILL it after the grace period anyway.) Either way, requests are lost: add a handler that drains.

Your server opened the DB pool, then Redis, then started the HTTP listener. What order do you shut down?

HTTP listener → Redis/workers → DB pool: the reverse of acquisition, so nothing still in use loses its dependencies.

Why not set the shutdown timeout to 10 minutes "just to be safe"?

Deploys and scaling would hang for minutes, and a stuck request would block everything. Pick a limit based on your real request durations.
