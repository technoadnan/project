What is a backend, how does it work and why do we need it?

A backend is a computer that listens on an open port (usually 80 or 443) for requests coming over the internet, and either serves something (HTML, images, JSON) or accepts data. Strip its job down to one word and you get: data.

What you'll learn

  • The real hops a request takes: DNS, firewall, reverse proxy, your app
  • Why apps need one central server
  • How a frontend actually runs in your browser
  • Four reasons the backend can't just live in the browser

A computer listening on a port

"Server" literally means something that serves. It waits for HTTP, WebSocket or gRPC requests on a port that's reachable from the internet, then responds with static files (HTML, JS, images) or data (usually JSON). It also accepts data the client sends.

Analogy

Think of a building with numbered doors. The IP address is the street address, the port is the door number, and the server is the person waiting behind door 443 to answer whoever knocks.

Following a real request

The video traces a live request to backend-demo.<domain>/users, a Node.js app on an AWS EC2 instance. Here are the hops:

DNS records

An A record maps a name to an IP address. A CNAME maps a name to another name.

Firewall

The AWS security group only lets in the ports you allow: 22 (SSH), 80 (HTTP) and 443 (HTTPS). Everything else is dropped before it reaches the machine.

Reverse proxy

Nginx sits in front of your apps, redirects HTTP to HTTPS (with Certbot certificates) and forwards each domain to the right local port.

Your process

The Node app listens on localhost:3001, kept alive by a process manager (PM2). The same request on the box itself gets the same response.

Notice

On your laptop, localhost:3000/users works directly. In production, DNS, the firewall and the proxy are just extra hops that eventually deliver the request to the same kind of local process.

Why do we need a backend at all?

Take a single Instagram like. Between your tap and your friend's notification, something has to know about both of you.

Your app only knows your world: your feed and the people you follow. The server must hold everyone's state in one place. That's why it's centralised, and why its whole job revolves around data: fetching it, receiving it and persisting it.

How a frontend actually works

A frontend server (here, a Next.js app on the same EC2 box behind the same Nginx, on port 3000) doesn't run your logic. It ships code to the browser, and the browser runs it.

Why not put backend logic in the browser?

The browser runs code it downloaded from strangers, so it locks that code in a sandbox: only the DOM, a few browser APIs (localStorage, cookies) and limited network calls.

Analogy

The browser is like a hotel room for visiting code. Guests can use what's in the room, but they can't wander into the building's control room, open other guests' doors or carry the safe out. That protects you, and it also makes the room a terrible place to run a business.

1 Security sandbox

Backends need the file system (log files) and environment variables (secrets). Browsers forbid both, by design.

2 CORS

Browsers block calls to other domains unless those APIs send the right headers. Backends must call any service they need.

3 Databases

Native drivers need raw sockets, binary data and persistent connections. Servers keep a shared connection pool; a million browsers would each open their own.

4 Computing power

Users might be on a 256 MB, single-core phone. A central server can be given more CPU and RAM whenever load grows.

Analogy: connection pools

A bank doesn't hand every customer a key to the vault. A few tellers (pooled connections) serve thousands of customers in turn. Letting every browser connect to the database is like giving everyone a vault key and letting them all crowd in at once.

Key takeaways

  • A backend is a computer listening on an open port, serving content or accepting data.
  • A production request hops: DNS (name → IP) → firewall (allowed ports) → reverse proxy (domain → local port) → your app.
  • Backends exist to hold centralised state. Their one-word job is data.
  • Frontend code is downloaded and run by the browser; backend code runs on your server.
  • Browser sandboxing, CORS, database connection needs and unpredictable device power keep backend logic on the server.

Check yourself

Your DNS is correct, the app is running, but requests time out. Port 443 is missing from the security group. What happens?

The cloud firewall drops the traffic before it reaches the instance, so Nginx and your app never see the request.

What does the reverse proxy decide?

Which local process gets the request, based on the domain (server_name). For example frontend-demo → port 3000 and backend-demo → port 3001. It also handles the HTTP → HTTPS redirect and TLS certificates.

Give two reasons a browser can't talk to Postgres directly.

Browsers can't open raw TCP sockets or keep the persistent binary connections native drivers need. And even if they could, every user would open their own connection, overwhelming the database with no shared pooling. (It would also expose credentials.)
