Testing for backend engineers

A test is just a second program that runs your program and makes claims about what happened. Writing good ones is the hard part: a rushed, incomplete test gives false confidence, which is worse than no test. This lesson covers the tests a backend engineer writes and runs (about 80% of a team's testing): what to fake and what to keep real, how to avoid flaky tests, TDD, and how to measure a test suite honestly.

What you'll learn

What a test is

Strip away the frameworks and a test is a function that calls your code with chosen inputs and complains if the output isn't what you expected:

// a test with no framework at all
function testMoveTask() {
  const board = newBoard();
  board.move(7, "done");
  if (board.columnOf(7) !== "done")
    throw new Error(`task 7: want done, got ${board.columnOf(7)}`);
}

What frameworks add

A runner finds every test, generates a main that calls them, runs the program and reports results. go test, for instance, writes a _testmain.go and compiles it into a board.test binary. Assertions are the checks that fail a test; give them messages that say exactly what was expected and what happened.

The most valuable job of a test suite is catching regressions: bugs you already fixed coming back when someone changes a function months later. Run the suite in CI on every pull request, and the regression is caught before merge instead of reported by users. That's what lets a team move fast without fear.

Kinds of tests and a better mental model

Unit

One unit of code in isolation. What's a "unit": a function, a class, a package? There's no universal definition.

Integration

Two or more parts working together, usually your code plus something you didn't write, like a database. It can bypass auth and go straight to the logic under test.

End-to-end

The whole system the way a user experiences it: log in, keep the session, open the dashboard, create a task.

Unlike "unit", this is enforceable: a machine can check whether a test opened a socket. Other names you'll hear (regression, functional, performance, security tests) describe a test's purpose, not a new kind; any of them can be small, medium or large.

Test doubles

A real handler writes to Postgres, publishes to Redis, charges a card and sends an email. To test it, you hand it stand-ins that look and act like those services. The category is called test doubles, after stunt doubles in films. Most people call them all "mocks", but there are five kinds:

Passed only because a signature requires it; never actually used.

const noopLogger = { info() {}, error() {} };
const svc = new TaskService(repo, noopLogger); // logging is irrelevant here

Returns canned answers, whatever you ask.

const users = { findById: async () => ({ id: 7, name: "Priya", plan: "pro" }) };

A stub that also records how it was called.

const calls = [];
const users = { rename: async (id, name) => { calls.push({ id, name }); } };
// later: expect(calls).toEqual([{ id: 7, name: "Priya S." }])

Pre-programmed with expectations, and fails the test if they aren't met.

const mailer = mock<Mailer>();
mailer.send.expectCalledOnceWith({ to: "priya@example.com", template: "invite" });

A working but simplified implementation, unfit for production: same inputs and outputs, different internals.

class InMemoryUserRepo {
  #rows = new Map();
  async save(u) { this.#rows.set(u.id, u); }
  async findById(id) { return this.#rows.get(id) ?? null; }
}

Check the result, not the steps

You can end a test two ways: state verification asks the system where it ended up ("is task 7 in done? did the sequence number go up?"); interaction verification asks a double what it saw ("was publish called twice?"). Watch what happens when someone refactors the handler to publish one combined event instead of two; users see no difference:

A test that breaks on refactors that change nothing for users is a change-detector test. Default to state verification; use interaction checks only when the interaction is the behaviour, like "the welcome email is sent exactly once".

Don't mock what you don't own

You mock the payment provider's client so charge() returns { success: true, newBalance }. Tests pass; production fails. Every field name, duplicate-charge behaviour and error format in that mock came from you. Instead, wrap the provider in your own small interface with your own types, mock that, and add a few contract tests against the provider's sandbox to prove your wrapper matches reality.

Design for testability

Handlers become hard to test when they build their own dependencies: open their own database connection, create their own Redis client. Pass dependencies in instead (dependency injection), and arrange code as a functional core, imperative shell:

imperative shell: HTTP, Postgres, Redis, payments, email
functional core
canMove · price · validate · plan

Pure core, thin shell

Decisions and calculations live in pure functions: values in, values out, nothing to mock, trivially testable. All talking to the outside world sits in a thin shell around them, which has little logic left to test.

What to fake, and what to keep real

Databases: keep them real

Swapping Postgres for an in-memory fake buys speed and costs fidelity. Think about which bugs live in the data layer: a wrong column name, a missing index, a forgotten unique constraint, a transaction that doesn't isolate what you thought, a JSON operator Postgres has and your fake doesn't. You replaced exactly the layer where those bugs live. Use a real database and make it cheap:

Transaction per test

Begin a transaction, run the test inside it, roll back. The database is untouched for the next test. Requires code that accepts a transaction handle (dependency injection again).

Template databases

Run migrations once on a template; each test gets CREATE DATABASE t42 TEMPLATE app_template in milliseconds, so tests can run in parallel.

Testcontainers

Starts a real database container from your test code (SDKs for most languages) and hands you its address.

Networks

Wrap external APIs in your own interface and fake that. When you want to test the HTTP client code itself (headers, retries, error parsing), start a real local server in the test (Go's httptest) or intercept at the network layer (MSW in Node). Requests really travel over TCP, but never leave the machine.

Time

sleep(100) then check works on your laptop, and fails on a busy CI machine where the background work took 110 ms. Raising the sleep only makes tests slower until the next failure. Instead, wait for a condition (a channel message, a callback, or polling with a timeout), or inject a clock you control.

Hermetic tests

A test that brings its whole environment with it, starting what it needs and stopping it afterwards, runs identically on your laptop, a colleague's machine and CI. Testcontainers makes the database hermetic; an injected clock makes time hermetic.

Test-driven development

TDD is a workflow, not a kind of test: write the test before the code, in a loop of three steps.

TDD is contested. Kent Beck, who popularised it, restated the loop in 2023 ("Canon TDD"). Ian Cooper's talk TDD, Where Did It All Go Wrong argues people took "unit" to mean "class", mocked everything, and drowned in tests that broke on every refactor; the unit should be a behaviour, tested through a module's public interface. DHH's 2014 TDD is dead. Long live testing. pushed back on test-first and designing for mockability. A practical stance: TDD shines when you know what the answer looks like but not how to compute it (parsers, pricing rules, state machines), and gets in the way when you're still exploring what to build.

Flaky tests

A flaky test passes and fails on the same code. It's worse than a missing test: a gap is visible, but flakiness teaches the team "just re-run it", until a real failure gets re-run too. A 2014 study by Luo and colleagues of 201 real flaky-test fixes found three top causes:

1

Async wait

Waiting the wrong way: sleeps instead of conditions. Fix: wait for a signal.

2

Concurrency

Things inside the test racing each other. Fix: synchronization primitives (Go's synctest, for example).

3

Test order dependency

Test B passes only if test A ran first and left a row, a global or a file behind. It breaks when someone adds a test or turns on parallelism.

For a flaky test you can't fix now: delete it (more often right than you'd think), or quarantine it out of the blocking suite with an owner, a date and a reason. Automatic retries hide the problem.

Measuring tests: coverage

Code coverage is the share of code executed by your tests. The tool splits each function into branch-free basic blocks, inserts a counter in each, runs the tests and reports blocks that never ran. It records that code ran, not that anything was checked: a suite that calls everything and asserts nothing scores 100%. And it isn't one number:

What does a coverage number say about quality? Inozemtseva and Holmes (ICSE 2014) generated thousands of test suites for large Java programs and found only a low to moderate correlation between coverage and bugs caught, once suite size is held constant. Google's guidance is a useful calibration (60% acceptable, 75% commendable, 90% exemplary), with two warnings: the uncovered red lines tell you more than the percentage, and a mandatory target breeds low-value tests written to hit it.

Mutation testing: testing your tests

A mutation testing tool (Stryker for JavaScript, for example) damages your code on purpose: < becomes <=, + becomes -, a return value becomes empty. Each damaged copy is a mutant. If a test fails, the mutant is killed; if all tests still pass, it survived, and your tests aren't really checking that code.

Measuring code: complexity metrics

Cyclomatic complexity

Thomas McCabe, 1976: the number of independent paths through a function. Draw it as a graph and compute edges − nodes + 2, or count 1 + decision points (each if, loop, case, &&, ||). The common limit is 10, which McCabe called reasonable but not magical; he noted that a big, flat switch breaks it while staying easy to read.

Cognitive complexity

SonarSource's measure of how hard code is to understand. A flat switch barely counts; every level of nesting adds more. An if inside a loop inside an if is far harder to hold in your head than three ifs in a row.

On the task board, the hub's run method scored 8 cyclomatic (third place) but 19 cognitive (top of the list): eight ways in, deeply nested. Treat both numbers as flags that point you at code to look at, not as rules.

Tools that find problems without running anything

Linter

Flags suspicious patterns, such as a condition that's always true or an ignored error. Not syntax (the compiler's job) and not correctness.

Formatter

Rewrites code into the team's standard layout. Changes no behaviour, ends style debates.

Type checker

Catches type misuse, like arithmetic on a string, often right in your editor (Go, TypeScript, Rust).

Static analysis

A deeper linter: follows values through the program to find issues without executing it.

Key takeaways

  • A test is a program that checks your program; its main value is catching regressions in CI before they reach users.
  • Classify tests by what they touch (process, machine, internet); leaving the process is what costs time and invites flakiness.
  • Know the five doubles. Verify state, not interactions, and don't mock what you don't own: wrap it and contract-test the wrapper.
  • Inject dependencies; keep a pure functional core inside a thin imperative shell.
  • Test against a real database cheaply (transactions, templates, Testcontainers). Wait for conditions, not durations; inject clocks.
  • TDD (red, green, refactor) suits problems with known answers. Fix, delete or quarantine flaky tests; don't auto-retry them.
  • Coverage shows what didn't run; mutation testing shows what isn't checked. Complexity metrics and linters are flags, not verdicts.

Check yourself

A test sleeps 200 ms waiting for a background job, and fails about once a week in CI. What's the proper fix?

Stop guessing durations: wait for a completion signal (a channel, callback, or a polling loop with a timeout), or inject a controllable clock. Increasing the sleep just makes it slower and still flaky.

Your repository tests use an in-memory fake and all pass, but production throws "duplicate key value violates unique constraint". What went wrong?

The fake didn't enforce Postgres's unique constraint, so the test couldn't see the bug. Test the data layer against a real Postgres (Testcontainers, transaction-per-test or template databases).

Merging two event publishes into one broke 40 tests, but users see no change. What kind of tests were they?

Change-detector tests using interaction verification (asserting how many times publish was called). Prefer asserting the resulting state.

A function has one if without an else, and the only test takes the true path. Line and branch coverage?

Line coverage 100% (every line ran); branch coverage 50% (the false path was never taken).

Your suite has 95% coverage but a mutation score of 40%. What does that tell you?

The tests execute the code but don't check much of its behaviour: most deliberate bugs went unnoticed. Strengthen assertions to check exact outputs, edge cases and boundaries.
