Authentication and authorization

Two questions. Authentication: who are you, in this context? Authorization: what are you allowed to do here? Every login screen, token and "403 Forbidden" is machinery for answering one of them.

What you'll learn

  • How authentication evolved from handshakes to tokens
  • Sessions, JWTs and cookies, and how they fit together
  • Stateful vs stateless auth, API keys, OAuth 2.0 and OpenID Connect
  • Role-based access control
  • Two security details: generic errors and timing attacks

Who are you vs what can you do

Analogy

At a hotel, the front desk checks your ID: that's authentication. Your key card then opens your room and the gym, but not other guests' rooms or the staff office: that's authorization. Identity first, permissions second.

A short history of proving who you are

Each era's method broke when the world grew, and the fix became the next era. Modern auth carries all of these ideas.

Hashing in one widget

A hash function turns any input into a fixed-length string. The same input always gives the same output, and you can't reverse it. Servers store the hash, then hash the password you type at login and compare.

In real systems

Use a slow, salted password hash such as bcrypt or Argon2, not plain SHA-256. A random salt per user means two people with the same password get different hashes, which defeats precomputed lookup tables.

The three building blocks

1. Sessions: memory for a stateless protocol

HTTP forgets everything between requests (lesson 5). That was fine for static pages, but not for carts or staying logged in. A session is temporary, server-side memory about a user:

  1. On login, the server creates a random session ID and stores it with the user's data (id, role, cart).
  2. It sends only the ID to the browser, in a cookie.
  3. Each later request carries the cookie; the server looks up the ID to know who you are.
  4. Sessions expire (say after 15 minutes) and get recreated.

Where sessions are stored has evolved: files on disk → databases (survive restarts) → in-memory stores like Redis and Memcached (fast, shared by many servers).

2. JWTs: the state travels with the request

By the mid-2000s, apps served millions of users across regions. Storing every session got expensive, and syncing sessions between servers worldwide added latency. JSON Web Tokens (standardised in 2015) offload the state: the token itself carries the user's claims, signed so nobody can tamper with them.

  • Header: metadata, such as the signing algorithm.
  • Payload: claims. sub is the user id, iat is when it was issued, plus optional fields such as name and role. It's only base64-encoded, so anyone can read it. Never put secrets here.
  • Signature: made with a secret key only the server knows. Change one character of the payload and verification fails.

Why JWTs got popular

Stateless: no session storage. Scalable: any server with the secret can verify, which suits microservices. Portable: URL-safe and small, so they fit in headers and cookies.

The catch

Theft: a stolen token works until it expires. Revocation: you can't log out one user, except by rotating the secret, which logs out everyone.

The common patch is a hybrid: verify the JWT, then check a blocklist in Redis. But if you're doing a storage lookup on every request anyway, why not use stateful sessions in the first place? That question has no universal answer.

Practical advice

Build auth yourself to learn the trade-offs. For a medium or large production system, prefer a dedicated auth provider (Auth0, Clerk and similar). Hashing, salting, token rotation and every security edge case are then their headache.

3. Cookies: server-controlled storage in the browser

A cookie is a small value the server stores in the browser via a response header. The browser then automatically attaches it to every later request to that same server, and never sends it to other sites. That makes cookies the perfect carrier for a session ID or a token. Mark them HttpOnly so JavaScript can't read them.

API keys: for machines, not people

Sessions and JWTs assume a human typing a password into a form. But what if your server wants to call OpenAI's API to summarise a paragraph? There's no human and no login screen. You generate an API key in the provider's dashboard (often with scopes and an expiry), store it as a secret, and send it with each request.

OAuth 2.0 and OpenID Connect

Two problems appeared as the web grew: password fatigue (dozens of accounts, reused weak passwords, one breach exposing many accounts) and delegation (a travel app wants to scan your Gmail for tickets; a social app wants your contacts). The first "solution" was handing over your password, which meant full access and no way to revoke it short of changing your password everywhere.

OAuth (2007) replaced shared passwords with tokens that carry specific permissions (scopes), such as "read contacts" but not delete them.

Analogy

OAuth is a valet key. It lets the valet drive and park your car, but not open the boot or the glovebox. You can take it back at any time, and you never handed over your house keys.

OAuth 2.0 (~2010) simplified 1.0's error-prone cryptographic signatures with bearer tokens, and added flows for each kind of app:

  • Authorization code: server-side apps (the standard choice).
  • Implicit: browser apps. Now discouraged for security reasons.
  • Client credentials: machine-to-machine, no user involved.
  • Device code: devices without keyboards, like smart TVs.

OAuth answers "what may this app do?", which is authorization. It never said who you are. OpenID Connect (2014) adds an ID token (a JWT with your id, name, email, issuer and login time) on top of OAuth 2.0. That's what powers "Sign in with Google".

Authorization and RBAC

Say your notes app moves deleted notes to a "dead zone" after 30 days, and you want an admin UI to inspect them. The tempting hack is a secret "god mode" string sent with admin requests. That's a disaster waiting to happen: intercept the string and someone can wipe the database. And to give access to a teammate, you'd have to share or multiply secret strings.

The clean answer is role-based access control (RBAC): users get roles, and roles get permissions.

Two details that matter

Generic error messages

"User not found", "Incorrect password" and "Account locked" are friendly, and they're a gift to attackers. "User not found" tells them to try the next email; "Incorrect password" confirms the account exists, so they can brute-force just the password. In auth flows, always answer with one generic message: "Invalid credentials". Save the friendly messages for validation errors elsewhere.

Timing attacks

A login usually: (1) finds the user, (2) checks whether the account is locked, (3) hashes the password and compares. If the email doesn't exist, it fails at step 1 and responds fast. If the password is wrong, it does the slow hash first. That timing difference leaks which part was wrong.

Fixes: use constant-time comparison functions, and make failures take the same time, for example by hashing a dummy password or adding an equalising delay (setTimeout, time.Sleep).

Key takeaways

  • Authentication = who you are; authorization = what you can do.
  • Never store plain-text passwords. Store slow, salted hashes and compare hashes at login.
  • Sessions keep state on the server (easy to revoke); JWTs carry signed state in the token (easy to scale, hard to revoke). Cookies carry either automatically.
  • Default to stateful sessions for web apps; use JWTs for APIs and mobile, API keys for machines, OAuth/OIDC for delegation and social login.
  • OAuth gives scoped tokens instead of passwords (a valet key); OIDC adds an ID token for identity.
  • RBAC maps users → roles → permissions; failing a check means 403.
  • Keep auth errors generic and response times constant.

Check yourself

A user reports their account was hacked. With pure JWT auth, how do you kick the attacker out right now?

You can't target one token. Your options are rotating the signing secret (logs out everyone) or adding a stateful check, such as a blocklist or a token version in the database. This is the main argument for sessions in web apps.

Why is a JWT payload not a safe place for a user's password or API secrets?

It's only base64url-encoded, not encrypted. Anyone holding the token can decode and read it. The signature prevents tampering, not reading.

What does OpenID Connect add that OAuth 2.0 lacks?

Authentication. OAuth issues access tokens for permissions; OIDC adds an ID token (a JWT) describing who the user is, which enables "Sign in with…".

Which OAuth flow fits a nightly job on your server that syncs data with a partner's API?

Client credentials: machine-to-machine, with no user in the loop.
