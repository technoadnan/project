Task queues and background jobs

A background job is any work that runs outside the request–response cycle: it doesn't need to finish before the user gets an answer. Push it onto a queue, respond immediately, and let separate workers do it, with automatic retries if something fails.

What you'll learn

  • Why sending an email inside a request is risky
  • Producers, brokers, consumers, acknowledgements and visibility timeouts
  • Retries with exponential backoff
  • One-off, recurring, chained and batch tasks
  • Idempotency, monitoring, scaling and best practices

Why not just do it in the request?

A user signs up. You validate, save them, then send a verification email through a provider like Resend, Mailgun or Brevo, which means calling someone else's server. If that provider is slow or down:

  • Without careful error handling, the whole signup fails because of an email.
  • With error handling, signup succeeds but you tell the user "we sent you an email" when you didn't. They click "resend", and it fails again.
Analogy

At the dry cleaner, you don't stand at the counter while they wash your shirt. You hand it over, get a ticket, and leave. The shop works through tickets in the back and calls you when it's done. Your API should hand out tickets, not make users wait at the counter.

How a task queue works

Think of it as a to-do list for your backend: your app adds items, and workers tick them off.

Producer

Your application code. It serializes everything the job needs (user ID, email, code) to JSON and enqueues it.

Broker (the queue)

Holds tasks until a worker is free: RabbitMQ, Redis, or a managed, multi-region service like AWS SQS.

Consumer (worker)

A separate process that watches the queue, dequeues a task, deserializes it into native types and runs the handler you registered for that queue.

// producer, inside the signup handler (BullMQ, Node.js)
await emailQueue.add("send-verification", { userId, email, code }, {
  attempts: 5, backoff: { type: "exponential", delay: 60_000 }
});
return res.status(201).json({ message: "Check your inbox" });

// consumer, a separate worker process
new Worker("email", async (job) => {
  await emailProvider.send({ to: job.data.email, template: "verify", code: job.data.code });
});

Same idea everywhere: Celery (Python), BullMQ (Node.js), Asynq (Go). Different queues for different jobs (email, push notifications, images) can have their own workers.

Acknowledgements and visibility timeout

When a worker finishes, it sends an ack and the broker deletes the task. But what if the worker crashes halfway? While a task is being processed it's hidden from other workers for a visibility timeout. No ack in time? The task becomes visible again, so another worker picks it up and nothing gets lost.

Analogy

It's a library hold shelf. A reserved book waits for you for three days; if you don't collect it, it goes back into circulation for the next person.

Retries with exponential backoff

Failed tasks go back into the queue and are retried with growing gaps (1, 2, 4, 8 minutes…) up to a maximum number of attempts. Big providers rarely stay down for minutes, so the second or third attempt usually succeeds, and the user still gets their email.

What usually runs in the background

Emails

Verification, welcome, password reset: all depend on an external service.

Images & video

Resize and re-encode uploads into the sizes and formats each device needs.

Reports

Daily, weekly or monthly PDFs and stats emails, run on a schedule (cron-style jobs).

Push notifications

Your backend stores each device's token and asks Apple's or Google's push service to deliver. Another external call.

Four kinds of tasks

One-off

Triggered by an event: verification email, "you got a message" notification. The most common kind.

Recurring

Run on a schedule: monthly reports, cleaning up orphaned sessions every few months.

Chained

Parent → child dependencies; some children can run in parallel.

Batch

One trigger fans out into many tasks: account deletion, nightly reports for thousands of users.

A chained workflow: publishing a course video

A batch task: "delete my account"

Deleting everything a user owns (projects, assets, profile, and data spread across shards) could take a minute. Instead, the API enqueues delete-account, responds 200 immediately and logs the user out (often with a grace period). The worker then fans out into smaller deletion tasks and finally emails a confirmation.

Designing for real-world scale

Idempotency

Retries will happen, so a task must be safe to run twice. Wrap multi-step work in a transaction so a failure rolls back cleanly and the retry starts from zero.

Error handling

It all happens in another process, out of sight. Catch, log and let the queue retry.

Monitoring

Track queue length, successes, failures and why they failed, with tools like Prometheus and Grafana (lesson 18).

Scalability

Traffic doubles? Add more workers horizontally.

Ordering

If order matters, make sure your broker and library guarantee it.

Rate limiting

Don't let 10,000 queued tasks hammer an external API that bills or throttles you.

Best practices
  • Small, focused tasks. One job, one responsibility. If step 9 of 10 fails, a big task redoes all 10.
  • Avoid long-running tasks. Split them into chained or parallel pieces.
  • Log generously so failures are debuggable and retryable.
  • Alert on growing queue length and unhealthy workers.

Key takeaways

  • Background jobs run outside the request–response cycle; the user gets a fast response either way.
  • Offload anything slow or dependent on external services: emails, media processing, reports, push notifications.
  • Producer serializes and enqueues; the broker stores; a worker dequeues, runs the task and acks.
  • Visibility timeouts recover tasks from crashed workers; exponential backoff retries failures.
  • Task shapes: one-off, recurring, chained (parent → child) and batch (fan-out).
  • Make tasks idempotent, small and observable, and scale workers horizontally.

Check yourself

A worker charges a card, then crashes before acking. The task is retried. What could go wrong, and how do you prevent it?

The customer gets charged twice. Make the task idempotent, for example by passing an idempotency key to the payment provider or recording "charged" in the same transaction and checking it first.

Why respond 201 before the email is actually sent?

The account was created. The email is non-critical, slow, external work; the queue guarantees it will be attempted (with retries) without making the user wait or fail.

Encode video → (thumbnails, transcription) → resize thumbnails. Which steps can run in parallel?

Thumbnail generation and transcription, since both depend only on encoding. Thumbnail resizing must wait for thumbnail generation.
