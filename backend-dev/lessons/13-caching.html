Caching, the secret behind it all

Caching means keeping a subset of your data somewhere faster to reach, so you spend less time and effort getting it again. It's behind almost every fast system you use, and it shows up wherever a system wants to avoid repeating heavy computation or shipping heavy data over long distances.

One idea, everywhere

Analogy

You keep salt, pepper and oil on the kitchen counter and the 10 kg bag of rice in the pantry. The counter is small but right there; the pantry is big but a trip away. A cache is your counter: a small selection of what you use most, placed where it's quickest to grab.

Google search

Ranking billions of pages is expensive, and "weather today" is searched millions of times. Results live in a distributed in-memory cache. A hit returns instantly; a miss runs the full pipeline once, then caches the result.

Netflix

Each title is encoded in several resolutions and pushed to edge servers near viewers. Which titles go where is decided by regional viewing trends; caching everything everywhere would cost too much.

X trending topics

Analysing millions of posts is heavy, but trends change over hours, not seconds. Compute them every few minutes, store the result in Redis, and serve that to everyone.

The core pattern: cache-aside

Also called lazy caching: only cache something once someone actually asks for it.

The alternative is write-through: whenever you write to the database, update the cache in the same flow. The cache is never stale, but every write does double work.

Three levels you'll meet

Network

CDNs and DNS: cache content and lookups close to users.

Hardware

CPU caches (L1/L2/L3) and RAM.

Software

Redis, Memcached and friends: libraries you call, running on fast hardware.

CDNs: content near the user

A CDN caches files (videos, images, JS, CSS, whole pages) on edge servers grouped into points of presence (PoPs) around the world. DNS routes each user to a nearby PoP, taking location and network conditions into account. Each cached item has a TTL; after it expires, the edge fetches a fresh copy from the origin. Platforms like Vercel serve front-end apps this way.

Analogy

Big retailers don't ship every order from one central warehouse. They stock popular items in local warehouses near customers. The first order of a new item might come from far away; after that it's around the corner.

Hardware: why RAM is fast

The CPU keeps tiny, ultra-fast caches (L1, L2 and a shared L3) and predicts what you'll need next. That's one reason walking an array in order is so fast. Below them sits RAM, then disk:

L1 / L2 / L3fastestKB–MB, on the CPU
RAMvery fastGBs, volatile
SSD / HDDslower, but big and permanentTBs, persistent

Random access memory reaches any address electrically in about the same time, unlike a spinning disk head that must physically move. But RAM is limited and volatile: power off and it's gone. So you can't replace disk with RAM; each has its job.

Redis and Memcached

These are in-memory key–value NoSQL databases (Redis, Memcached, managed options like AWS ElastiCache, and the open-source Valkey). All reads and writes hit RAM, which makes them very fast. Behind the scenes they can persist to disk and reload on restart. The data model is simple: a key, and a value (a string, number, list, JSON…). No schemas, joins or SQL.

Eviction: when the cache is full

RAM runs out, and a cache is only ever meant to hold a subset. An eviction policy decides who leaves to make room:

No eviction

New writes fail with "memory full". Rarely what you want.

LRU

Evict the least recently used key.

LFU

Evict the least frequently used key.

TTL

Evict the key closest to expiring.

Analogy

LRU is your phone closing the app you haven't opened for the longest. LFU is a library keeping its most-borrowed books at the front desk and sending rarely borrowed ones back to storage.

Where backend engineers use Redis

Expensive queries

A heavy join and aggregation behind a busy dashboard? Cache the result with a TTL (say 1 hour) and invalidate it when the underlying data changes. Amazon caches product details during sales; social networks cache profiles. Both are read-heavy, rarely written.

Sessions

Session data is read on every request. Reading it from RAM keeps latency low and takes load off the database (lesson 8).

External APIs

Calling a weather API on every request burns money and rate limits. The weather doesn't change by the second, so cache it for an hour.

Rate limiting

A middleware keeps a counter per client IP (from X-Forwarded-For). Over 50 per minute → 429. Counters live in Redis so every request doesn't hit Postgres.

// rate limiting with Redis: one counter per IP per minute
const key = `rl:${ip}:${currentMinute}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 60);
if (count > 50) return res.status(429).json({ message: "Too many requests" });
Rule of thumb

Cache data that is read often, changes rarely, and is expensive to produce. Always decide up front how it gets invalidated: a TTL, an explicit delete on write, or write-through.

Key takeaways

  • A cache stores a subset of data somewhere faster, to avoid repeated heavy computation or heavy data transfer.
  • Hit = found in the cache; miss = go to the source, then (usually) store it.
  • CDNs cache content at edge PoPs near users; DNS caches lookups in the browser, the OS and resolvers.
  • Redis and Memcached are fast because they live in RAM: limited and volatile, but with near-constant access time.
  • Cache-aside fills on demand; write-through updates the cache on every write.
  • Eviction policies (LRU, LFU, TTL) decide what leaves when memory is full.
  • Typical uses: expensive query results, sessions, external API responses, rate-limit counters.

Check yourself

A user updates their profile but keeps seeing the old one for an hour. What happened, and how do you fix it?

The profile was cache-aside with a 1-hour TTL and nothing invalidated it on write. Delete (or update) the cache key when the profile changes, or use write-through.

Why not keep the whole database in Redis?

RAM is far more expensive and limited than disk, and it's volatile. A cache is meant to hold the hot subset; the database remains the durable source of truth.

A viral post is read a million times an hour but edited once. Good cache candidate?

Excellent: read-heavy, rarely written, and the same for everyone. Cache it with a TTL and invalidate on the rare edit.
