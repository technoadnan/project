Object storage, part 1

Users want to upload a profile picture. The obvious approach (save it to the server's disk, store the path in the database) breaks in six different ways in production. This lesson explains why files need a different kind of storage, how object storage like S3 works inside, and how to upload files the production way with presigned URLs.

What you'll learn

  • Why local disks fail for user files
  • Block vs file vs object storage
  • Objects, buckets, keys and the folder illusion
  • Erasure coding, eleven nines and why durability isn't backup
  • Consistency and conditional writes
  • Streaming uploads, presigned URLs and the two-phase upload flow

The naive approach and how it breaks

The intuitive way: the browser sends the file as form data, the server saves it to its local disk and records the path in the database. It works on your laptop. Then production happens.

The root mistake is assuming files are something your app owns. Files are data with a completely different shape from the JSON your server handles 95% of the time: different sizes, access patterns and costs. They need their own storage.

1

Disks are ephemeral

A container's filesystem lives only as long as the container. Every restart and every deploy starts a fresh container from an image that doesn't contain your users' files.

2

Scaling breaks it

With N servers behind a load balancer, a file exists on one of them. A request for it hits the right server with probability 1/N. Servers must be stateless (lesson 21.2).

3

Disks have a ceiling

You add servers horizontally, but a disk only grows by resizing it, often with downtime, up to a maximum. Meanwhile uploads are your fastest-growing data: 1,000 users × 100 MB is 100 GB a month, forever.

4

One disk, one copy

Disks die. With one copy, the files die with it. Real durability needs replication, checksums and repair processes: a whole engineering field.

5

Downloads tie up workers

A 50 MB file to a phone on a 2 Mbit/s connection takes ~3.5 minutes, with a worker doing nothing but trickling bytes. Your server becomes an expensive, slow CDN.

6

No transaction

Write the file then the row, and a failed insert leaves an orphan file. Write the row then the file, and a failed write leaves a path to nothing. Disk and database can't commit together.

Availability vs durability

A library that's closed for the night has an availability problem: wait until morning and you get your book. A library that burned down has a durability problem: no amount of waiting brings the book back. The only defence is copies kept somewhere else.

Object storage starts from a different question: what is the smallest interface we can get away with, so it can scale to exabytes? You can't modify an object in place (changing one byte of a 1 GB object means uploading 1 GB again), there's no seek, no append, no rename (copy and delete instead), no locks, and no real folders.

Analogy

A coat check. You hand over a coat and get a ticket; later the ticket gets you the coat back. You can't sew a button onto your coat while it's in the cloakroom; you take it out and hand in a new one. Because attendants never coordinate edits, you can add as many attendants and racks as you like.

What you get in return: with nothing to modify, there's nothing to coordinate; with no folder tree, there's no tree to lock or rebalance; every request is self-contained HTTP, so any of thousands of servers can answer it. Capacity is effectively infinite with nothing to provision, S3 promises eleven nines of durability, and browsers, phones and video players can fetch objects directly over HTTP.

A pattern worth noticing

Distributed systems keep making the same trade: give up mutability, gain scale. Caches, stateless servers and immutable deployments all follow it. Object storage is its purest example.

Objects, buckets and the folder illusion

Key

A string that is the object's entire identity, e.g. uploads/2026/cat.png.

Value

The bytes. Any size, any format.

Metadata

System: size, last-modified, content type, ETag (a fingerprint). User: your own key–value pairs, like uploaded-by: 42.

Bucket

A named container for objects. On AWS, bucket names are globally unique.

The folders you click through in the S3 console don't exist. There's one flat list of keys; the slashes are ordinary characters. "Folders" are computed on the fly by grouping keys on a prefix and a delimiter:

That's why "moving a folder" of 40,000 files is slow and costs money (40,000 copies and deletes), and why empty folders can't exist; tools fake them with a zero-byte object whose key ends in /.

What happens when you PUT 100 MB

The request lands on one of thousands of stateless front-end nodes, which verifies its signature. Then the work splits into two very different systems: the data plane (store huge volumes of bytes so they survive; simple operations) and the metadata plane (remember which key maps to which bytes; small data but countless operations, and it must be fast and strongly consistent).

The data plane: erasure coding

The simple way to survive dead drives is three copies on three machines in separate failure domains. But storing 1 PB then means buying 3 PB of drives: 200% overhead. Large providers use erasure coding instead: split the object into, say, 14 data shards, compute 6 extra parity shards with Reed–Solomon math, and scatter all 20 across different drives, racks, power domains and ideally buildings. Any 14 of the 20 rebuild the whole object.

Cheaper and more durable; the price is CPU to compute parity and extra reads during recovery, a good trade since drives cost more than CPU. This math is where S3's eleven nines (99.999999999%) comes from: store 10 million objects and statistically expect to lose one every 10,000 years.

Durability is not backup

Eleven nines protect you from dying drives, not from yourself. Delete the wrong prefix and S3 will durably, reliably delete it. A bug that overwrites objects gets its corrupted versions stored perfectly. For data that matters, turn on versioning (overwrites and deletes create new versions) and replicate to a bucket in a separate cloud account, so one leaked credential can't destroy both.

The metadata plane: a giant sorted index

Conceptually it's a distributed, sorted key–value index (think a distributed B-tree) mapping bucket + key to shard locations, size, ETag and content type, partitioned by key range. Some consequences:

  • LIST is a range scan over that distributed index: slow. Never call it in a request path. Your database is the index of which files exist; the bucket just holds the bytes.
  • No atomic rename: the key decides the partition, so renaming means moving the entry.
  • Size and type are instant: they're read from the index without touching a drive (a cheap HEAD request).

S3 was once eventually consistent: upload an object, read it immediately, and you might get a 404 from an index replica that hadn't caught up. Since December 2020 it's strongly consistent (read-after-write). Old advice to add retry loops or sleeps after uploading is outdated.

Conditional writes

For almost 20 years, two writers to the same key meant one silently won, with no way to tell. Since 2024, S3 supports conditional writes:

  • If-None-Match: * creates the object only if the key doesn't exist yet; otherwise 412 Precondition Failed. No more silent overwrites.
  • If-Match: <ETag> replaces the object only if it's still the version you read: compare-and-swap.

With strong consistency plus "exactly one writer wins", object storage can coordinate: people now build leader election and even database write-ahead logs on S3. Not every "S3-compatible" provider (meaning it speaks the S3 API, like R2 with the AWS SDK) supports conditional writes; check the docs before relying on them.

Uploading through your server

The obvious architecture: the browser posts the file to your API, which forwards it to the bucket. Your server sees every byte, so it can validate, scan and hash the content, and authorization is your normal middleware. For small files (avatars, CSVs, documents of a few MB) it's acceptable.

The hidden problem is buffering. Go's ParseMultipartForm or a default Node body parser reads the whole file into memory: 20 concurrent 100 MB uploads is 2 GB of RAM, and the container is killed for running out of memory. You won't see it locally, with small test files, a fast network and 16 GB of RAM.

// Go: stream the multipart body straight to S3
r.Body = http.MaxBytesReader(w, r.Body, 10<<20) // hard cap first
mr, _ := r.MultipartReader()
part, _ := mr.NextPart()                   // an io.Reader, not []byte
_, err := uploader.Upload(ctx, &s3.PutObjectInput{
    Bucket: aws.String(bucket),
    Key:    aws.String(key),
    Body:   part,                          // chunks flow through
})

Even streamed, the pipe has limits

Now bandwidth is the bottleneck. Load balancers drop connections idle for ~60 s, reverse proxies like Nginx reject big bodies with 413 Request Entity Too Large, and API gateways and serverless functions cap payloads at a few MB, often with no way to raise it.

Presigned URLs: let the browser talk to the bucket

The production answer: the bytes go straight from the browser to the bucket and never touch your server. But the bucket must stay private, and you can't hand the browser your storage credentials. You need to grant permission for exactly one operation, on exactly one key, for the next few minutes.

A presigned URL does exactly that. It's a normal URL whose query string holds the algorithm, your access key ID, a timestamp, an expiry and a signature: an HMAC of the method, bucket, key and expiry, computed with your secret key. The secret never leaves your server, and signing needs no network call.

The size loophole and presigned POST policies

A presigned PUT covers the method, bucket and key, but not the body size. Nothing stops a user from sending a 5 GB file to a URL meant for a profile picture. Instead, sign a presigned POST with a policy: a small JSON document of conditions that the storage service itself enforces.

{
  "expiration": "2026-03-14T10:05:00Z",
  "conditions": [
    ["content-length-range", 1024, 5242880],
    ["starts-with", "$Content-Type", "image/"],
    ["starts-with", "$key", "tenant_9/user_42/"]
  ]
}

Telling your backend about the upload

If the bytes never pass through your server, how does your database learn the file exists? With a two-phase flow: record the intent before any bytes move, then confirm.

Some uploads will be abandoned: closed tabs, dropped mobile connections, a completion call that never arrives. A bucket lifecycle rule (or a background job, lesson 14) deletes objects from uploads that never completed after ~24 hours, and a job marks stale pending rows expired. The database is the source of truth for which files exist and the bucket for their bytes; this cleanup keeps the two from drifting apart. That's the answer to problem 6: not a transaction, but a state machine plus reconciliation.

CORS

A browser uploading to my-bucket.s3.amazonaws.com makes a cross-origin request (lesson 5). The bucket needs a CORS configuration allowing your front end's origin, the PUT/POST methods, and exposing the ETag header (needed for multipart uploads in part 2). If uploads work in curl or Postman but fail in the browser, check CORS first.

Key takeaways

  • Never keep user files on your servers' disks: they're ephemeral, unshared, capped, single-copy, slow to serve and can't commit with your database.
  • Object storage offers a tiny interface (PUT, GET, DELETE, LIST by key) and immutable objects, in exchange for unlimited scale and extreme durability.
  • Folders are an illusion: prefixes plus a delimiter. Generate keys yourself, put randomness early, encode ownership.
  • Erasure coding gives more durability than 3 copies at half the storage. Durability isn't backup: use versioning and cross-account replication.
  • Your database is the index; never LIST in the request path. S3 is strongly consistent and supports conditional writes (If-None-Match, If-Match).
  • If you must proxy uploads, stream them with a size cap. Better: presigned URLs, ideally presigned POST policies that enforce size, type and key prefix.
  • Use a two-phase upload (pending → HEAD check → ready) plus lifecycle cleanup to keep the database and bucket in sync.

Check yourself

After a deploy, all profile pictures return 404. What happened?

They were saved to the container's local filesystem, which is ephemeral: the deploy replaced the container with a fresh one from the image, which never contained user files.

Two users upload invoice.pdf and one of them later sees the other's invoice. Why, and what's the fix?

The user's filename was used as the key, and PUT silently overwrote the first object. Generate unique keys (e.g. tenant/user/uuid) and store the original name separately. Conditional writes (If-None-Match: *) would also have refused the overwrite.

Your "files" page calls ListObjects for the user's prefix on every request and is getting slow. What should it do instead?

Query your database, which should record every file (key, owner, size, status). LIST is a range scan over a distributed index and doesn't belong in the request path.

A presigned PUT URL for avatars was used to upload a 4 GB file. How do you prevent that?

Use a presigned POST with a policy containing content-length-range (plus content-type and key-prefix conditions). The storage service rejects anything outside the limits before storing it.

S3 has eleven nines of durability. Do you still need backups?

Yes. Durability protects against hardware failure, not against deletes, overwrites or compromised credentials. Enable versioning and replicate to a bucket in another account.
