DevOps for backend engineers

Everything in this course ran on localhost. DevOps is the journey from a commit on your laptop to a service on the internet that stays up while you ship changes every day. This final lesson builds a mental model of the whole path: pipelines, containers from first principles, orchestration, deployment strategies, infrastructure as code, and running production.

What you'll learn

  • Why small, frequent deploys are both faster and safer (DORA)
  • CI, trunk-based development, builds and pipelines
  • What a container really is: namespaces, cgroups, layers, registries
  • Running services: systemd, TLS, Kamal, Kubernetes
  • Rolling, blue-green and canary deploys; GitOps
  • Infrastructure as code, SLOs, incidents, chaos and supply-chain security

Dev, Ops, and the wall between them

In many companies two teams faced each other. Developers were measured by how fast they shipped features; operations by how rarely production broke. Every deploy adds risk, so ops wanted fewer of them, and when something broke each side blamed the other ("it's your code" / "it's your machines"). Releases slowed to once every week or two, with everyone on deck.

The DevOps movement is a collection of practices that grew out of fixing this: infrastructure defined in code, everything (including infrastructure config) in version control, one command to build and one to deploy, feature flags to switch features on and off without deploying, and observability shared with developers. The common thread: make deployment small, cheap and boring, a merge or a button that takes seconds, so nobody hesitates to do it several times a day.

Measure it: the DORA metrics

Change lead time

Commit merged at 9:00, live at 11:00: two hours.

Deployment frequency

How often you deploy to production.

Change failure rate

4 of 100 deploys caused failures: 4%.

Failed deployment recovery

How long it takes to recover when one does fail.

DORA surveyed tens of thousands of teams. In 2024 the top group (about 20% of teams) deployed on demand, got commits to production in under a day, saw about 5% of deploys fail and recovered in under an hour. The bottom group deployed every one to six months, saw about 40% fail and took a week to recover. The teams that deployed most were also the most stable. Speed and stability are not a trade-off.

Continuous integration and trunk-based development

Continuous integration is a practice: every developer merges into one shared branch at least daily, and every merge is verified by an automated build and test run. The CI server only enforces the checks; it can't make people merge. Two branches that lived apart for three weeks take hours to reconcile; a day's drift takes minutes, and everyone still remembers their changes.

Git-flow

Develop, release, hotfix and main branches. Built for software shipped as versions that customers install (desktop and mobile apps), where version 2 needs support while version 3 is being built. Its own author later recommended something simpler for continuously shipped web apps.

Trunk-based development

One main branch, short-lived feature branches (a day or two), deleted after merging, and releases from main. A backend has exactly one version in production. A feature that takes three weeks ships in small merges behind a feature flag.

Builds, pipelines and credentials

A build turns source into a runnable artifact. It must be reproducible: same source and config in, byte-identical artifact out, no matter what the build machine has installed. That means a pinned toolchain plus a committed lockfile (lesson 27): go build with a pinned Go version and go.sum, or npm ci with package-lock.json. Stamp the commit hash into the artifact.

A deployment pipeline chains stages from cheap to expensive: compile and unit tests in minutes (fail fast, notify the author), then integration tests with real databases and a staging deploy, then production.

# .github/workflows/deploy.yml
on: { push: { branches: [main] } }      # event
permissions: { id-token: write, contents: read }
jobs:
  test:                                # job on a fresh runner
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4      # always first: the VM is empty
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go test ./...
  build:
    needs: test                        # waits for test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: go build -ldflags "-X main.commit=${{ github.sha }}" -o server .

GitHub Actions vocabulary

Workflow: a YAML file in .github/workflows. Event: what triggers it (push, pull request, schedule, manual click). Job: steps on one machine; jobs run in parallel or wait for each other with needs. Runner: a fresh VM per job (or self-hosted). Step: one command or action.

Versions

Libraries use semantic versioning (major.minor.patch) because their users depend on compatibility. A service's users are HTTP clients who don't care about deploy versions, so version deploys by commit hash (plus a build ID): stamp it on the artifact and the image tag, and expose it from a /version or health endpoint to check what's actually running.

Containers from first principles

A Go binary that runs on your laptop fails on the server: an older system library, a different certificate store, no time-zone database. A Node app written against Node 22 meets Node 18 in production. The fix: ship the environment too, meaning the runtime, libraries and files your process needs, packaged so it behaves identically on a laptop, a data-center server or a rented VPS.

Hardware

A VM virtualizes hardware and runs its own kernel: strong isolation, but gigabytes of RAM, slow boots and its own disk. A container is not a small VM. It's an ordinary process started by the host's kernel (it shows up in the host's ps) that the kernel treats specially: it gets its own process IDs, hostname, filesystem root and network interfaces, plus limits on CPU and memory. Three kernel features make that illusion.

1. Namespaces: what a process can see

A namespace wraps a global resource so a group of processes sees its own copy. Linux has eight: PID (the process sees itself as PID 1), UTS (hostname), mount, network (two containers can both listen on port 80), IPC, user, cgroup and time. Three system calls manage them: clone (start a process in new namespaces), unshare (move the caller into new ones) and setns (join existing ones). Docker and Kubernetes ultimately use exactly these. Liz Rice's talk Containers From Scratch builds one in about 76 lines of Go:

cmd := exec.Command("/proc/self/exe", append([]string{"child"}, os.Args[2:]...)...)
cmd.SysProcAttr = &syscall.SysProcAttr{
    Cloneflags: syscall.CLONE_NEWUTS | syscall.CLONE_NEWPID | syscall.CLONE_NEWNS,
}
// in the child:
syscall.Sethostname([]byte("container"))
syscall.Chroot("/home/rootfs/ubuntu")   // an unpacked Ubuntu filesystem
syscall.Chdir("/")
syscall.Mount("proc", "proc", "proc", 0, "") // so ps reads the new PID namespace
// …then exec the requested command, e.g. /bin/bash

2. Control groups: how much it can use

Namespaces limit what a process sees, not what it uses: it could still eat all the host's memory. cgroups are plain folders under /sys/fs/cgroup. Write a number into memory.max, cpu.max or pids.max, and every process listed in that folder's cgroup.procs shares the limit. When Kubernetes gives a container a 512 MiB limit, the kubelet writes that number into memory.max; exceed it and the kernel's OOM killer ends the process: the familiar OOMKilled status.

3. Layers: where the filesystem comes from

That chroot target held about 100 MB of Ubuntu. Containers don't copy it each time. An image is a stack of layers, each a tarball of changes (files added, modified, deleted), combined at runtime by OverlayFS:

An image is a set of blobs (the layer tarballs, each named by its SHA-256 hash), a config (layer order plus the command, environment, working directory and ports) and a manifest pointing at them; the image's identity is the manifest's hash. Tags like ubuntu:24.04 point at those digests. Think of an image as a git commit for a filesystem: shared layers are stored once, and changing one Dockerfile line changes only the layers after it.

Dockerfiles and the build cache

Each instruction that changes the filesystem produces a layer, and the builder reuses cached layers top-down until the first instruction whose inputs changed; everything after is rebuilt. Order matters:

For compiled languages, add a multi-stage build: one stage with the compiler builds the binary; the final stage starts from a tiny base image and copies in only the binary, leaving compilers and build dependencies behind.

Registries and the runtime stack

Builds and runs often happen on different machines, so artifacts travel through a registry (Docker Hub, GitHub's, AWS, GCP, Azure, or self-hosted): an HTTP server of blobs addressed by digest and manifests addressed by tag or digest. A push uploads only the blobs the registry lacks; a pull fetches the manifest, then only the missing layers, which is why pulling a new version after a small code change takes seconds.

A good image is…

Small (less to patch and pull) · one process (no init system or cron inside) · non-root · pinned (golang:1.23.4, not latest) · scanned against published vulnerabilities.

No Dockerfile?

Buildpacks and Nixpacks, used by platforms like Render and Railway, detect your language from package.json, go.mod, requirements.txt or Cargo.toml and build an optimized image for you.

Running it: one machine, then many

Running a service on a Linux machine means three things: a process started at boot and restarted when it dies (systemd), a reverse proxy on ports 80/443 terminating TLS and forwarding to your port (Nginx or Caddy), and logs you can read (stdout into the journal, read with journalctl -u tasker).

# /etc/systemd/system/tasker.service
[Unit]
Description=Tasker API
After=network-online.target

[Service]
ExecStart=/usr/bin/docker run --rm --name tasker \
  -p 127.0.0.1:8080:8080 --env-file /etc/tasker.env \
  ghcr.io/acme/tasker@sha256:3f9a…
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
# Caddyfile: HTTPS certificates are automatic
api.tasker.app {
    reverse_proxy 127.0.0.1:8080
}

More traffic means more machines (lesson 21.2), and deploying to each by hand gets slow and risky. Kamal automates it over SSH: install Docker if needed, build and push the image, pull it on every host, start the new container alongside the old one, wait for /health to answer, switch the proxy to the new container, then stop the old one.

Cattle, not pets

A pet server has a name, gets nursed back to health, and only one or two people know how. That's the snowflake from lesson 27. Cattle are numbered and replaced without ceremony. Immutable infrastructure means never modifying a running server: change the code, build a new image, replace the instances. Containers made replacement cheap, and everything from here on assumes it.

Orchestration: Kubernetes

With 40 containers on 10 machines, new questions appear. Which container runs where? Who restarts containers when a machine dies? Who adds copies when traffic doubles? Who swaps 40 old containers for 40 new ones in the right order? That's an orchestrator's job, and the best-known is Kubernetes, the open-source descendant of the system Google ran internally for years.

Kubernetes is declarative: you don't say what to do, you state what you want ("three copies of this image on this port with this much memory") and controllers keep comparing what you asked for with what exists and close the gap.

ObjectWhat it is
PodOne or more containers scheduled together, sharing a network namespace and volumes; usually just yours, sometimes with a helper (a log shipper, a proxy). Gets its own IP; mortal. Grouped by labels such as app=api.
ReplicaSetKeeps N pods from a template running.
DeploymentOwns ReplicaSets: a new template means a new ReplicaSet and a gradual shift of counts. This is what you write.
ServiceA stable virtual IP and DNS name in front of whichever pods match its selector.
Ingress / Gateway APIMaps hostnames and paths from the internet to services, programming a real load balancer.
ConfigMap / SecretConfiguration as env vars or files; Secrets only go to pods that ask for them.

Behind the scenes: the API server (the only component that talks to the etcd store), the scheduler (picks a machine for each new pod), the controller manager (built-in reconcile loops), and on every machine a kubelet (runs what the API server says should run there) and kube-proxy (service networking). Each container declares resource requests (reserved for it) and limits (hard caps, written into those cgroup files).

Rolling updates and probes

Readiness probe

Can this pod serve traffic right now? Failing removes it from the Service's endpoints, with no restart.

Liveness probe

Is the process stuck? Failing repeatedly makes the kubelet restart the container.

Startup probe

Holds the other two off until a slow-starting process has finished booting.

Never check the database in liveness

The database gets slow, liveness checks time out, and the kubelet restarts perfectly healthy pods in waves; the reconnect storm makes the database slower still. Liveness asks "is the process stuck?"; readiness asks "can I serve right now?"

Scaling becomes changing a number: set replicas: 10 and the controller adds seven pods. A HorizontalPodAutoscaler changes it for you based on average CPU, within a minimum and maximum. Do you need Kubernetes? Usually not at first. Start small (one machine with systemd or Docker Compose, a hosting platform, or a few machines with Kamal) and adopt Kubernetes when you've earned it.

Shipping safely

Continuous delivery means every merged change passes the full pipeline, so main is always deployable at the press of a button: a technical property. Continuous deployment removes the button: every change that passes ships automatically. That's a business decision; a team with continuous delivery may still release weekly for changelogs or compliance. You can't have continuous deployment without continuous delivery.

Progressive delivery automates the canary: a controller widens traffic on a schedule, compares error rates and latency at each step as a human would, and rolls back on its own if the numbers go bad.

GitOps

Instead of a pipeline pushing into the cluster, GitOps declares the cluster's entire desired state (Deployments, Services, ConfigMaps) in files in Git, where every change is versioned, reviewed and reversible. An agent in the cluster (Argo CD or Flux) pulls those files, applies them, and reverts any manual change that drifts from them. A deploy becomes a pull request that bumps an image digest, and the pipeline never holds cluster credentials, because it only pushes images and opens PRs.

Environments (development, staging, production) run the same image with different config (lesson 27). Two terms you'll hear: preview environments, created per pull request for live review and destroyed on merge, and promotion, moving the same artifact from one environment to the next, often through a human approval gate.

Infrastructure as code

The test: with a brand-new cloud account and one hour, could you rebuild your infrastructure identically, with every machine, network, load balancer, DNS record and security group? If it was clicked together in a console, probably not, especially if the person who did it has left. Infrastructure as code puts it all in version-controlled files that a tool applies, producing the same result every time.

Creates machines, networks and cloud services: Terraform, or its open-source fork OpenTofu after Terraform's licence change. Write blocks, review the plan, apply.

Configuration management

Installs and configures software on existing machines from scripts: Ansible.

Builds machine images with everything preinstalled: Packer, with cloud-init for first-boot scripts.

Terraform's state file maps each block to a real resource ID. Each run compares code, state and the cloud's reality to compute the plan. Lose the state and Terraform thinks nothing exists and plans to create everything again; two people with separate copies overwrite each other. So keep state in a remote, locked, encrypted backend, never in Git, because it contains every attribute, secrets included. Manual console changes cause drift: the next apply removes them, because the code is the source of truth.

Operations: promises, budgets and incidents

Users don't care how automated your pipeline is; they care whether the service works. An SLI (service level indicator) measures that: the share of requests that succeed, or that finish within 300 ms. An SLO (objective) is a target over a window: 99.9% of requests succeed over 30 days. An SLA (agreement) is a contract that puts money behind it, such as refunds or credits if you miss.

The allowed failure is your error budget. While budget remains, ship as fast as you like, and spend it on deploys, maintenance, experiments and risky migrations. Blow it on the 23rd of the month and deploys freeze until it recovers, with all effort going to reliability.

On-call

One engineer per week (plus a backup) is paged when an alert fires (lesson 18). "Paging" outlives the pagers; today it's an incident-management app on your phone.

Incident response

An incident commander coordinates without fixing; engineers fix; a communicator updates the status page and management. A running document records the timeline. Mitigate first: roll back, flip the feature flag off. Find the root cause afterwards.

Blameless postmortems

Timeline, impact, root cause and actions. Cloudflare's November 2025 outage write-up: a database permission change made a query return duplicate rows, a config file doubled in size and hit a size limit in the software reading it. No one is named. Blame people and you never learn why the wrong command looked right.

Recurring principles in postmortems: design for failure (every machine and dependency will eventually fail), keep deploys simple (files and pipelines, not hand-run steps) and make one change at a time. Chaos engineering goes further and causes failures on purpose: kill a pod during business hours and watch the ReplicaSet replace it, drain a machine, inject latency into a dependency. Better to discover a broken safety net in an experiment than in an outage.

The software supply chain

Most of what's in your image isn't your code: the base image, the runtime, hundreds of packages from npm install or go mod download. Dependencies can vanish or change and break thousands of builds, or be poisoned. In 2024, the xz compression library used across Linux shipped a backdoor hidden in its release tarball rather than in the source repository, so code reviewers never saw it. Defences: pin every dependency and base image to exact versions (and lockfiles), and scan continuously against published vulnerability databases.

Key takeaways

  • DevOps makes deploying small, cheap and boring. DORA shows the fastest teams are also the most stable: deploy small changes often.
  • Merge to a shared trunk daily, hide unfinished work behind flags, build reproducibly, and run cheap pipeline stages first. Prefer OIDC to stored cloud keys; version services by commit hash.
  • A container is a process with namespaces (what it sees), cgroups (what it uses) and layered filesystems; images are content-addressed layers shipped through registries.
  • Order Dockerfiles for caching, use multi-stage builds, and keep images small, single-process, non-root, pinned and scanned.
  • Run services with a supervisor, a TLS-terminating proxy (ACME certificates) and logs; treat servers as cattle. Kubernetes reconciles desired state with pods, Deployments, Services, probes and rolling updates; adopt it when you need it.
  • Choose a strategy (rolling, blue-green, canary) deliberately; GitOps keeps the cluster equal to Git; Terraform keeps infrastructure equal to code, with remote, locked state.
  • Define SLIs and SLOs, spend the error budget wisely, mitigate before diagnosing, write blameless postmortems, test your safety nets with chaos, and pin and scan your supply chain.

Check yourself

Your team deploys monthly "to be safe" and each release is painful. What does DORA's research suggest?

Deploy smaller changes more often. Large batches make failures more likely and much harder to diagnose (which of 200 commits?), while small, frequent deploys are easier to verify, attribute and roll back. Speed and stability improve together.

Is a container a lightweight VM?

No. A VM runs its own kernel on virtualized hardware. A container is an ordinary host process that the host kernel isolates with namespaces (what it sees) and limits with cgroups (what it uses), on a layered filesystem.

Every code change makes your Docker build reinstall all dependencies. Why?

The Dockerfile copies the whole source tree before installing dependencies, so any change invalidates that layer and everything after it. Copy only the dependency manifest and lockfile, install, then copy the source.

During a slow-database incident, all your pods restart in waves. What's misconfigured?

The liveness probe depends on the database. Liveness should only detect a stuck process; put dependency checks (if anywhere) in readiness, which removes a pod from traffic without restarting it.

You need zero downtime and can't have two versions serving at once. Which strategy?

Blue-green: deploy the new version to an idle environment, test it, then switch all traffic at once, keeping the old environment for instant rollback, at the cost of running double infrastructure meanwhile.

What does a 99.9% monthly availability SLO allow?

About 43 minutes of failure per 30 days. That's your error budget.
