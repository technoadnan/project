Backend security: everything you need to know

No application is ever "fully secure". The goal is a mindset: a healthy paranoia that makes you ask, every time you write code, "what could go wrong here?" Attackers don't care about your framework. They hunt for one thing: the place where you made an assumption.

What you'll learn

  • How to think like an attacker
  • Injection (SQL, NoSQL, command): why data turns into code
  • Password storage from plain text to Argon2id, plus sessions, cookies, JWTs and rate limiting

Think like an attacker

Security spans browsers, networks, server operating systems and your backend code. This lesson stays with the backend. Nearly every vulnerability below comes from a developer assuming something under deadline pressure, while thinking about the happy path:

"Input will be clean."

It won't. Every field is an attack surface.

"The user is who they say."

Unless you verify it on every request, they aren't.

"Requests come from our frontend."

Anyone can call your API with curl or a script.

"Nobody opens DevTools."

Attackers live in the network tab, editing parameters.

Analogy

A house is only as secure as its least-considered entrance. Lock the front door (frontend validation) but leave the kitchen window open (an unchecked API parameter), and the burglar uses the window.

Injection: when data becomes code

Your backend speaks several languages: SQL to the database, HTML/JS to browsers, shell to the operating system. Each has special characters that separate commands from data. Trouble starts when user input crosses into one of these languages and its special characters get interpreted.

Analogy

Imagine a mail-merge letter: "Dear {name}, your order shipped." Someone sets their name to "Bob. P.S. Please refund every customer". The template can't tell where the name ends and your instructions begin. A parameterized query is a form with a boxed field: whatever is written in the box is only ever the name.

SQL injection, character by character

  • Swap the payload for '; DROP TABLE users; -- and a second, destructive statement rides along. Attackers also use UNION to read other tables, database functions to read files, and sometimes even run OS commands.
  • Fix 1: parameterized queries (lesson 12). The input goes in a slot and is treated purely as data. Every modern driver and ORM supports them; you're only vulnerable if you deliberately build SQL strings yourself.
  • Fix 2: least privilege. The app's database user should only run data operations (SELECT, INSERT, UPDATE, DELETE), never DDL like DROP or ALTER. Many drivers also refuse stacked statements by default.

NoSQL injection

MongoDB queries are objects, and objects can contain operators. Pass a request body straight into a query and the attacker controls the structure, not just the value:

// POST /login  body: { "email": { "$ne": null }, "password": { "$ne": null } }
db.users.findOne({ email: req.body.email, password: req.body.password }); // ✕ matches the first user

Command injection

Resizing an upload with ffmpeg and letting the user choose the output filename? A name like out.jpg; rm -rf / ends your command and starts theirs (pipes and & open more doors). Pass arguments as an array so they never go through a shell:

// ✕ shell string: the shell interprets ; | & $( )
exec(`ffmpeg -i in.png -vf scale=120:220 ${outputName}`);
// ✓ argument array: outputName is passed to the process as plain data
execFile("ffmpeg", ["-i", "in.png", "-vf", "scale=120:220", outputName]);
The rule for every injection

Whenever you build a string that another system will interpret (SQL, a shell, HTML, LDAP, XML…) and it contains user input, stop. Use the API that separates structure from data: query parameters, argument arrays, templating that escapes. Never string concatenation.

Authentication

Advice first: in production, strongly consider an auth provider (Clerk, Auth0…). Real-world auth isn't just "sign a JWT". It's stateful sessions with device lists and instant revocation, social login with OAuth redirects on both frontend and backend, linking a Google sign-in to an existing email/password account, and more. Providers have security teams on it 24/7. Revisit building your own when the bill reaches five figures and you have the revenue and people. But you still need to understand how it works to integrate it safely.

A slow hash is a 400 ms speed bump at your front door. Residents barely notice it once a day. A burglar trying a billion keys is stuck there for a decade.

Sessions and cookie flags

After login, the server issues a random session ID (at least 128 bits from a CSPRNG, so it can't be guessed), stores it in Redis or the database with the user, expiry, IP and user agent (handy for a "your devices" page), and sends it in a cookie.

HttpOnlyJavaScript can't read the cookieXSS stealing sessions (and why tokens don't belong in localStorage)
SecureSent over HTTPS onlySniffing on public Wi-Fi or by a malicious router
SameSite=StrictOnly sent on requests from your own siteCSRF
SameSite=LaxAlso sent on top-level link navigation, not images, iframes or cross-site formsMost CSRF (browser default)
SameSite=NoneSent everywhere; requires SecureNothing. Avoid for session cookies.

JWTs: the security trade-offs

  • Revocation is hard. A user reports a hacked account and you can't log out their devices. Workarounds: a blocklist in Redis, or short-lived access tokens with refresh tokens.
  • The payload is only base64. Tampering breaks the signature, but anyone can read it. No secrets inside.
  • Storage: localStorage is readable by any XSS. An HttpOnly cookie is safer, and then you're most of the way back to sessions.
Recommendation

Prefer stateful sessions; they scale fine across servers with Redis. If you use JWTs: expiry in minutes to hours (not days), a refresh flow with server-side storage, and HttpOnly cookies.

Rate limiting, in layers

Without it, attackers try millions of passwords, or simply flood and crash your server. Be strict on auth endpoints and more generous elsewhere. One layer is never enough:

Authorization: the most common hole

A typical setup: a requireAuth middleware and a permission check (read:invoices) at the routing layer. Then a false sense of security sets in: authenticated, has the permission, so anything goes. But having permission to read invoices doesn't mean permission to read everyone's invoices.

Analogy

A hotel key card that opens the lift (authentication) and the "guest floors" (permission), but where no door checks the room number. Every room is now your room.

SELECT * FROM invoices WHERE id = $1 AND user_id = $2;  -- $2 = ctx.userId, from verified auth
-- no rows → 404. Do the same for UPDATE, DELETE and INSERT.

BOLA / IDOR

Broken object-level authorization (insecure direct object reference). Ownership isn't checked where the data is accessed. Fix: scope every query to the user.

Don't confirm existence

A 403 for someone else's invoice tells attackers it exists, which is fuel for enumeration and social engineering. Return 404 for both "missing" and "not yours".

BFLA

Broken function-level authorization: /admin/invoices "protected" only by nobody knowing the URL. That's security through obscurity. Add a role check (admin) on top of permissions.

Guessable IDs

Sequential IDs (101, 102, 103…) invite enumeration. UUIDs make guessing impractical (with some performance trade-offs to read up on).

↔ Horizontal attack

User A reaches user B's data. Same privilege level, wider scope. (BOLA/IDOR.)

↕ Vertical attack

A member reaches admin functions. Higher privilege. (BFLA.)

Prevent it systematically
  • Centralise authorization logic instead of scattering ad-hoc checks.
  • Default deny: anything not explicitly allowed is refused, so new endpoints start out protected.
  • Automated authorization tests in CI: A can't read B's data, members can't call admin endpoints, anonymous users get nothing.
  • Audit logs: record sensitive access, and flag failed authorization checks as possible probing.

Cross-site scripting (XSS)

XSS means an attacker's JavaScript runs in other users' browsers, inside your site. From there it can read the page, call your API as the victim, steal non-HttpOnly cookies and localStorage, redirect to phishing pages, or rewrite what the user sees.

  • Stored XSS: the payload is saved (a comment) and served to everyone. Reflected XSS: it comes from the URL. DOM-based XSS: client code writes untrusted data into innerHTML. React names its escape hatch dangerouslySetInnerHTML for a reason.
  • Same root cause as SQL injection: user content treated as code, this time in the browser's HTML/JS context.
  • Prevent it by sanitizing user-supplied markup on the server before storing it (and escaping on output).
  • Limit the damage with a Content-Security-Policy header. It's a last line of defence, not a fix:
Content-Security-Policy: default-src 'self'; script-src 'self'; img-src 'self' https://cdn.example.com
# no inline scripts, scripts only from our origin, images only from known hosts

CSRF, briefly

Browsers attach cookies to requests for a site, even when another site triggers the request. You're logged in to bank.com; evil.com auto-submits a hidden form to bank.com/transfer, and your cookie rides along. With modern stacks this is largely handled: browsers default cookies to SameSite=Lax, and a strict CORS policy adds another layer. Keep session cookies Strict or Lax, never None.

Misconfiguration

Secrets in Git

Anyone with repo access gets your database and API keys. Deleting the file isn't enough, because it's still in the history. Rotate the secret immediately. Keep secrets in env vars or a secret manager (lesson 17).

Debug logging in production

Stack traces, raw SQL, config and user data in logs give an attacker a blueprint if the logs leak. Production runs at info.

Missing security headers

X-Frame-Options stops your site being framed for clickjacking; add HSTS, nosniff and CSP too. Most frameworks provide a one-line security middleware (e.g. helmet).

Boundaries and defence in depth

Every attack in this lesson is data crossing a boundary: user input into SQL, markdown into HTML, one user's request into another user's data. Every time data crosses one, ask:

  1. Where is data crossing a boundary here?
  2. What am I assuming about it?
  3. What happens if that assumption is wrong?

And because no single defence is perfect, stack them:

1 · Input validation→2 · Parameterized operations→3 · Authorization at the point of access→4 · Headers & policies (CORS, CSP)→5 · Monitoring & alerts
Analogy

A castle doesn't rely on one wall. Moat, outer wall, gate, guards and a keep: an attacker has to beat all of them, and each one buys you time to notice.

Key takeaways

  • Attackers exploit assumptions. Never trust input, identity or the request's origin.
  • Injection happens when data is interpreted as code. Use parameters and argument arrays, never string concatenation.
  • Store passwords with a slow, salted hash (Argon2id). Issue random session IDs in HttpOnly, Secure, SameSite cookies.
  • Prefer stateful sessions. If you use JWTs, keep them short-lived with refresh tokens.
  • Rate-limit in layers: per IP, per account and global, plus alerts.
  • Check authorization where data is accessed. Scope queries to the user, return 404 instead of 403, and add role checks for admin functions.
  • Sanitize user markup, add CSP, keep secrets out of Git and debug logs out of production.
  • Defend in layers, and keep asking where data crosses a boundary.

Check yourself

Your API returns 403 when Alice requests Bob's invoice. What's the subtle problem?

It confirms the invoice exists. An attacker can enumerate IDs to map your data. Scope the query to the user and return 404 for both "missing" and "not yours".

Why is SHA-256 a poor choice for password hashing even with a salt?

It's designed to be fast. GPUs compute billions per second, so leaked salted hashes can still be brute-forced. Use a slow, tunable hash like Argon2id or bcrypt.

An attacker tries the password "Summer2024!" once on 50,000 accounts from rotating IPs. Which rate limit catches it?

A global limit on failed logins (with alerting and captcha). Per-IP limits miss rotating IPs, and per-account lockouts miss a single attempt per account.

You accidentally pushed a Stripe key to GitHub and force-pushed a fix a minute later. Are you safe?

No. Treat it as leaked: it may have been scraped instantly, and forks or caches can keep it. Revoke and rotate the key now, then move secrets to env vars or a secret manager.
