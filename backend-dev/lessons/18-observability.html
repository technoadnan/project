Logging, monitoring and observability

Your backend runs on many servers in many regions for users everywhere. When something breaks, you need to know that it broke, where, and why. Logging, monitoring and observability are the practices that answer those questions. There's no finish line: every team implements them somewhere on a spectrum.

What you'll learn

  • The difference between logging, monitoring and observability
  • The three pillars: logs, metrics and traces, and how they link up
  • Log levels, and structured vs unstructured logs
  • Instrumentation, OpenTelemetry and the usual tool stacks
  • How a real debugging session flows from alert to root cause

Three practices

Logging

Recording important events (logins, queries, failures, security events) with metadata: user ID, request ID, latency, function. Your app's diary.

Monitoring

Continuously tracking system state (CPU, memory, requests per second, open DB connections) in near real time, usually 10–15 s behind, plus trends over time.

Observability

Being able to work out a system's internal state from its external outputs. Requires all three pillars: logs, metrics and traces.

Analogy

Monitoring alone is a car's check-engine light: it tells you something is wrong and nothing more. Observability is the mechanic plugging in a diagnostic computer that says which sensor failed and when. A decade ago most teams only had the light.

The three pillars

Logs → what happened

Discrete events with context. Like a diary.

Metrics → patterns & trends

Numbers over time: requests processed, failure rate, todos created, average latency. Like a car dashboard's gauges.

Traces → how components interacted

One request's journey (middleware → validation → service → repository → database) as a single transaction. Like a parcel's tracking history.

Structured vs unstructured

In development, readable coloured console lines make problems easy to spot. In production, logs go to tools (the ELK stack, Grafana Loki…) that must parse them, so write JSON, where every field (user ID, request ID, status) is machine-readable.

Remember

Log enough context to debug (request ID, user ID, operation), but never secrets: no passwords, tokens, card numbers or raw personal data (lesson 16).

Instrumentation in code

Instrumentation means adding code that measures and records what your functions do. The video's Go to-do app does it in layers:

  1. A logger is created at startup: level debug locally and info in production; console format locally and JSON in production, chosen from config.
  2. A monitoring middleware wraps every request to record timing, status and errors.
  3. A tracing middleware starts a transaction with the service name, environment, IP, user agent, request ID, user ID and tenant, and puts it in the request context (lesson 10).
  4. Each service pulls the transaction from the context, adds attributes (user ID, todo title, priority), logs key steps, records errors on the trace, and ends its segment when it returns.
// inside the "create todo" service (illustrative)
txn := tracing.FromContext(ctx)
defer txn.StartSegment("todo.create").End()
txn.AddAttribute("user_id", userID)

log.Info().Str("op", "todo.create").Str("title", in.Title).Msg("creating todo")
todo, err := s.repo.Create(ctx, in)
if err != nil {
    log.Error().Err(err).Str("op", "todo.create").Msg("insert failed")
    txn.NoticeError(err)                    // links the error to this trace
    return nil, err
}
log.Info().Str("todo_id", todo.ID).Msg("todo created")   // business event

OpenTelemetry is the open standard for this: SDKs, APIs and collectors for every major language, so your instrumentation isn't locked to one vendor.

Tools

Open-source stack

Prometheus (metrics), Loki + Promtail (logs), Jaeger (traces) and Grafana (dashboards and alerts). Powerful, but you run and maintain it.

All-in-one platforms

New Relic, Datadog and similar: logs, metrics, traces and alerting in one place. Simpler if your team is small.

It's a team effort: developers instrument the code; DevOps sets up collection, storage, dashboards and alerts.

Key takeaways

  • Logging records events, monitoring tracks state and trends, and observability lets you explain why.
  • The three pillars: logs (what happened), metrics (patterns), traces (how components interacted).
  • Real debugging flows alert → metric → logs → trace → the failing span.
  • Use levels deliberately: debug only in development, info for business events, warn, error and fatal for problems.
  • Pretty logs for humans in development; structured JSON logs for machines in production.
  • Instrument code with request-scoped traces (OpenTelemetry is the standard) and never log secrets.

Check yourself

Error rate is up, but you can't tell which dependency is failing. Which pillar is missing?

Traces. Metrics showed that errors rose and logs may show individual errors, but traces connect a failing request to the exact component and span where it failed.

Should a wrong password be logged at error level?

No, warn. It isn't a system failure. (Do log it, without the password, since repeated failures can signal an attack.)

Why do production log tools struggle with plain-text logs?

They have to guess structure from free text to extract fields like user ID or status. JSON logs give every field a name, so parsing, searching and charting are reliable.
