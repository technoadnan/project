Validations and transformations

Never trust incoming data. Right after a route matches, and before any business logic runs, every request passes through a validation and transformation pipeline that checks the data has exactly the shape your API expects and reshapes it into what your code needs.

What you'll learn

  • Where validation sits in the request lifecycle
  • Why missing validation turns a 400 into a 500
  • Syntactic, semantic, type and complex validations
  • Transformations: casting, normalising and why they live in the same pipeline
  • Why frontend validation never replaces backend validation

Where validation happens

A typical API call flows controller → service → repository. The controller handles HTTP concerns (status codes, response format, validation), the service runs business logic, and the repository talks to the database. Validation sits at the very front: after routing picks a handler, before the controller does anything significant.

Everything a client sends goes through it: the JSON body, query parameters, path parameters and headers.

Analogy

Airport security screens bags at the entrance, not halfway through the flight. Validation is the screening gate: check everything once, at the edge, so the rest of the system can trust what's inside.

Why it matters: 400 vs 500

Say POST /books expects { "name": "..." } as a string of 5–100 characters, and a client sends { "name": 0 }.

Without validation, the bad value travels all the way to Postgres, which rejects a number for a text NOT NULL column. The user gets a vague 500 Internal Server Error, even though they made the mistake. With validation, they get a precise 400 Bad Request telling them what to fix, and the server never wastes work on it.

Inside the pipeline

A reusable middleware or utility takes a schema and walks each field, failing fast with a specific message:

  1. Is it present? "name is required"
  2. Is it the right type? "expected string, received boolean"
  3. Does it meet the constraints? "must be 5–100 characters"

A bonus: good validation errors double as documentation. Send an empty body and the errors tell you exactly which fields the API expects.

Kinds of validation

Syntactic

Does it have the right structure? An email has name@domain.tld, a phone number has a country code plus digits, a date matches YYYY-MM-DD.

Semantic

Does it make sense? A date of birth can't be in the future; an age of 430 is impossible (accept 1–120).

Type

Is it a string, number, boolean, array or object? For arrays, is each element the right type?

Complex

Rules across fields: password confirmation must match; partner is required only if married is true.

Transformations

Sometimes data must change before it can be validated or used. The classic case is pagination: /bookmarks?page=2&limit=20. Your schema says page is a number between 1 and 500, but query parameters always arrive as strings. "2" would fail the number check even though the client did nothing wrong. So the pipeline casts "2" → 2 first, then validates.

Analogy

It's like changing money at the border. Query values arrive in "string currency"; you exchange them into numbers at the gate, before any shop (your validation rules and business logic) has to deal with them.

Other common transformations are normalisations: lower-casing emails, trimming whitespace, adding + to phone numbers, converting date formats. Validation and transformation live in one pipeline so every input rule and operation is in a single place.

Frontend validation is not enough

Form validation in the browser is great for user experience: instant feedback, no round trip. But it's not security. Anyone can call your API directly with Postman, Insomnia, curl or a script, and skip your frontend entirely.

Analogy

The bag-size frame at check-in helps passengers know if their bag will fit (frontend validation). The security scanner is mandatory for everyone, including people who walked straight past the frame (backend validation).

So be as strict and specific as possible on the server, regardless of what any client does.

Key takeaways

  • Validate and transform at the entry point: after routing, before controllers call services.
  • Validate everything: body, query params, path params and headers.
  • Validation turns confusing 500s into precise 400s, and stops bad data before it reaches the database.
  • Kinds: syntactic (format), semantic (makes sense), type, and complex (cross-field, conditional).
  • Transform (cast, normalise) in the same pipeline. Query and path values are always strings at first.
  • Frontend validation is for UX; backend validation is for security and data integrity. You need both.

Check yourself

Is "end date must be after start date" syntactic, semantic or complex?

Complex (a relationship between two fields), and semantic in spirit. Each date can be syntactically valid on its own.

Your API rejects ?limit=50 with "expected number, received string". What's missing?

A transformation step that casts query string values to numbers before validating them.

The frontend already checks emails. Why check again on the server?

Requests can bypass the frontend (API clients, scripts, other apps). Server-side validation is the only one you control, so it's the only one that guarantees integrity and security.
