Stateless servers: the entry ticket

Horizontal scaling only works if any server can handle any request and give the same answer. Then adding a server adds capacity and losing one loses nothing. That's what stateless means: no instance holds data that others can't see.

Analogy

At a bank, any teller can help you because your balance lives in the central ledger, not in one teller's drawer. If a teller kept your money in their own drawer, you'd have to queue for that teller, and if they went home, your money would go with them.

Load balancers: who gets the next request?

Every request goes to the load balancer, which picks a server, forwards the request and relays the response. The interesting part is how it picks:

Round robin

A, B, C, A, B, C… Simple and fine when servers are equal and requests are similar. Not when some requests take 250 ms and others 2 s.

Weighted round robin

A server with twice the RAM and cores gets twice the turns.

Least connections

Send to the server with the fewest active connections. Heavy requests hold connections open, so new work flows elsewhere. Variants: weighted least connections, least response time, and resource-based (live CPU/RAM).

Round robin sends every heavy request to C while big A sits idle. Try weighted and least connections, then crash B with health checks off and on. (Least connections without health checks is the worst case: a dead server always has zero connections, so it attracts everything.)

Health checks

The load balancer calls something like GET /health on every server every second or so. A non-2xx answer (or no answer) takes the server out of rotation; the balancer keeps probing and adds it back once it returns 200. Without health checks, round robin keeps feeding a dead server and users see 502/503 errors.

Scaling the database: read replicas

Once state lives outside your app servers, they scale easily. The database is the stateful part, and it becomes the next bottleneck. Most apps read far more than they write, so the first move is read replicas: copies of the primary that serve reads only.

Managed databases (RDS, Cloud SQL) make adding a replica a few clicks. The catch is the one every distributed system pays: consistency. Replication takes time; across continents, physics alone adds around 200 ms.

Read your own writes

For a few seconds after a user writes, route that user's reads (of that data) to the primary.

Wait out the lag

Track replication lag and only read from a replica that has caught up.

Hide it in the UI

Show the value the user just typed (optimistic update) instead of re-fetching immediately.

Sharding: splitting the table itself

Replicas spread reads, but every replica still holds every row. When a table reaches billions of rows (say, orders), sharding splits the rows across separate database instances by a shard key. More instances means more throughput; fewer rows per shard means faster queries.

Analogy

An encyclopedia too big for one book is split into volumes: A–F, G–M, N–Z. You go straight to the right volume, but a question like "every article mentioning Paris" means opening all of them.

Don't build this yourself

Distributed databases such as PlanetScale (Vitess/MySQL), Neon (serverless Postgres), CockroachDB and YugabyteDB handle sharding, replication and distributed transactions for you. Your job is to understand the concepts well enough to pick replica regions, shard keys and backups in their console.

CDNs: you can't beat the speed of light

Light in fiber travels about 200,000 km/s. Tokyo to a server in Northern Virginia (us-east-1) and back is roughly 20,000 km, so ~100 ms is the floor before your code does anything. Add database queries and external calls and a Tokyo user waits 500–800 ms. No optimization of your code can fix distance; only moving closer can.

A CDN (content delivery network) keeps copies of your content in points of presence (PoPs) around the world. The Tokyo user is served from Tokyo in 2–3 ms, and your origin never sees the request.

What to cache

Static files (JS/CSS bundles, images, fonts, video) and cacheable API responses, like a product catalog. Purge by URL or by tag when data changes.

Origin offload

Every hit served at the edge is a request your servers never handle, often half your traffic or more.

DDoS shield

A botnet of 20,000 machines can trigger autoscaling and a $50,000-a-day bill. A CDN like Cloudflare absorbs the flood and challenges suspicious clients before they reach you.

Edge computing: running code at the PoP

CDNs can also run your code at the edge (Cloudflare Workers, on lightweight V8 isolates). Good for quick decisions that don't need your database:

Edge runtimes are deliberately small: limited CPU and memory, no filesystem, no raw TCP connections. They're a front door for authentication checks, localization, routing and validation, not a replacement for your origin.

Async processing: respond now, work later

Not every task needs to finish before you respond. Move anything the user doesn't need to see immediately to a queue (lesson 14): the handler enqueues a job and responds; workers process it in the background and scale independently.

Video upload

Respond once the file is stored; thumbnails, HD encodes and subtitles happen in workers.

Delete account

Cleaning up 8 tables takes ~8 s. Respond in ~100 ms and let a worker do the deletes.

Tools

Redis (managed, e.g. Upstash) with BullMQ in Node; RabbitMQ or Kafka at larger scale. Adopt it early: it's one of the cheapest ways to cut perceived latency.

Microservices: an organizational tool

A monolith is one deployable unit: auth, orders, payments and notifications are modules in one codebase, running in one process (or many identical copies when scaled out). It's simple to develop, test, refactor and deploy. And you can always scale it horizontally.

So why split it into microservices? Mostly not for machine performance, but for organizational performance.

Analogy

A monolith is one restaurant kitchen; microservices are a food court. Each stall hires, cooks and renovates on its own schedule, and the busy stall can add staff without touching the others. But a combo meal now means walking between stalls, and if one stall's register goes down, your order is half-finished.

  • Independent deploys. With hundreds of engineers on one main branch, the payments team's urgent fix waits on the notifications team's half-ready code.
  • Independent scaling. Order processing is heavy and notifications are light, but a monolith scales as one block.
  • Right tool per job. The markdown service needs an npm package; image resizing in Go or Rust takes 50 ms instead of 500 ms. One deployable unit means one language.
  • The network. Function calls become HTTP or gRPC calls: added latency, failures, timeouts and retries to handle.
  • Debugging. One request crosses the load balancer, gateway, orders, payments and notifications. You need distributed tracing to follow it (lesson 18).
  • Data consistency. Each service owns its database, so keeping data consistent across them becomes your problem.

Consider it only with clear answers to these:

  • A large team (think 100–200+ developers) whose team boundaries can match service boundaries. This one is a prerequisite.
  • Parts that genuinely need to scale independently.
  • Parts that genuinely need different technology.

Otherwise the costs outweigh the benefits. A startup of 10–30 engineers coordinates fine with a monolith and feature flags.

The capacity-planning problem

With a traditional server you choose its size (say 2 cores, 4 GB RAM) before traffic arrives, which means predicting user behaviour. Guess too small and a campaign spike makes every request take 3–4 seconds, or crash; users leave. Guess too big and you pay for a 32 GB machine that sits mostly idle. Autoscaling adds instances when usage crosses a threshold (e.g. 70% memory) and removes them when it drops, but it has its own catches:

  • It's slow. A new instance boots an OS, fetches or builds your code and joins the load balancer: seconds to minutes.
  • It's reactive. It only scales once you're already under load, so a sharp spike hits before help arrives.
  • Its limits are a guess too. Set the maximum too low and you're capped; too high and a Black Friday or an attack can cost $100,000 in a day.
  • The minimum always costs money, at zero requests per second too.

Serverless: pay per request

Serverless still runs on servers; you just never see them. You hand the provider (AWS Lambda, Cloudflare Workers, Vercel…) functions and the events that trigger them. No OS, no machine size, no capacity planning. You pay only for the milliseconds your code actually runs.

The price of that model is the cold start: when no instance is warm, the provider must create one before your code runs.

Fighting cold starts

Keep-warm pings: ping your own functions so an instance stays ready; overdo it and you're paying 24/7 again. Faster sandboxes: Firecracker microVMs (AWS Lambda) and V8 isolates (Cloudflare Workers start in about a millisecond). Faster runtimes: JavaScript, Python and small compiled binaries start much faster than a JVM. Cold starts shrink, but never reach zero.

Other limits

Execution time: a Lambda function runs for at most 15 minutes. Statelessness: instances come and go, so long-lived database connections and WebSockets need rethinking, often with a serverless database or a pooler. Price per unit: each millisecond of compute costs more than on a server you keep busy.

✓ Good fits

Occasional heavy jobs: image resizing, video processing. Event-driven work: a message lands in a queue, a file is uploaded, a database row changes. Spiky, unpredictable traffic.

✕ Poor fits

Latency-critical paths (payments, banking), long-running requests and WebSocket connections, workloads that hold many database connections, and steady, predictable traffic, which most SaaS apps have.

Serverless is a powerful tool for specific jobs, not a universal replacement for servers.

Five rules of thumb

1

Start with the problem

Every technique here is a solution. Measure first (logs, metrics, traces, load tests; Prometheus + Grafana or New Relic) and know exactly what's slow and why before you fix anything. Fixing the wrong bottleneck is worse than doing nothing: it feels like progress.

2

Prefer simple

A big server before a fleet. An index before a Redis layer. A monolith before microservices; Kubernetes only when you must. Every component is something new to fail, monitor and operate.

3

Scale for the problems you have

Build for today's load plus reasonable headroom, not a million users on day one. Big-company engineering blogs solve their problems, not necessarily yours.

4

Observe from day one

The one exception to "keep it simple": production-grade logs, metrics and traces early. They warn you before users do.

5

It's a mindset

You learn scaling by watching your own systems struggle and fixing what the numbers point at. The goal isn't to predict every problem but to diagnose and recover quickly when one appears.

Key takeaways

  • Scale out only after making servers stateless: sessions in Redis, files in object storage, data in a shared database.
  • Pick a balancing algorithm that fits your traffic (least connections handles uneven requests well) and always use health checks.
  • Read replicas spread reads but bring replication lag; route a user's reads to the primary right after they write.
  • Sharding splits big tables across machines; the shard key is the hard decision. Prefer a managed distributed database.
  • Distance costs ~100 ms per ocean round trip. CDNs bring content close; edge functions bring small decisions close.
  • Queue anything the user doesn't need to wait for.
  • Microservices solve team-scale problems at the price of network, debugging and consistency complexity.
  • Serverless removes capacity planning but adds cold starts, time limits and statelessness. Great for spiky and event-driven work.

Check yourself

After adding a second server, users get logged out at random. What's wrong?

Sessions live in each server's memory. When the load balancer sends a request to the other server, it doesn't know the session. Move sessions to a shared store such as Redis (or use self-contained tokens).

A user changes their display name, the page reloads, and the old name is back. A minute later it's correct. Why?

Replication lag: the write went to the primary, the reload read from a replica that hadn't caught up yet. Route that user's reads to the primary briefly after a write, or update the UI optimistically.

Some API calls take 2 s and most take 200 ms. Why might round robin overload one server?

It counts turns, not work. Heavy requests can pile up on one server by chance or by pattern. Least connections (or least response time) sends new work to whoever is least busy.

Your API is in Virginia and Japanese users complain it's slow, even though server time is 20 ms. What helps?

The latency is mostly distance (~100+ ms per round trip). Cache what you can at a CDN, run quick checks at the edge, or deploy servers (and read replicas) in Asia.

A 15-person startup wants microservices "to scale". What would you suggest?

Keep the monolith and scale it horizontally. Microservices mainly solve large-team coordination; for a small team they add network calls, distributed debugging and data-consistency work without a matching benefit.

Which workload suits serverless best: a busy payments API, a nightly image-thumbnail job, or a chat server with WebSockets?

The thumbnail job: occasional, event-driven and tolerant of cold starts. Payments are latency-critical; WebSockets need long-lived connections.
