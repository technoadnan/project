The Twelve-Factor App

Config in environment variables, logs to stdout, stateless processes, servers that bind a port: this course has prescribed many such rules without defending them. Most come from one document: the Twelve-Factor App, written in 2011 by the people running Heroku. It's a contract between your app and the platform that runs it, and every modern platform assumes you follow it.

What you'll learn

  • Why the twelve factors exist: snowflake servers and software erosion
  • Codebase, dependencies, config and backing services
  • Build, release, run and immutable releases
  • Stateless processes, port binding and the process formation
  • Disposability and dev/prod parity
  • Logs as streams and one-off admin processes

A contract with the platform

The Twelve-Factor App states what must be true about your app so that any machine, any platform and any new teammate can run it, scale it and update it without surprises. Heroku, Docker, Kubernetes, Render, Railway, Fly, Cloud Run, App Runner, Vercel and Netlify all assume it, directly or indirectly. Many of its rules are now so standard that people follow them without knowing their source.

Scope: apps that run as a network service (web apps, APIs), in any language with any database. It's about the interface between app and platform, not general good practice like DRY or KISS.

The world it was written for

In 2011, deploying meant renting a server (or keeping one in the office), installing the OS, runtime and database by hand, copying code over FTP and editing config files over SSH. Each server was a hand-built snowflake, impossible to reproduce. A new developer needed days to get the app running, and it still didn't match production: "it works on my machine". Teams froze other work on deploy day.

Software erosion

The document's name for an app that slowly stops working although nobody changed its code: the OS gets patched, another app on the same server upgrades a shared library, the one person who knew the setup leaves. Like a riverbank washed away grain by grain. The twelve factors are its defences.

Heroku had watched many thousands of apps deploy, scale and break across languages and frameworks. Co-founder Adam Wiggins wrote the patterns down at 12factor.net. The text stayed nearly frozen (last touched in 2017) while containers, Kubernetes and serverless arrived. In November 2024, Heroku (now part of Salesforce) open-sourced it under neutral governance, with maintainers from AWS and Google Cloud among others. A community rewrite keeps all twelve names but restates each as numbered principles; at the time of the video it was still an unmerged draft. I. One codebase, many deploys

Version control sounds obvious now, but in 2011 production code could be a folder on someone's machine or final_v2_REALLY_final.zip. The subtler half is many deploys: production, staging, per-PR previews, your laptop. All run the same codebase, possibly at different commits. What makes them differ is never code; it's config.

Two boundaries: several codebases make a distributed system (each app follows the factors on its own), and the same code copy-pasted into two apps is a violation; extract it into a library pulled in as a dependency. Monorepos are fine: a repo that builds five apps is five codebases sharing a repository. The anti-pattern is one app living in two places.

II. Explicitly declare and isolate dependencies

Declare: a manifest lists every library the app needs (package.json, go.mod, pyproject.toml or requirements.txt, Gemfile), so setup is one command instead of days of guessing versions from import statements. Today's lockfiles (package-lock.json, go.sum) go further, pinning the exact version of every library and every library they depend on, so a build years later pulls identical code.

Isolate: declaring is useless if the app quietly uses whatever the machine has. Your manifest says requests v2, but the system Python already has v1 and the import finds that first. The same goes for system tools: shelling out to ImageMagick runs magick (v7, via Homebrew) on your Mac and convert (v6, via apt, with different defaults) on the Ubuntu server. In 2011 the answer was bundle exec, virtualenv and vendoring.

Then → now Containers freeze not just libraries but the OS, system tools and runtime too: the strongest declaration and isolation possible. People say Docker practically solved this factor.

III. Store config in the environment

Config is everything likely to differ between deploys: the database URL (a local container vs Amazon RDS), the email provider (sandbox vs live), object storage (MinIO vs S3), Redis, credentials. It must live outside the code. The document's test:

The open-source test

Could you open-source your codebase right now without leaking a single credential? Not would you, but could you. If not, config is hiding in your code.

Why environment variables? They change per deploy without editing files, can't be committed by accident (the classic way credentials leak), and they're an OS standard that works identically for Go, Node, Rust, Python or a bash script, unlike Java .properties files or Rails' config/database.yml, which kept ending up in repositories. The course's task app loads ~38 values, from server port to AWS settings, from TASKER_-prefixed variables into one config struct (lesson 17): config changed constantly over its history; the code reading it barely did.

# ✕ named environments: every new deploy needs new code
config/environments/development.rb
config/environments/staging.rb
config/environments/production.rb
config/environments/staging-but-other-db.rb  # …and so on
# ✓ granular, independent variables: compose a deploy by setting values
DATABASE_URL=postgres://…@pr-481-db:5432/app
REDIS_URL=redis://cache:6379
EMAIL_PROVIDER=sandbox
LOG_LEVEL=debug
The secrets debate

Environment variables are perfect for hostnames, but for passwords? In 2017 Diogo Mónica, then head of security at Docker, argued no: child processes inherit the whole environment, crash reporters and debug pages print it, and on Linux it's readable at /proc/<pid>/environ. The safer pattern is a secret manager (Vault, AWS Secrets Manager or Parameter Store) read at startup, held in memory, rotated and audited. For a solo developer or small team, platform-injected secret variables are fine, and far better than committed credentials.

IV. Treat backing services as attached resources

A backing service is anything your app uses over the network: Postgres, Redis, a queue, SMTP, S3, a payment API. The rule: your code makes no distinction between one you run and one someone else runs. Each is an attached resource reached through a resource handle (a URL plus credentials) stored in config.

Then → now In 2011, "the database is somebody else's computer and your app just has its URL" was eccentric; most people ran the app and database on one box. Today managed Postgres (RDS, Neon, PlanetScale, Supabase), managed Redis, S3 and email APIs like Resend are the norm, and app and database on the same server counts as an anti-pattern for scaling. This factor was practically a prediction.

V. Strictly separate build, release and run

A build contains code and dependencies, never config. A release is an exact build plus an exact config: the same image with production config is the production release; with staging config, the staging release. Releases form an append-only ledger: each gets an ID and is never modified.

Two payoffs. Rollbacks are instant and safe, because v101 still means exactly what it meant two hours ago: fix production in seconds, then debug the bad build at leisure. Heroku releases, Docker image tags and Kubernetes rollouts all work this way. And nobody can edit code on a production server: code enters only at the build stage, so the snowflake-era SSH hot patch, the reason production and the repository used to drift apart, has no path back in. The rewrite makes "every release is a unique, immutable snapshot" an explicit principle.

VI. Execute the app as stateless processes

Share nothing: processes keep no memory or disk state between requests; anything that must persist goes to a backing service. Assume any process can serve any request and any process can vanish at any moment. Memory or a temp file used within a single request is fine; nothing later may rely on it.

The document calls sticky sessions (the load balancer pinning each user to one instance so in-memory sessions keep working) a violation. They defeat the point of several instances: kill one and its users are logged out; add one and it gets no existing users. Sessions are state; put them in Redis or Postgres (lesson 21.2).

The honest exception: a WebSocket is state held in one process (lesson 25), which is why real-time systems lean on pub/sub. Treat statelessness as the default and break it only when the feature itself is the state.

Rule of thumb

If you can't kill any process at any moment without a user losing data, there's state somewhere it doesn't belong.

VII. Export services via port binding

In 2011 a PHP app didn't run itself; Apache ran, with PHP loaded as a module. A Java app was a file dropped into Tomcat's folder. The web server's version and config were part of the app's environment, living on the physical server: erosion again. The factor says the app must be self-contained: bring its own HTTP server as a declared dependency and bind a port (:8080, :4000), with a routing layer in front in production.

A neat consequence: anything that binds a port can be a backing service for anything else. Your database, cache and mail catcher run on local ports in development; in production the handles point at someone else's ports in the cloud. Same pattern throughout.

Then → now Serverless functions don't bind ports; the platform calls an exported function. The rewrite keeps port binding as the headline but generalises it: the app is self-contained and exports its service through a declared interface, covering both long-running servers and functions.

VIII. Scale out via the process model

Runtimes once scaled in their own ways: the JVM grabbed a huge block of memory at startup and multiplexed threads inside; Apache spawned PHP child processes on demand. Borrowing from Unix service daemons, the factor makes the process the unit of scale, with a process type per kind of work: web for HTTP, worker for background jobs like video encoding, clock for schedules. Each type scales on its own; the types and counts together are the process formation.

# Procfile (Heroku, Overmind, Foreman)
web:     ./tasker serve
worker:  ./tasker jobs
release: ./tasker migrate
# Kubernetes: the same idea in YAML
kind: Deployment
metadata: { name: web }
spec:
  replicas: 10   # ← the formation

Threads, goroutines and event loops inside a process are fine (lesson 22), but scale by adding processes, because a share-nothing process spreads across machines while one machine only grows so far. And a twelve-factor app never daemonizes or writes PID files; it runs in the foreground and lets the platform (systemd, Kubernetes) manage its lifecycle. Then → now Orchestrators made this so universal that it's invisible: you declare a formation, and the platform keeps it running.

IX. Maximize robustness with fast startup and graceful shutdown

Processes must be disposable: startable and stoppable at a moment's notice. Stopping is routine now: deploy 5 times a week to 10 instances and that's 50 stops and 50 starts before any autoscaling.

  • Fast startup: a 60-second boot makes a rolling deploy of 10 instances take 10 minutes and leaves the autoscaler a minute late to every spike. Aim for a few seconds.
  • Graceful shutdown on SIGTERM (lesson 19): web processes stop accepting requests, finish in-flight ones, then exit; workers return their current job to the queue.
  • Re-entrancy: a returned job will run again, so it must leave no half-done state: wrap it in a transaction or make it idempotent.
  • Sudden death: an out-of-memory kill gives no warning. The document points to crash-only design: if your app survives a crash at any instruction, the crash path is the shutdown path.

X. Keep development, staging and production as similar as possible

TimeWeeks between writing and deploying, many changes at onceHours

ToolsDifferent stacks: a Mac with SQLite locally, Linux with Postgres in productionAs similar as possible

The tools gap is the one that survives. ORMs (Prisma, Drizzle, GORM, SQLAlchemy) make it tempting to develop on SQLite and run Postgres in production, and the differences bite silently, with no error and no log:

Use the same backing services everywhere; a container is one command away. Managed services reopen the gap: AWS DynamoDB is proprietary, and LocalStack only emulates its documented behaviour. If a managed service's benefits are large, accept the gap knowingly.

XI. Treat logs as event streams

A log file was never the log; it's one possible output. The log is a time-ordered stream of events flowing as long as the app runs. So the app shouldn't route or store it, manage file paths or rotate files: write every event, unbuffered, to stdout, and let the environment capture and route it. In 2011 that meant syslog; today Loki or Datadog (lesson 18).

Changing where logs go becomes a config change, not a code change, and streams compose: your terminal shows them live, a container runtime stamps them with their source, and the platform merges all instances into one time-ordered stream. Metrics and traces weren't common practice in 2011; treat them as additions, not contradictions.

XII. Run admin tasks as one-off processes

Migrations, data fixes and scripts run as one-off processes next to the app, in an identical environment: same codebase, same commit (shipped with the release), same config, same dependency isolation. The old way was SSHing into a production server and typing an UPDATE: no review, no record, and production silently drifting from the code. Database migrations that ship with the code and run before the app starts are the classic example; Heroku even has a release process type for them.

All together

The task app on a Linux box, driven by a Procfile and the Overmind process manager: on boot it checks the schema, starts the job server and binds its assigned port, logging to stdout. A one-off auto-archive command runs from the same code and config, then exits. Ctrl-C closes the connection pool, waits for workers to finish their jobs and exits cleanly: factors VIII, IX and XII in one terminal.

Key takeaways

  • The twelve factors are a contract between app and platform, written to stop snowflake servers and software erosion. Every modern platform assumes them.
  • One codebase, many deploys; deploys differ only by config. Declare and isolate dependencies; containers finish the job.
  • Config lives in the environment (pass the open-source test); secrets go to a secret manager as you grow. Backing services are attached via URLs.
  • Build, release, run: immutable builds plus config make an append-only ledger of releases and instant rollbacks.
  • Stateless, share-nothing processes that bind a port, scale by process type, start fast, shut down gracefully and survive crashes.
  • Keep dev and prod alike, especially backing services. Logs go unbuffered to stdout. Admin tasks run as one-off processes from the same release.

Check yourself

Your staging and production differ by an if (env === "production") branch that picks a different database. Which factor does this break, and what's the fix?

Factor III (and I): deploys should differ by config, not code. Read DATABASE_URL from the environment and drop the branch; any new deploy is then just a new set of values.

A bad deploy is throwing errors. Why can a twelve-factor app recover in seconds?

Releases are immutable build + config snapshots in an append-only ledger. Rolling back re-runs a previous release whose build already exists; nothing needs rebuilding. Debug the bad one afterwards.

Your app scales to 10 instances at lunch, but most of the memory goes to background-job code that's idle. What should change?

Split process types (web, worker) so each scales independently: 10 web and 2 workers at lunch, the reverse at night.

Search works locally but returns fewer results in production. Development uses SQLite, production Postgres. A likely cause?

SQLite's LIKE is case-insensitive for ASCII; Postgres's is case-sensitive (use ILIKE or lower()). Factor X: use the same backing service in development.

Why shouldn't your app write its own rotating log files?

Factor XI: the app's job is to emit an unbuffered event stream to stdout. Routing, storage and rotation belong to the platform, so they change through config, and streams from many instances can be merged.
