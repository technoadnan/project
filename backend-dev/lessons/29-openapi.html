OpenAPI: the contract between clients and servers

Inside one codebase, change a function's signature and the compiler flags every caller. Across HTTP there are no signatures, so a renamed field breaks clients at runtime, in production. OpenAPI gives remote calls a signature: one machine-readable file describing every endpoint, from which you generate docs, clients, server interfaces, mocks and tests.

What you'll learn

Three copies of the truth

The task board's POST /api/move takes a JSON body with task_id, to and actor, and answers 200, 400, 404 or 502 depending on what happened. Where does that knowledge live? In three places: the backend handler that reads the body, the frontend code that calls it, and (maybe) a document someone wrote. Three copies drift:

This problem only exists across a network boundary. Inside one Go codebase, renaming a struct field or changing a string to an int breaks the build at every call site, so you fix it during development. An HTTP call has no signature for a compiler to check, so mismatches surface at runtime.

Analogy

A restaurant menu is a contract between the kitchen and the diners: what you can order, what you must specify ("how would you like your steak?"), and what arrives. If the kitchen renames a dish but the printed menus are left as they were, diners order something that no longer exists. OpenAPI is a menu that the kitchen, the waiters and the menu printer all generate from one master copy.

What OpenAPI is

An OpenAPI description is a file, in JSON or YAML (equally supported), that lists every endpoint of your API with its inputs, outputs and behaviour. The specification calls itself a language-agnostic interface description that lets both humans and computers understand a service's capabilities without source code, extra documentation or inspecting network traffic. From one file you get:

Docs

Read-only or interactive: Swagger UI, ReDoc and Scalar render the file and let you send real requests with your token.

Clients

Typed SDKs in TypeScript, Python, Go, Rust… generated, not hand-written.

Server code

Interfaces and boilerplate your handlers must satisfy.

Validation

Middleware that checks query, path and body against the schema, with no hand-written validation code.

TermMeans
OAS: OpenAPI SpecificationThe rulebook: which fields exist and what they mean.
OAD: OpenAPI DescriptionYour file, usually openapi.yaml or openapi.json, following those rules.
OAI: OpenAPI InitiativeThe Linux Foundation organization that maintains the spec.
SwaggerThe old name of the spec; today a family of tools such as Swagger UI. A "Swagger file" means an OAD.

Most people write YAML: it's a superset of JSON and, unlike JSON, allows comments.

Anatomy of a description

The smallest valid description needs only three fields:

openapi: 3.1.1          # version of the SPEC
info:
  title: Task Board API
  version: 1.4.0        # version of YOUR API
paths: {}

The root object

Required: openapi, info, and at least one of paths, components or webhooks. Optional: servers (where the API lives: localhost, staging, production, so paths stay relative), security (how clients authenticate) and tags (groups for the docs). Don't confuse the two versions: one is the spec's, one is yours.

Here's the move endpoint, fully described:

servers:
  - url: http://localhost:8080
paths:
  /api/move:                      # keys start with "/"; dynamic parts look like /api/tasks/{id}
    post:                          # one operation per HTTP method
      operationId: moveTask         # unique, function-style: becomes client.moveTask()
      summary: Move a task to another column
      tags: [tasks]
      requestBody:
        required: true
        content:
          application/json:          # media type → schema
            schema: { $ref: "#/components/schemas/MoveRequest" }
      responses:
        "200": { description: Moved, content: { application/json: { schema: { $ref: "#/components/schemas/Event" } } } }
        "400": { description: Invalid body }
        "404": { description: No task with that id }
        "502": { description: Moved, but publishing to the event bus failed }
components:
  schemas:
    MoveRequest:
      type: object
      required: [task_id, to]
      additionalProperties: false
      properties:
        task_id: { type: integer, minimum: 1 }
        to:      { type: string, enum: [todo, doing, done] }
        actor:   { type: string, maxLength: 40, default: guest }

Parameters

Each has a name, an in (path, query, header or cookie), required and a schema. The polling endpoint takes since (integer) in the query; the SSE endpoint can receive the same value as the Last-Event-ID header. Path parameters are always required; an optional one would describe a different URL.

Request bodies

content maps a media type (what goes in Content-Type) to a schema: application/json for JSON, multipart/form-data for uploads, application/x-www-form-urlencoded for classic HTML forms.

Responses

Keyed by status code in quotes; each needs a description and usually a content with a schema. Document the errors too, not just the 200.

Schemas

Types (string, number, integer, boolean, array, object, null) plus constraints: minLength, maxLength, pattern, enum, minimum, maximum, items, properties, required. Nest them to describe any shape; share them via components and $ref.

Code-first or design-first?

Code-first

Write handlers first; derive the description from annotations, comments above handlers, or the types themselves. Python's FastAPI generates it from your handlers' type hints. In TypeScript, Zod schemas wired into a ts-rest contract can generate openapi.json from code, which beats comments: code is easier to maintain and harder to let rot.

Design-first (contract-first)

Write the description before the implementation; the server, clients, mocks and tests all follow it. The Swagger team itself started code-first, because they had an existing server, and later concluded contract-first makes more sense.

Code-first is natural when the server already exists. For new projects, design-first pays off: once frontend and backend agree on the contract, they can be built in parallel, with neither blocked on the other. The same applies to AI coding agents: settle the contract, then one agent builds the server while another builds the client.

The design-first pipeline

Everything below derives from one file, the single source of truth.

// types generated by openapi-typescript; calls via openapi-fetch
import createClient from "openapi-fetch";
import type { paths } from "./api.d.ts";

const client = createClient<paths>({ baseUrl: "http://localhost:8080" });

const { data, error } = await client.POST("/api/move", {
  body: { task_id: 7, column: "done" },
  //                 ~~~~~~ Object literal may only specify known properties,
  //                        and 'column' does not exist in type 'MoveRequest'.
});
// generated by oapi-codegen (strict server): handlers must implement this
type StrictServerInterface interface {
    GetBoard(ctx context.Context, req GetBoardRequestObject) (GetBoardResponseObject, error)
    MoveTask(ctx context.Context, req MoveTaskRequestObject) (MoveTaskResponseObject, error)
}

// Add a field or an operation to openapi.yaml, regenerate, and
// the build fails until the handler matches the contract again.

OpenAPI is the industry's common language for HTTP APIs: GitHub and Stripe publish theirs (roughly 344,000 and 171,000 lines respectively) so anyone can generate clients. And it has found a new audience: AI agents use API descriptions to understand which tools they can call and how.

Key takeaways

  • API knowledge spread across handler, client code and docs drifts; across HTTP nothing catches the mismatch until runtime.
  • An OpenAPI description is one JSON/YAML file describing every endpoint's inputs, outputs and behaviour, readable by humans and machines.
  • OAS is the rulebook, OAD your file, OAI the organization; Swagger is the old name and now a set of tools.
  • Key pieces: servers, paths → operations (with a function-style operationId), parameters (in), request bodies and responses by media type, and schemas with constraints, shared through components.
  • Code-first derives the file from code; design-first writes it first so teams (and agents) work in parallel.
  • Lint it (Spectral), mock it (Prism), generate clients and server interfaces, render docs (Swagger UI, ReDoc, Scalar), and contract-test the real server (Schemathesis).

Check yourself

Why does renaming a field break a frontend at runtime, while renaming a Go struct field breaks the build?

Inside one codebase the compiler checks every call against the function's signature. An HTTP call has no signature the compiler can see, so mismatches only appear when the request is made, unless both sides are generated from or checked against a shared contract.

What's the difference between openapi: 3.1.1 and info.version: 1.4.0?

The first is the version of the OpenAPI Specification the file follows; the second is the version of your API.

Your frontend team is blocked waiting for the backend. How does design-first help?

Agree on the OpenAPI description first, run a mock server (e.g. Prism) that answers with the documented examples, and generate a typed client. The frontend builds against the mock while the backend implements the same contract.

How can you verify that the running server actually matches its description?

Contract testing: a tool like Schemathesis generates valid and invalid requests from the schemas, sends them to the real server, and checks every response against the description.

Why should operationId look like a function name?

Generators turn each operation into a function or method named after it (moveTask, getBoard), so it must be unique and a valid identifier.
