Understanding HTTP for backend engineers

HTTP is how browsers and servers talk. It rests on two ideas: it's stateless (every request carries everything the server needs) and it's client–server (the client always starts the conversation). Everything else, from headers and methods to CORS, status codes and caching, is built on that.

What you'll learn

  • Statelessness and why it makes scaling easy
  • What raw request and response messages look like
  • Headers, methods and idempotency
  • How CORS and preflight requests really work
  • Status codes you'll use 95% of the time
  • Caching with ETags, content negotiation, compression, big files and TLS

Idea 1: statelessness

HTTP has no memory. After the server responds, it forgets the request. The next request from the same client is a brand-new, unrelated event. So every request must be self-contained: if the server needs to know who you are, you send your token or cookie every time.

Analogy

It's like a support hotline where a different agent answers every call. Nobody remembers you, so you read out your account number each time. Annoying for you, but the company can add agents freely, and if one goes home sick, nothing is lost.

Simplicity

No session storage on the server means less memory and less complexity.

Scalability

Any server can handle any request, so you can spread traffic across many machines.

Resilience

If a server crashes, there's no in-memory session to lose or restore.

When you do need continuity (logins, shopping carts), you layer it on top with cookies, sessions or tokens. Lesson 8 covers this.

Idea 2: client–server

There's always a client (a browser, a mobile app, another server) and a server that hosts resources and waits. The client always initiates. A server can't spontaneously send an HTTP response to someone who didn't ask. (Real-time techniques in lesson 25 work around this.)

HTTPS is HTTP plus encryption. Everything here applies to both.

Under HTTP: TCP and the versions

HTTP only needs a reliable transport that doesn't silently lose messages, so it traditionally runs on TCP. Backend engineers live at layer 7 of the OSI model (the application layer). TCP handshakes and TLS belong to the network layers below, so it's worth knowing they exist without going down that rabbit hole.

VersionWhat changed
1.0A new TCP connection for every request: open, request, response, close.
1.1Persistent connections (keep-alive by default), chunked transfer and better caching. Still one request at a time per connection.
2Multiplexing: many requests interleaved on one connection. Binary framing, HPACK header compression, server push.
3Runs on QUIC over UDP: faster connection setup, better handling of packet loss, and no TCP head-of-line blocking.

Anatomy of an HTTP message

A request and a response share the same shape: a start line, headers, a blank line, then an optional body.

Headers: metadata on the outside

Headers are key–value pairs describing the message. Why not stuff this into the URL or body?

Analogy

When you post a parcel, the address and phone number go on the outside. Every courier along the way can read them without opening the box. Headers are that label: proxies, caches, load balancers and your framework can act on them without parsing the body.

Sent by the client to describe itself and its preferences.

  • User-Agent: what's calling (browser, Postman, mobile app, another server).
  • Authorization: credentials, such as a bearer token.
  • Accept: which formats the client wants back (JSON, HTML…).

Used in both directions; about the message itself.

  • Date: when the message was sent.
  • Cache-Control: no-cache, max-age=60…
  • Connection: keep-alive or close.

Describe the body so the other side can interpret it.

  • Content-Type: media type, e.g. application/json.
  • Content-Length: size in bytes.
  • Content-Encoding: compression, e.g. gzip.
  • ETag: a version fingerprint, used for caching.

Tell the browser how to behave safely.

  • Strict-Transport-Security: HTTPS only; prevents downgrade attacks.
  • Content-Security-Policy: where scripts, styles and images may load from (blocks XSS).
  • X-Frame-Options: no embedding in iframes (blocks clickjacking).
  • X-Content-Type-Options: nosniff: don't guess MIME types.
  • Set-Cookie: …; HttpOnly; Secure: hide cookies from JS, send them over HTTPS only.

Two ideas make headers powerful:

  • Extensibility: add a header (even a custom X-Something) and behaviour changes without touching the protocol.
  • Remote control: the client steers the server: "send JSON", "in Spanish", "gzipped", "here's who I am".

Methods: the intent of a request

The method says what you intend to do to a resource. It gives every request a clear meaning.

Rule of thumb: use PATCH unless you really mean "replace everything". Many APIs misuse PUT for partial updates.

Idempotency

An operation is idempotent if doing it once or ten times leaves the server in the same state. GET reads, PUT replaces with the same data, DELETE can only delete once. POST creates a new thing each time.

Analogy

Pressing a lift's call button five times still brings one lift: idempotent. Telling a barista "one more coffee" five times gets you five coffees: not idempotent.

CORS: the browser's guest list

Browsers enforce the same-origin policy: JavaScript from example.com may not read responses from a different origin like api.example.com (a different port counts too). CORS lets the server say which other origins are allowed.

Analogy

The browser is a bouncer and the server owns the guest list. For a quick visit (a simple request), the bouncer checks the list when the answer comes back. For a big entrance with unusual demands (a preflighted request), the bouncer phones ahead first: "Do you accept PUT requests with an Authorization header from example.com?"

Simple requests

Gotcha

A CORS error doesn't mean the server didn't run your request. For simple requests, the server processes it. The browser just refuses to hand the response to your JavaScript. CORS protects users' browsers, not your server.

When is a request preflighted?

A cross-origin request needs a preflight if any one of these is true:

  • The method isn't GET, POST or HEAD (for example PUT or DELETE).
  • It has non-simple headers, such as Authorization or custom headers.
  • Its Content-Type isn't form-urlencoded, multipart or text/plain. application/json triggers a preflight, so most API calls are preflighted.

Status codes: the result at a glance

A three-digit code tells the client what happened without it having to inspect the body. They're standard across every language and framework, so a client can react consistently: on 401 log the user out, on 400 highlight the form.

1xx Info

100 continue (send the big body), 101 switching protocols (e.g. to WebSocket).

2xx Success

It worked.

3xx Redirect

Look elsewhere, or use your cached copy.

4xx Client error

The request was wrong; the client should fix it.

5xx Server error

The server failed; not the client's fault.

Analogy: 401 vs 403

401 is the receptionist saying "Who are you? Please show your badge." 403 is "I know exactly who you are, and you're not allowed on this floor."

HTTP caching

Caching reuses a stored response instead of downloading it again: faster pages, less bandwidth, less server load. Three response headers drive it:

  • Cache-Control: max-age=10: reuse this copy for up to 10 seconds without asking.
  • ETag: "3141": a fingerprint (usually a hash) of this version of the response.
  • Last-Modified: when the resource last changed.
Analogy

Instead of asking the library to post you the whole book again, you ask: "Is there a newer edition than #3141?" Most of the time the answer is a one-word "no" (304), and you keep reading your copy.

In practice, keeping ETags correct is fiddly: forget to update one and clients see stale data. Many apps now cache on the client with libraries like React Query, which control exactly when to refetch. HTTP caching is still great for simple cases and static assets.

Content negotiation and compression

The client states preferences and the server picks the best match (or a fallback):

  • Media type: Accept: application/json or application/xml
  • Language: Accept-Language: en or es
  • Encoding: Accept-Encoding: gzip, deflate, br, zstd

In the video's demo, a JSON response with 11,000 entries is 26 MB uncompressed but 3.8 MB with gzip. The browser decompresses it transparently, so you get the same data for about a seventh of the bandwidth.

Persistent connections

Opening a TCP connection is slow. HTTP/1.1 keeps connections open by default so many requests can reuse one. Connection: keep-alive (optionally with a timeout and a max request count) asks to keep it open; Connection: close closes it after the response, which was the HTTP/1.0 default. The defaults are almost always fine.

Large requests and responses

Uploading: multipart

Files go up as multipart/form-data. The body is split into parts, separated by a boundary string declared in the Content-Type header, so the server knows where each part starts and ends.

Downloading: streaming

The server sends data in chunks over one kept-alive connection (e.g. Content-Type: text/event-stream), and the client appends each chunk as it arrives instead of waiting for the whole thing.

SSL, TLS and HTTPS in one minute

SSL

The original protocol for encrypting client–server traffic. Now outdated because of security flaws.

TLS

Its modern replacement. Uses certificates to prove the server's identity, then encrypts data in transit. TLS 1.3 is the current recommendation.

HTTPS

Plain HTTP running over TLS. Same messages, but nobody in the middle can read or tamper with them.

Key takeaways

  • HTTP is stateless: each request carries its own auth and context, which is exactly what makes horizontal scaling easy.
  • The client always initiates. Messages are a start line, headers, a blank line and a body.
  • Headers are the parcel label: metadata every hop can read. They give HTTP its extensibility and "remote control".
  • Methods express intent. GET, PUT and DELETE are idempotent; POST isn't. Prefer PATCH for partial updates.
  • CORS is enforced by the browser. JSON bodies, auth headers and PUT/DELETE trigger an OPTIONS preflight.
  • Status codes are a shared language: 2xx success, 3xx redirect or cache, 4xx client mistake, 5xx server failure.
  • ETags plus conditional GETs give cheap 304 responses; compression and streaming handle big payloads.

Check yourself

Your React app sends PUT /api/notes/1 with a JSON body and a bearer token to another domain. How many HTTP requests does the browser make?

Two. First an OPTIONS preflight (it's PUT, has an Authorization header and a JSON content type), then the actual PUT, if the preflight response allows the origin, method and headers.

A user is logged in but tries to delete someone else's post. 401 or 403?

403 Forbidden. The server knows who they are (so not 401) but refuses the action.

Why is POST not idempotent but PUT is?

Each POST creates a new resource, so repeating it changes server state again. PUT replaces a resource with the given data; repeating it with the same data leaves the same state.

What does a 304 response contain, and why is it cheap?

Just headers, no body. The server confirms the client's cached version (matched by If-None-Match/ETag or If-Modified-Since) is still current, so nothing big is re-sent.

Nginx returns 504 to your users. Where should you look?

At the upstream app server behind Nginx. It didn't answer within the timeout, perhaps because a slow query or a hung process. 502 would mean it answered with something invalid, or crashed.
