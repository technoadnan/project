Full text search with Elasticsearch

WHERE name ILIKE '%laptop%' works fine for 5,000 products and falls apart at millions. It's slow, it has no sense of relevance, and one typo breaks it. Search engines like Elasticsearch fix all three with an old idea: the inverted index.

What you'll learn

  • Why LIKE-based search doesn't scale
  • How an inverted index flips the problem
  • How relevance is scored (BM25, field boosting)
  • Typo tolerance, type-ahead and log search
  • When to choose Elasticsearch vs Postgres full-text search

A search that stopped working

It's 2005. Your e-commerce company has 5,000 products and you write:

SELECT * FROM products
WHERE name ILIKE '%laptop%' OR description ILIKE '%laptop%';

About 50 ms, and everyone's happy. Then the company explodes to millions of products, and the same query takes 30 seconds. Your manager also wants it to be:

Fast

Milliseconds, not seconds. Every second of delay costs conversions.

Relevant

"laptop" should show a MacBook Pro before a laptop bag.

Typo-tolerant

Rushed shoppers type "laptpo". They should still find laptops.

The librarian problem

Analogy

Your database is a librarian who knows where every book is, but to find "books about machine learning" they must open every book on every shelf: Harry Potter, no; Game of Thrones, no; Introduction to Machine Learning, yes… With a billion books, that takes days. And they hand you results in random order: a book that mentions machine learning once on its last page might come before the one with it in the title.

That is exactly what ILIKE '%…%' does: scan every row, pattern-match every text field character by character, then return the matches unranked. Thorough, but slow and dumb about relevance. Google, Amazon and LinkedIn, indexing billions of pages, products and profiles, couldn't live with that.

The big idea: flip it

Decades of information-retrieval research (since the 1960s) produced the key insight: don't search the documents for the words; look the words up to find the documents. When a document arrives, break it into terms and record, for each term, which documents contain it (and where). That's an inverted index, like the index at the back of a textbook, built for the whole library.

This idea is implemented by Apache Lucene, the engine inside Elasticsearch (and many other search tools). Postgres also ships its own full-text search.

Relevance scoring

Elasticsearch ranks results with the BM25 algorithm. You don't need the maths, just the intuition:

Term frequency

A term appearing many times in a document is a sign the document is about it.

Document frequency

Rare terms matter more. "laptop" across all products tells you less than "thunderbolt".

Document length

One mention in a short title outweighs one mention in a 500-page book.

Field boosting

You decide: a match in the title beats one in the description, which beats one in the body.

What it's used for

Type-ahead & typos

Search-as-you-type boxes like Amazon's or Google's. Type "what is treading today" and it still understands "trending".

Product, profile & content search

Full-text search over users, posts and comments, ranked by relevance, with filters and aggregations.

Logs (ELK stack)

Elasticsearch + Logstash + Kibana: fast search and dashboards over huge volumes of logs (lesson 18).

Which should you use?

Postgres full-text search

Already on Postgres and your search needs are modest? Start here: no extra system to run and keep in sync.

Elasticsearch

Need heavy relevance tuning, typo tolerance and type-ahead at scale, or already run the ELK stack for logs? Use it.

Perspective

Master your database: it touches almost all of your code. Elasticsearch you can mostly use well from the docs and standard examples, then dig deeper only when you need to optimise.

Key takeaways

  • ILIKE '%term%' scans every row and returns unranked results, which breaks down at scale.
  • An inverted index maps each term to the documents containing it: look up words instead of scanning documents.
  • Relevance (BM25) uses term frequency, rarity across documents, document length and field boosts.
  • Search engines add typo tolerance, type-ahead, filters and aggregations; Elasticsearch is built on Apache Lucene.
  • Use Postgres full-text search for simple needs; use Elasticsearch for serious search or if you already run ELK.

Check yourself

Why can't a normal B-tree index speed up ILIKE '%laptop%'?

A B-tree helps with prefix or equality lookups. A leading wildcard means the match could start anywhere in the text, so the database still has to examine every value.

In Elasticsearch, should an order status like shipped be mapped as text or keyword?

Keyword: you filter on the exact value; you don't want it analysed into terms or scored.

A laptop bag outranks a laptop for "laptop". What would you tune?

Field boosting (weight the title or category more heavily), and possibly use structured filters such as category = laptops alongside the text query.
