Why one big PUT stops working

1

A hard limit

A single PUT to S3 can't exceed 5 GB. Accept videos, drone footage, CAD files or database dumps and you're architecturally forced to do something else.

2

All or nothing

At 4.8 GB of 5 GB, the Wi-Fi blinks and the upload is gone. No resume; start from zero. On mobile, that transfer takes 20–30 minutes, and mobile networks glitch constantly.

3

One TCP stream is slow

A single connection's throughput is bounded by window size ÷ round-trip time, and one lost packet collapses its window. On a 200 Mbit/s link, one stream may manage 30. Parallel streams each get their own window; that's all download managers do.

4

Poor experience

Coarse progress, no pause, and nothing survives a closed tab.

The multipart upload protocol

Three calls (plus one for giving up):

Analogy

Like git add before git commit: parts pile up in a staging area, invisible to everyone (a GET on the key is still 404), until one commit makes them a single object. And because the commit just records "this object = these parts in this order" in the metadata plane, completing a 50 GB upload takes as long as completing a 50 MB one.

Choosing the part size

There's a hard cap of 10,000 parts (each at least 5 MB, except the last). With a fixed 5 MB part size, the biggest possible file is 50 GB; a 60 GB upload fails at part 10,001, after 50 GB has been transferred. So compute it: partSize = max(floor, fileSize ÷ 10,000). Why not just use huge parts? A part is your retry unit: a failed 500 MB part on mobile means resending 500 MB. A floor of 16–64 MB is the sweet spot.

Gotcha: multipart ETags aren't MD5s

For a single PUT, the ETag is the MD5 of the content, so people compare it with a local hash. For multipart uploads it's an MD5 of the parts' MD5s plus -N (e.g. "9b2c…-42"), so that check breaks. Use the SDK's checksums (CRC32C or SHA-256 per part, plus a full-object checksum the service verifies), or compute your own SHA-256 in the browser, store it as metadata and verify it in a background job. Bonus: free deduplication.

Gotcha: abandoned uploads cost money, invisibly

300 parts uploaded, tab closed, Complete never called: ~10 GB sits in the staging area, billed every month, yet absent from the console and from listings (no object exists). Only "list multipart uploads" reveals them. Add this lifecycle rule to every bucket on day one:

{ "Rules": [{ "ID": "abort-stale-mpu", "Status": "Enabled",
  "Filter": {},
  "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 } }] }

Multipart + presigned URLs: the full architecture

  • Presign in batches (say 100 at a time) as the browser works through them. Signing 10,000 URLs up front makes the init response megabytes of JSON.
  • 4–6 parallel PUTs is the sweet spot; more just fights over the same bandwidth.
  • file.slice() returns a lazy Blob, read only when sent, so browser memory is part size × concurrency, not the file size.
  • The bucket's CORS config must expose the ETag header, or JavaScript can't read it and can't complete the upload.
  • Resume comes free: after a refresh, the API finds the pending row, calls ListParts to see which parts the bucket already has, and presigns only the missing ones.

Downloads: keep your server out of the way

Files are downloaded far more often than uploaded, so this is where most of the data (and money) goes. Rule one, again: don't proxy downloads through your backend. Each one ties up a worker for its whole duration, you pay for the bandwidth twice, and your one or two regions are slower than a CDN's hundreds of edge locations.

1

Public assets

Product images, CSS, JS bundles: keep the bucket private, put a CDN in front that alone may read it, set a long Cache-Control, and use content-addressed keys (the key includes a hash of the content, like app.3f9a1c.js). New content means a new URL, so caches never serve stale files. Cheapest and fastest.

2

Presigned GET

Private files: your API checks the user may see the file, then returns a GET URL valid for 5–15 minutes. Same mechanics as presigned uploads.

3

CDN signed URLs or cookies

Authorization moves to the CDN's edge, which also keeps full control of caching. Ideal for video, where one viewing session fetches hundreds of segments you'd otherwise have to sign one by one.

Range requests

A client can ask for part of a file: Range: bytes=1000000-2999999. The server answers 206 Partial Content with a Content-Range header saying which bytes these are and how big the whole file is; a nonsensical range gets 416 Range Not Satisfiable. This is plain HTTP, and since object storage speaks HTTP, every bucket supports it. That unlocks:

  • Video seeking: drag to minute 30 and the player computes the byte offset and fetches from there, skipping everything before.
  • Resumable downloads: the connection drops at byte 400,000,000; re-request from exactly that byte.
  • Parallel downloads: six connections, six ranges, one file.
  • Peeking: read the first 8 bytes to learn a file's real type without downloading it.

Adaptive video streaming

Range requests serve one version of a file to everyone. Netflix and YouTube do better with segmented streaming (HLS or DASH): transcode the original into several qualities, cut each into segments of a few seconds, and write a manifest listing them all. The player fetches the manifest, then one segment at a time, timing each download to decide the next segment's quality: adaptive bitrate.

Nothing changes on the storage side: segments and manifests are just objects, and object storage plus a CDN can serve a streaming platform. The hard engineering is the transcoding pipeline: queues and workers triggered on every upload (lesson 14). If video is a small feature, use a hosted service such as Mux or Bunny Stream. If video is your product, building the pipeline yourself is what makes the costs work.

What you pay for

Storage

Per GB per month.

Operations

Per request. Writes (PUT, POST, LIST…) cost roughly 10× more than reads (GET).

Egress

Per GB of data leaving the provider. Often the biggest line for media-heavy apps, and why Cloudflare R2's free egress is popular.

Prices change every few years; check your provider's pricing page when designing.

Key takeaways

  • Object storage trades mutability (no edits, renames, folders or locks) for near-infinite capacity, eleven nines of durability and a plain HTTP interface.
  • Generate keys yourself with randomness up front and ownership encoded; set metadata at write time (changing it means rewriting the object).
  • Durability isn't backup: versioning plus cross-account replication. Your database, not LIST, is the index of files.
  • Stream small uploads through your server with a size cap; send large ones straight to the bucket with presigned POST policies, a pending row, a HEAD check and cleanup.
  • Big files: multipart uploads, part size computed from file size, 4–6 parallel parts, resume via ListParts. Don't trust multipart ETags as checksums, and abort stale uploads with a lifecycle rule on every bucket.
  • Never relay downloads. Use a CDN over a private bucket, presigned GETs (round expiries so the CDN can cache) or CDN-signed cookies; range requests give you seeking, resuming and parallel downloads.

Check yourself

A 60 GB upload with 5 MB parts fails near the end. Why, and what's the fix?

10,000 parts × 5 MB = 50 GB, so part 10,001 is rejected after 50 GB has been sent. Compute the part size from the file size: max(16 MB, size ÷ 10,000), about 6.1 MB here, so 16 MB parts with a 16 MB floor.

Your storage bill keeps rising but the console shows the bucket's size is flat. What might be happening?

Incomplete multipart uploads: their parts are billed but don't appear as objects. List them with "list multipart uploads" and add an AbortIncompleteMultipartUpload lifecycle rule (e.g. 7 days).

You put a CDN in front of private files served by presigned GET URLs, but the cache hit rate is 0%. Why?

Every presigned URL has a unique timestamp and signature, so the CDN sees a different resource each time. Round the expiry (e.g. to the next hour) so users share URLs, or use the CDN's own signed URLs/cookies.

How can a video player start playing at minute 45 of a 2 GB file without downloading the first 1.5 GB?

It computes the byte offset for that timestamp from the file's index and sends a range request (Range: bytes=offset-). The server answers 206 Partial Content with just those bytes.

Why does a 50 GB CompleteMultipartUpload return about as fast as a 50 MB one?

It's a metadata operation: the service records that the object consists of these parts in this order, without physically copying the data.
