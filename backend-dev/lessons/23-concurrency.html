Concurrency & parallelism: IO-bound vs CPU-bound

A server that handles one request at a time can't serve a thousand users. This lesson builds the mental model behind async/await, threads and goroutines: where a request's time actually goes, the difference between concurrency and parallelism, how threads, event loops and Go's scheduler each juggle work, and the bugs that shared state brings.

What you'll learn

  • Why backends are mostly IO-bound
  • Concurrency vs parallelism
  • OS threads and what they cost
  • The event loop, callbacks and what await really does
  • Goroutines and virtual threads
  • Race conditions, locks and channels

Where does a request's time go?

A handler sends a query to the database and waits. Locally that wait is 1–2 ms; in another availability zone, 20–30 ms; in another region, around 100 ms. If the server handles one request at a time, its CPU does nothing during that wait.

That's a lot of nothing. A modern CPU core executes roughly 3 billion instructions per second, 3 million per millisecond. A 100 ms wait wastes the chance to run 300 million instructions.

Anything that waits on something outside the CPU (network, database, disk, the terminal) is IO, input/output. In a typical backend, well over 70% of the time goes to IO. Using that idle time is the problem concurrency solves.

Concurrency vs parallelism

Concurrency: dealing with many things

Structuring a program so tasks can start, pause and resume: while one waits on IO, another uses the CPU. Works on a single core. Both tasks are "in progress", but at any instant only one runs.

Parallelism: doing many things

Executing instructions at the same instant. One core runs one instruction stream at a time, so parallelism needs hardware: two cores for two things at once.

Analogy

One chef puts pasta water on to boil and chops salad while it heats: that's concurrency, one person juggling several dishes by never standing idle. Two chefs cooking side by side is parallelism. A kitchen that's mostly waiting on ovens needs a good juggler more than a second chef.

Validating input or parsing JSON is CPU work too, but usually done in a millisecond or two. Most backends are IO-bound: whether you have one core or eight, the bottleneck is waiting. You still want parallelism for the occasional heavy job.

Under every language's concurrency feature (Go's goroutines, JavaScript's async/await, Java's virtual threads) sit two basic mechanisms: threads and event loops.

Threads

A thread is an independent line of execution managed by the operating system. For each one the OS creates a stack (the chain of function calls and their local variables) and an instruction pointer (where it is in the code). The OS scheduler gives each thread a time slice of a few milliseconds, then pauses it, saves its state and switches to the next, whether the thread likes it or not. That's preemptive scheduling.

When a thread hits a blocking operation like reading a database socket, the OS marks it blocked and runs another thread. When the data arrives, the thread becomes runnable again and waits for its next turn.

Shared memory

Processes are isolated: one can't read another's memory. Threads in the same process share the heap and globals, so they communicate just by reading and writing the same data: fast (no copying, no serialization) and dangerous, as you'll see below.

True parallelism

With several cores, several threads run at the same instant, which is exactly what CPU-bound work needs.

What threads cost

  • Memory. Each thread gets its own stack: 8 MB of virtual memory by default on Linux, with real memory allocated as it's used. Even at ~1 MB each, 10,000 threads need ~10 GB.
  • Creation. A system call into the kernel to allocate the stack and bookkeeping: microseconds to milliseconds.
  • Context switches. Saving one thread's registers and restoring another's costs ~1–10 µs each. With hundreds or thousands of threads on a few cores, that pure overhead adds up to milliseconds.

That's why the thread-per-request model struggles at high concurrency, and why most servers use a fixed pool of threads instead.

The event loop

The other approach uses one thread. When a task needs IO, it doesn't block; it tells the loop "resume me when this result is ready" and hands the CPU back. The loop asks the OS which sockets are ready (via epoll on Linux, kqueue on macOS), runs the callbacks of finished operations, and repeats, forever.

Analogy

One waiter serves twenty tables. They take an order, hand it to the kitchen and move to the next table instead of standing at the kitchen window. When a dish is ready, they deliver it. But if they stop to carve a whole roast at one table, every other table waits.

For IO-bound work this is very efficient: one thread means no context switches and no per-thread stacks. More threads would only add switching. The trade-off is the golden rule: never block the event loop. A 100 ms CPU task freezes every request on the server. Typical SaaS code rarely has one, but image processing, video and ML do, and they belong in worker threads or separate services.

What await really does

Event loops resume work through callbacks: "run this function when the query returns". Chain a few IO calls and callbacks nest inside callbacks, the infamous callback hell. async/await is syntactic sugar over the same idea: everything after an await, to the end of the function, becomes the callback.

// callbacks
function getUser(req, res) {
  db.query("SELECT * FROM users WHERE id=$1", [req.params.id], (err, user) => {
    db.query("SELECT * FROM orders WHERE user_id=$1", [user.id], (err, orders) => {
      res.json({ user, orders }); // …deeper with every call
    });
  });
}
// async/await: same behaviour, flat code
async function getUser(req, res) {
  const user = await db.query("SELECT …", [req.params.id]);
  // ↑ hand the CPU back; resume here when the rows arrive
  const orders = await db.query("SELECT …", [user.id]);
  res.json({ user, orders });
}

Under the hood, the runtime turns an async function into a state machine that advances one state per await:

function fetchUserData(userId) {            // roughly what "async" compiles to
  let state = 0, user, orders;
  return new Promise((resolve) => {
    function step(result) {
      switch (state) {
        case 0: state = 1; db.getUser(userId).then(step); return;        // await #1: loop is free
        case 1: user = result; state = 2; db.getOrders(userId).then(step); return; // await #2
        case 2: orders = result; resolve({ user, orders });
      }
    }
    step();
  });
}

Two puzzles solve themselves: await only works inside async functions because only those are converted into state machines, and blocking the loop is fatal because no state machine can advance to its next step until the loop is free.

Goroutines: lightweight threads

Go takes a third path. A goroutine looks like a thread to your code, but it's managed by Go's own runtime scheduler, not the OS. The runtime starts about one OS thread per CPU core (GOMAXPROCS) and multiplexes thousands, even millions, of goroutines onto them. Switching goroutines is cheap, and each starts with a stack of a few KB, so Go's net/http simply starts a new goroutine for every incoming connection.

Analogy

A restaurant with four cooks (the OS threads, one per stove) and a rail of order tickets (goroutines). A cook whose dish is in the oven doesn't wait; they clip that ticket back on the rail and grab the next one.

Your Go code reads like plain blocking code, with no async or await. The pause happens invisibly, as with threads, but at a fraction of the cost. Java's virtual threads (Java 21) follow the same idea.

def handle_request(user_id):
    user = db.execute("SELECT * FROM users WHERE id = %s", (user_id,))
    # ↑ this OS thread blocks; the OS scheduler runs another thread
    return to_json(user)
async function handleRequest(userId) {
  const user = await db.query("SELECT * FROM users WHERE id = $1", [userId]);
  // ↑ the single thread moves on; this resumes as a callback
  return user;
}
func handleRequest(w http.ResponseWriter, r *http.Request) {
    row := db.QueryRow("SELECT name FROM users WHERE id = $1", r.PathValue("id"))

Race conditions: the price of shared state

Almost every concurrency bug comes from one source: shared state. Even counter++ is three steps: read the value into a CPU register, add one, write it back. If two threads interleave those steps, one update can vanish.

Click the threads' steps in any order. Run A completely, then B, and you get 2. Interleave the reads and you get 1: a lost update.

A single-threaded event loop doesn't save you. Every await is a point where other code can run:

let balance = 100;
async function withdraw(amount) {
  if (balance >= amount) {            // ① check
    await processWithdrawal(amount);   // ② yield: other code runs here
    balance -= amount;                 // ③ act on a stale check
  }
}
withdraw(100); withdraw(100);

Locks (mutexes)

Only one thread at a time may enter the critical section; the others wait for the lock. Simple, but hold locks briefly and in a consistent order to avoid slowdowns and deadlocks.

Channels

Go's alternative: instead of many goroutines touching one variable, they send messages to the single goroutine that owns it. "Don't communicate by sharing memory; share memory by communicating."

Let the database decide

In a backend, shared state usually lives in the database. Make check-and-update one atomic step: UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1, or a transaction with SELECT … FOR UPDATE (lesson 12).

Choosing the right tool

WorkloadBest fitExamples
IO-bound, high concurrencyEvent loop or lightweight threadsWeb servers, API gateways, services calling other services: async/await, goroutines, Java virtual threads
CPU-boundParallelism on OS threads (one per core)Image and video processing, encryption, ML, crunching data

Concurrency keeps your program productive while it waits; parallelism lets it compute on many cores at once. Most backend work leans on concurrency, but knowing which kind of work you have is what lets you pick the right tool.

Key takeaways

  • A typical request spends ~95% of its time waiting on IO; concurrency fills that idle CPU time with other work.
  • Concurrency is dealing with many things (works on one core); parallelism is doing many things at once (needs many cores).
  • IO-bound work needs concurrency; CPU-bound work needs parallelism. Most backends are IO-bound.
  • OS threads give true parallelism but cost memory, creation time and context switches.
  • An event loop handles thousands of connections on one thread, as long as nothing blocks it. await means "resume me later" and compiles to a state machine.
  • Goroutines and virtual threads look like threads but are scheduled by the runtime, cheap enough for one per request.
  • Shared state causes race conditions, even in single-threaded async code. Use locks, channels or atomic database operations.

Check yourself

Your Node.js API's latency spikes for everyone whenever one user uploads a large image to be resized. Why?

Resizing is CPU-bound and runs on the event loop's only thread, so it blocks every other request until it finishes. Move it to a worker thread, a queue worker or a separate service.

Would moving an IO-bound API from 2 cores to 16 cores make it much faster?

Probably not. It's mostly waiting on the database and other services; more cores don't shorten waits. Concurrency, fewer round trips and faster queries help more.

Is a single-core server capable of concurrency? Of parallelism?

Concurrency, yes: it can interleave many tasks, switching whenever one waits. Parallelism, no: that needs instructions executing at the same instant on multiple cores.

Why can Go afford a goroutine per connection when a thread per connection would exhaust memory?

Goroutines start with tiny stacks (a few KB) and are switched by the Go runtime, not the OS, so creating and switching them is cheap. OS threads reserve far more memory and switch through the kernel.

Two requests each run stock = await getStock(); if (stock > 0) await setStock(stock - 1); for the last item. What can go wrong, and how do you fix it?

Both read stock = 1 before either writes, so both sell the last item. Make it atomic in the database: UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0, and check whether a row was updated.
