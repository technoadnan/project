Webhooks: how the server calls you

So far a client always started the conversation; even real-time needed the browser to open a connection first. Webhooks are different: one backend calls another when something happens, with no browser involved. This lesson covers receiving them safely (signatures, replays, duplicates, ordering), sending them reliably (outbox, retries, SSRF guards), and when they're the wrong tool.

What you'll learn

  • Why polling a provider fails and webhooks flip the direction
  • Anatomy of a delivery, deadlines and handshakes
  • Verifying senders: HMAC on raw bytes, timestamps, constant-time compare
  • At-least-once delivery, idempotency and out-of-order events
  • Fast receivers and background processing
  • Sending webhooks: outbox, backoff with jitter, SSRF
  • Notifications vs data sync

Don't call us, we'll call you

The task board sells a paid plan through Stripe. The payment succeeds in Stripe's system, not yours. How do you find out, so you can unlock the plan? Not through the user's browser: the tab can close, the network can drop, and anything client-side can be tampered with. Your server must get the signal.

The brute-force answer is polling Stripe's API every second: an average delay of half a second, nearly every request wasted, and if 10,000 merchants all poll every second, Stripe absorbs 10,000 requests per second. So providers rate-limit you; poll every 60 seconds and the average delay becomes 30. The fix is to reverse the direction: the provider tells you. A webhook is nothing more than an HTTP POST from the provider to a URL you expose and register, a reverse API call.

Analogy

Instead of walking to the door every minute to check whether the parcel has arrived, you install a doorbell. The courier rings it once, when there's actually something to deliver.

Jeff Lindsay proposed the idea in 2007 as the web's version of Unix pipes: user-defined callbacks over HTTP POST, letting one service push its output into another. Two years later, Google engineers built PubSubHubbub on the same idea for blog feeds.

Success means 2xx, fast

Any 2xx (200 or 202) is success; anything else, including 3xx, is failure. And there's a deadline: 10 s for GitHub, 5 s for Shopify, 3 s for Slack; Microsoft Graph is strict too. Miss it and it counts as a failure. Check each provider's docs.

  • One URL per provider: /hooks/github, /hooks/stripe, never a generic /hooks/callback. Each provider has its own headers, signature scheme and retry behaviour.
  • Handshakes: some providers verify a new URL before sending events. Microsoft Graph sends a validation token you must echo back as plain text, Discord sends a ping expecting a pong, Amazon SNS sends a confirmation URL you must visit. Otherwise an attacker could register a victim's URL, subscribe to everything, and use the provider to flood it.
  • Local development: providers can't reach localhost behind your home router. A tunnel (ngrok, Cloudflare Tunnel) gives your local port a temporary public HTTPS URL.

Is it really from the provider?

Your endpoint is public, and URLs like /webhooks or /hooks are easy to guess. Anyone can POST {"type":"payment.succeeded","user_id":42} and get a free plan. HTTPS doesn't help: it stops eavesdropping, but says nothing about who wrote the request.

HMAC (hash-based message authentication code; lessons 8 and 20): the provider computes HMAC-SHA256 over the payload with the shared secret and puts it in a header; you recompute it over the bytes you received and compare. Change one byte and the signature no longer matches. What gets signed varies: GitHub signs the body; Stripe signs timestamp.body; the Standard Webhooks spec signs id.timestamp.body; Twilio signs the full URL plus sorted form fields with SHA-1.

Raw bytes first

Verify the exact bytes you received, then parse. A framework that parses JSON and you re-serialize it changes spacing or number formatting, the HMAC differs, and every genuine delivery fails. In Express, use express.raw() on the webhook route.

Timestamps stop replays

An attacker who captures one genuine delivery can resend it a thousand times; the signature stays valid. Stripe puts the timestamp inside the signed string (so it can't be altered) and its libraries reject anything older than 5 minutes.

Constant-time comparison

A normal string comparison stops at the first differing byte, and that timing difference, measured over many requests, can leak the signature byte by byte. Use hmac.Equal (Go), crypto.timingSafeEqual (Node) or hmac.compare_digest (Python).

At-least-once: duplicates are normal

Your handler upgrades the user and returns 200, but the response is lost (a dropped connection, a load balancer restarting). To the provider that's a failed delivery, so it retries with the same payload, seconds or minutes later. Providers promise at-least-once delivery: never lost, sometimes repeated, never exactly once. Your receiver must be idempotent: the same event, processed any number of times, causes its side effects once.

BEGIN;
INSERT INTO processed_webhooks (delivery_id) VALUES ($1)
  ON CONFLICT (delivery_id) DO NOTHING;      -- unique constraint; 0 rows → already done
UPDATE users SET plan = 'pro' WHERE id = $2;   -- run only if the insert affected a row
COMMIT;

The ID comes from the provider and stays the same across retries: X-GitHub-Delivery, Stripe's event id, webhook-id in Standard Webhooks. Record it in the same transaction as the work. Work first, then the ID, and a crash in between makes the retry redo the work; ID first, then the work, and a failed step is never retried.

Events arrive out of order

Stripe's docs say it plainly: events are not delivered in order. Timestamps have one-second resolution, so events created together look simultaneous. Three fixes:

1

Treat it as a signal

Ignore the payload's data; fetch the object's current state from the provider's API and act on that. Order stops mattering, at the cost of an API call.

2

Version check

Store a version or updated_at per object and apply an event only if it's newer than what you have, in one transaction.

3

Buffer

Hold events until earlier ones arrive. Hard to make predictable. Some providers sell strict ordering instead.

Retries, deadlines and a fast receiver

Retry schedules differ: Stripe retries with exponential backoff for up to 3 days, then disables the endpoint and emails you. Svix, a popular managed webhook service, retries immediately, then after 5 s, 5 min, 30 min, 2 h, 5 h and 10 h. GitHub doesn't retry at all: if you were down, click "Redeliver" or script it through the API.

Put it together: a 3–10 second deadline, every miss turning into a retry on top of your normal traffic, and bursts you don't control (a billing provider renewing every subscription on the 1st, a marketing tool sending receipts for 500,000 emails). Sending webhooks: becoming the provider

Now a customer of the task board wants a task.moved notification when a card reaches "done", to post it in their chat. They give you a URL; you give them a secret. The naive version calls http.post(customerUrl) inside the move handler. Three problems:

Their latency becomes yours

A slow or down customer endpoint stalls your move handler and your frontend.

Commit, then crash

The move is saved, the container dies before the POST: the event is silently lost.

POST, then fail

Send first, and if the database write then fails you've told the customer about a move that never happened.

The fix is the transactional outbox: an ordinary table in the same database. The move handler updates the task and inserts the event into the outbox in one transaction, so both happen or neither does. A separate dispatcher delivers from the outbox asynchronously. It's the write-ahead-log idea from the Postgres lesson, applied to events: write the intent somewhere durable first, deliver later.

For each delivery the dispatcher signs id.timestamp.body with the endpoint's secret (Standard Webhooks format), POSTs with a 10-second timeout, and records the attempt (status code, first 2 KB of the response, timing). A 2xx marks it delivered; anything else schedules the next attempt with exponential backoff plus jitter, honouring a Retry-After header if the receiver sends one. After the final attempt the event is marked exhausted; after 10 consecutive failures the endpoint is disabled and its owner emailed. Each endpoint gets its own queue, so one broken customer can't delay everyone else.

SSRF: the sender's danger

As a provider, you POST to whatever URL a customer registers, from inside your network. Register http://169.254.169.254/… (the cloud metadata service that hands out credentials) or an internal admin host, and your dispatcher becomes an attacker's proxy: server-side request forgery (lesson 20). Validating the URL at registration isn't enough, since DNS can point at a public IP during checks and a private one later. Resolve the hostname and check the IP against private ranges on every send, never follow redirects, treat only 2xx as success, and ideally send through an isolated egress proxy (Stripe open-sourced theirs, Smokescreen).

Building all this is real engineering, which is why many companies hand sending to a service like Svix.

Notifications, not data sync

Webhooks are notifications: "this happened, here's the data". They fit "post it to a channel", "trigger a CI build", "unlock this plan". They're the wrong tool for keeping a copy of a provider's data in sync.

A common case: Clerk handles your authentication, so users, organizations and roles live in Clerk's database. Calling Clerk's API for every check adds 70–600 ms versus a local query, so teams mirror the data into their own tables, kept in sync by user.created, user.updated, organization.deleted… webhooks. Now every edge case applies: downtime, retries, duplicates and above all ordering, and the copy quietly drifts.

The robust version uses the provider's ordered event log (an /events API). It's ordered because it's written inside the provider's own transactions. Key takeaways

  • A webhook is an HTTP POST from a provider to your registered URL: the provider tells you instead of you polling it.
  • Respond with a 2xx within the provider's deadline (3–10 s); use one endpoint per provider; tunnels for local development.
  • Verify every delivery: HMAC over the raw bytes, a signed timestamp against replays, constant-time comparison.
  • Delivery is at-least-once and unordered: deduplicate by delivery ID in the same transaction as the work; fetch current state or compare versions.
  • Keep receivers tiny: verify, store, 2xx, and let a background worker do the rest.
  • When sending: transactional outbox, signed payloads, timeouts, exponential backoff with jitter, per-endpoint queues, and SSRF checks on every send.
  • Use webhooks for notifications. For syncing data, read the provider's ordered event log, with the webhook only as a wake-up signal.

Check yourself

Your Stripe webhook verification fails for every genuine event, though the secret is correct. What's the usual culprit?

The body was parsed by a JSON middleware and re-serialized before computing the HMAC, so the bytes differ from what Stripe signed. Verify against the raw request body, then parse.

A user was charged once but got two months of credit. What went wrong?

The provider retried a delivery (at-least-once) and the handler wasn't idempotent. Record the event or delivery ID under a unique constraint, in the same transaction as the side effect, and skip duplicates.

An attacker captured a genuine, correctly signed webhook and resends it. How do you reject it?

Use a signature that covers a timestamp (and ideally the delivery ID), and reject deliveries outside a tolerance window such as 5 minutes. Deduplicating by delivery ID also stops reprocessing.

Why shouldn't your move handler POST to customers' webhook URLs directly?

Their slowness becomes your latency, and you can't make your database write and their POST atomic: you either lose events (crash after commit) or announce moves that didn't happen (POST before a failed commit). Use a transactional outbox and a separate dispatcher.

Why add jitter to retry backoff?

Without it, everything that failed together retries together, a thundering herd that can knock the recovering endpoint over again. Random jitter spreads the retries out.
