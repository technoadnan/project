Mastering databases with Postgres

A database lets data survive after the program that created it stops. A database management system adds what files can't: fast queries, structure, integrity and safe concurrent access. This lesson walks through what a backend engineer does with Postgres 80% of the time: choosing types, writing migrations, modelling relationships, writing safe queries and adding indexes.

What you'll learn

  • Why disk-based databases, and why not plain text files
  • Relational vs document databases, and why Postgres
  • Data types that matter (and the varchar(255) myth)
  • Migrations, schema design, constraints and relationships
  • Joins, parameterized queries, pagination, triggers and indexes

Why databases?

Persistence means data outlives the program. Close your to-do app, reopen it a week later, and your tasks are exactly as you left them. Broadly, any structured storage that supports create, read, update and delete is a "database": your phone's contact list, the browser's localStorage, even a notes text file.

In backend systems, "database" means disk-based storage (HDD/SSD):

RAM (primary memory)Disk (secondary memory)
SpeedVery fastSlower
Typical size8–128 GB512 GB – several TB
CostExpensiveCheap
Used byCaches (Redis), lesson 13Databases (Postgres, MongoDB)

Databases need lots of space and can trade a little speed for it. Caches do the opposite.

Why a DBMS, not a text file?

A database management system stores data and gives you efficient CRUD, plus organisation, integrity (a payment amount must be a number) and security (users and roles). Early systems really did use text files, and hit three walls:

Parsing

To find one customer, your code reads and splits every line. That's slow (especially in JS or Python) and error-prone.

No structure

A text file accepts anything, so there's no way to enforce "this field is a number".

Concurrency

Two people editing at once means one silently overwrites the other.

Relational vs non-relational

Relational (Postgres, MySQL, SQL Server)

Tables, rows, columns, with a predefined schema and relationships through foreign keys, queried with SQL. Strict, so you can always trust the data's shape. Ideal for a CRM: customers, contacts and deals with strong integrity and complex queries.

Document (MongoDB)

Collections of documents; each document can have a different shape. Fast to prototype and good for unstructured content such as a CMS (articles mixing images, code and embeds). But integrity moves into your application code, which is easier to break.

Why Postgres?

  • Open source and free: self-host it anywhere.
  • Follows the SQL standard: your SQL largely ports to other databases.
  • Extensible: about 1,400 pages of docs and a rich extension system.
  • Reliable and scalable.
  • Excellent JSON support (JSONB, indexable). The main reason to reach for MongoDB, flexible data, is covered inside Postgres.

Not covered here: SQL basics (SELECT, GROUP BY…). There are plenty of free courses; learn those first, then come back.

The varchar(255) myth

In Postgres, text and varchar(n) perform the same, and the official docs recommend text. "255" is a habit carried over from MySQL that means nothing in Postgres, yet it makes readers hunt for a reason that doesn't exist, and changing it later needs a risky migration. Use text and enforce lengths in your validation layer.

Migrations: version control for your schema

In production you never open a GUI and type CREATE TABLE. Changes go into numbered or timestamped SQL files committed with your code, and a CLI tool (dbmate, golang-migrate…) applies them in order. Each file has an up section (apply) and a down section (revert).

Benefits: a full history of schema changes in Git, and rollback when something breaks. A separate seed migration fills development databases with test data.

Designing the schema

Continuing the project-management example from lesson 11:

CREATE TYPE project_status AS ENUM ('active', 'completed', 'archived');
CREATE TYPE task_status    AS ENUM ('pending', 'in_progress', 'completed', 'cancelled');
CREATE TYPE member_role    AS ENUM ('owner', 'admin', 'member');

CREATE TABLE users (
  id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  email         text        NOT NULL UNIQUE,
  full_name     text        NOT NULL,
  password_hash text        NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE user_profiles (                -- one-to-one
  user_id    uuid PRIMARY KEY REFERENCES users ON DELETE CASCADE,
  avatar_url text, bio text, phone text,       -- optional: nullable
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE projects (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  description text,
  status      project_status NOT NULL DEFAULT 'active',
  owner_id    uuid NOT NULL REFERENCES users ON DELETE RESTRICT,
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE tasks (                        -- one-to-many: project → tasks
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  uuid NOT NULL REFERENCES projects ON DELETE CASCADE,
  title       text NOT NULL,
  priority    integer NOT NULL DEFAULT 1 CHECK (priority BETWEEN 1 AND 5),
  status      task_status NOT NULL DEFAULT 'pending',
  due_date    date,
  assigned_to uuid REFERENCES users ON DELETE SET NULL,
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE project_members (              -- many-to-many linking table
  project_id uuid REFERENCES projects ON DELETE CASCADE,
  user_id    uuid REFERENCES users    ON DELETE CASCADE,
  role       member_role NOT NULL DEFAULT 'member',
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (project_id, user_id)           -- composite key
);

Enums

A fixed list of allowed values. The database rejects anything else (integrity), and anyone reading the migration instantly sees the valid states (documentation).

Primary key

Uniquely identifies a row. It implies NOT NULL + UNIQUE and is indexed automatically.

NOT NULL by default

Every column is nullable unless you say otherwise. Aim for 70%+ NOT NULL; buggy scripts love inserting nulls.

Naming

Plural table names, lowercase_snake_case columns. Postgres folds unquoted names to lowercase, so camelCase would need quotes everywhere.

Defaults

id, created_at and enum statuses get defaults, so the app doesn't have to send them.

CHECK

Custom rules such as priority BETWEEN 1 AND 5. A value of 55 never gets in.

Relationships

Analogy

A linking table is like a class register. Students take many classes and classes have many students, so you don't write classes inside student records or vice versa. One register line per (student, class) pair, and that pair can only appear once.

Referential integrity: what happens on delete?

A foreign key already guarantees you can't reference a user who doesn't exist. ON DELETE rules decide what happens when the referenced row goes away:

Queries behind the API

List users, with their profile embedded

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
ORDER BY u.created_at DESC;
  • Write FROM first: know where the data comes from before choosing columns. Short aliases (u, up) keep it readable.
  • LEFT JOIN, not INNER: a user who never edited their profile has no profile row, and an inner join would drop them.
  • Always ORDER BY. Without it, row order isn't guaranteed.

Get one user: parameterized queries

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.id = $1;   -- $1 is a slot, filled separately with the id from the URL

A parameter is a slot whose value is always treated as data, never as SQL. Building queries by gluing strings together invites SQL injection:

Your database driver or ORM handles parameters for you. Use them for every user-supplied value.

Filtering, sorting and pagination

SELECT u.*, to_jsonb(up.*) AS profile
FROM users u LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.full_name ILIKE $1 || '%'      -- only added if ?letter= was sent; ILIKE ignores case
ORDER BY u.email ASC                    -- column + direction picked from a whitelist
LIMIT $2 OFFSET $3;                     -- offset = (page − 1) × limit

Your code builds this dynamically: include the WHERE only if the filter was sent, default to created_at DESC, page 1, limit 10. Column names can't be parameters, so map sortBy to a fixed whitelist (email, full_name, created_at).

Create and update

INSERT INTO users (email, full_name, password_hash)
VALUES ($1, $2, $3)
RETURNING *;                            -- send the created row back in the 201 response

UPDATE user_profiles
SET bio = $1, phone = $2                -- only the fields the PATCH actually sent
WHERE user_id = $3
RETURNING *;

Triggers: keep updated_at honest

You could set updated_at = now() in every UPDATE from app code, and someone will forget. A trigger runs an action automatically when a condition is met:

CREATE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER users_set_updated_at
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();   -- repeat for each table

Indexes

Analogy

To find chapter 4 in a 100-page book, you don't flip through 50 pages: you check the index at the back, see "page 54", and jump straight there. A database index is that lookup table: value → where the row lives on disk.

Indexes can also be ordered. A list endpoint that always returns ORDER BY created_at DESC benefits from an index on created_at DESC, because rows are already in the right order.

CREATE INDEX idx_users_created_at   ON users (created_at DESC);
CREATE INDEX idx_tasks_project_id   ON tasks (project_id);    -- FK used in joins
CREATE INDEX idx_tasks_assigned_to  ON tasks (assigned_to);   -- FK used in joins
CREATE INDEX idx_tasks_status       ON tasks (status);        -- WHERE status = …
CREATE INDEX idx_members_user_id    ON project_members (user_id);

When to index

Columns used in JOIN conditions, WHERE clauses or ORDER BY, on queries that run often. Primary keys (and UNIQUE columns) are indexed automatically; foreign keys are not.

The cost

Every INSERT and UPDATE must also update each index. Add indexes for frequent queries, monitor, and drop the ones that don't pay off.

Key takeaways

  • Databases persist data on disk (cheap, large); caches use RAM (fast, small).
  • A DBMS solves what files can't: fast access, enforced structure, integrity and concurrency.
  • Default to Postgres: SQL-standard, extensible, reliable, with JSONB for flexible data.
  • Use decimal for money, text for strings, timestamptz for time, jsonb for JSON.
  • All schema changes go through migrations (up/down, tracked in a table, committed to Git).
  • Model 1–1 with a shared primary key, 1–N with a foreign key, N–M with a linking table and a composite key. Choose RESTRICT, CASCADE or SET NULL deliberately.
  • Always parameterize user input, always ORDER BY lists, and whitelist sort columns.
  • Index the columns behind frequent JOINs, WHERE clauses and sorts, especially foreign keys.

Check yourself

You store prices as real and totals are off by 0.0000001. What should the type be?

decimal(…, 2) / numeric: exact representation for money.

Users can follow many tags, and tags have many followers. How do you model that?

A linking table user_tags(user_id, tag_id) with a composite primary key, foreign keys to both tables, and usually ON DELETE CASCADE.

"Fetch all tasks of a project" is slow at a million tasks. First thing to check?

Whether tasks.project_id has an index. Foreign keys aren't indexed automatically, so without one, every query is a sequential scan.

Why is WHERE id = '" + id + "'" dangerous even if ids are "just UUIDs"?

The value comes from the client, who can send anything, such as x' OR '1'='1. Concatenation lets that text become SQL; parameters keep it as data.
