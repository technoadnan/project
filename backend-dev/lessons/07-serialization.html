Serialization and deserialization

A JavaScript client and a Rust server don't share a single data type, yet they exchange data all day. They manage it by agreeing on a common format. Converting into that format is serialization; converting out of it is deserialization.

What you'll learn

  • The problem serialization solves
  • The mental model for what happens on the wire
  • Text vs binary formats
  • JSON's rules and types

The problem: two languages, no shared types

Your frontend is JavaScript: dynamic, interpreted, loose types. Your server might be Rust: compiled, strictly typed. A JS object means nothing to Rust. So how does { name: "Ada" } leave a browser and become something a Rust handler can use?

If you had to design the solution yourself, you'd land on the obvious one: agree on a standard. Both sides promise to send data in one shared format and to convert to and from their own types at the edges.

Analogy

Moving house: you can't ship a room as it is. You flat-pack the furniture into standard boxes any truck can carry (serialize). At the new house you unpack and assemble it to fit that house's layout (deserialize). The truck never needs to know what the furniture is.

Watch the round trip

In one sentence: serialization and deserialization convert data to and from a common format, so machines in different languages and environments can understand it, whether it's sent over a network or written to storage.

Analogy: the network layers

When you post a letter you care about the envelope and the address. Which sorting centre, truck or plane carries it is the postal service's problem. JSON is your envelope; the OSI layers below the application layer are the postal service.

For HTTP APIs, JSON is the default, used roughly 80% of the time. It's what the rest of this course assumes, just as it assumes HTTP for transport and Postgres for databases.

JSON in two minutes

JSON (JavaScript Object Notation) looks like a JS object, but it's language-independent. The rules are short:

{                                   // starts and ends with braces
  "id": 1,                         // keys: always double-quoted strings
  "title": "Dune",                  // string
  "price": 9.99,                    // number
  "inStock": true,                  // boolean
  "tags": ["sci-fi", "classic"],     // array
  "author": {                       // nested object, same rules inside
    "name": "Frank Herbert",
    "country": "USA"
  },
  "sequel": null                     // null
}
Common pitfalls
  • Dates have no JSON type. They travel as strings, so agree on ISO 8601 with a time zone ("2025-01-31T10:00:00Z").
  • Missing vs null vs extra fields: decide how your server treats each, and validate before trusting anything (lesson 9).
  • Big integers can lose precision in JavaScript. Send large IDs as strings.

Key takeaways

  • Clients and servers in different languages share no types, so they agree on a common format.
  • Serialize = native → common format; deserialize = common format → native. It happens on both sides, in both directions.
  • Your mental model: JSON in at the application layer, JSON out on the other side. Packets and bits are below your concern.
  • Text formats (JSON) are readable; binary formats (Protobuf) are smaller and faster.
  • JSON: braces, double-quoted string keys, and values that are strings, numbers, booleans, arrays, objects or null.

Check yourself

In one request–response cycle between a JS client and a Rust server, how many times does (de)serialization happen?

Four: the client serializes the request, the server deserializes it, the server serializes the response, and the client deserializes it.

Is {name: 'Ada'} valid JSON?

No. Keys must be double-quoted and strings use double quotes: {"name": "Ada"}.

When might you choose Protobuf over JSON?

For high-volume service-to-service traffic, where smaller payloads and faster parsing matter more than being able to read the payload by eye.
